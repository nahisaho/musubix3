# ADR-0023: Add an audited `tdd void <test-id>` command instead of hand-editing or regenerating `tdd.json`

## Context

`tdd-superseded-cycle-scoping` (Issue #11) already ignores an *earlier*
incomplete/invalid cycle for a test ID when a *later* cycle for the same
test ID has both a valid Red and a valid Green (`supersededCycles` in
`packages/analysis/src/tdd.ts`). It does not cover the reverse ordering: a
genuinely valid Red-Green cycle followed by a *later*, dangling, invalid
cycle for the same test ID. This was hit in this repository's own working
history during CHANGE-0010 (GitHub Issue #20): `TEST-CHANGE-RECORD-FAIL-
FAST-001` accumulated a valid Red-Green cycle followed by a later, dangling
`tdd red` invocation recorded by mistake, which permanently raises
`TDD_RED_MISSING`/`TDD_GREEN_MISSING`/`TDD_LEGACY_OR_UNSCOPED_EVIDENCE` for
that test ID with no tool-supported remedy. `.musubix/evidence/tdd.json`
and its hash chain are append-only and explicitly do not support
hand-editing (the tool's own error messages state this); the only
currently tool-supported remedy is to move `tdd.json` aside and re-record
every cycle in the repository from scratch. For a project with many
already-shipped, passing tests (this repository has roughly 175 recorded
cycles), that remedy is disproportionate: it either discards every other
test's legitimate evidence history, or requires reverting dozens of
unrelated, already-shipped features to fabricate fresh Red states purely
to regenerate evidence for defects unrelated to those features. This
recurrence, and the lack of any non-destructive remedy, was documented in
the reopened GitHub Issue #1.

Three remediations were proposed when Issue #1 was reopened: (1) a scoped
`tdd void <test-id>` command for this exact defect shape, (2) broadening
the `CHANGE_COMPLETENESS_ACCEPTANCE` keyword heuristic, and (3) an audited
evidence-ordering waiver mechanism for the retroactive-recording/
release-gate conflict. This ADR covers only remediation (1); the other two
are deliberately deferred to separate future changes, since they carry
higher design risk — (3) in particular is in tension with this project's
"never weaken a required check without an equally rigorous replacement"
constitution principle and needs its own dedicated design.

## Decision

1. Add a new append-only `void` phase to the TDD evidence chain
   (`TddChainPhase` gains `'void'`; `TddCycle` gains an optional `void:
   TddVoidEvidence` field capturing `approver`, `reason`, `recordedAt`, and
   an `order` sequence), recorded through the same
   `appendChainRecord`/`appendEvidenceOrder` machinery already used by
   `red`/`green`/`refactor`/`migrate`. Identity binding reuses the existing
   `order.json` uniqueness guarantee (records are already uniquely keyed by
   `(kind, entityId, phase)`, with `entityId` set to the cycle's own
   `cycleId`) plus the `TddChainRecord`'s own `testId`/`cycleId` fields, and
   adds one small, additive, backward-compatible schema extension:
   `EvidenceOrderRecord` gains an optional `testId?: string` field,
   populated only on newly appended `tdd`/`void` order records, so the
   order record itself (not only the chain record) can be checked against
   the cycle's own `testId`. Existing `change`-kind records and pre-existing
   `tdd` `red`/`green`/`refactor`/`migrate` order records are unaffected and
   never populate it. Voiding a cycle never edits, reorders, or deletes any
   existing evidence, and never overwrites an already-present `void` field
   (valid or malformed) on the target cycle; it only appends one new
   hash-chained, ordered record to an eligible cycle that does not yet have
   one.
2. Restrict `tdd void <test-id>` to the single, narrow, already-understood
   defect shape: the *latest* recorded cycle for a test ID has no valid
   Green, and an *earlier*, non-voided cycle for the same test ID has both
   a valid Red and a valid Green. Reject every other case (Green already
   valid, no eligible earlier fallback, already carries any void payload)
   with no evidence written, requiring an explicit human `--approver`,
   `--reason`, and `--confirm` on every invocation — mirroring the existing
   `tdd migrate` command's approval discipline.
3. Treat a cycle with a *validly linked* void payload (identity-bound to
   that exact cycle, hash- and order-consistent, checked by one shared
   predicate reused by both `tdd validate` and the `tdd void`/`tdd migrate`
   commands) the same way an already-superseded cycle is already treated
   for the purpose of suppressing `TDD_RED_MISSING`/`TDD_GREEN_MISSING`/
   `TDD_LEGACY_OR_UNSCOPED_EVIDENCE`, without touching `supersededCycles`
   itself or any other diagnostic (`TDD_CHAIN_HASH_MISMATCH`,
   order/sequence, `TDD_DURATION_INVALID`, etc., are unaffected and still
   apply to the void phase's own chain/order records like any other
   phase). A cycle whose void payload fails that linkage check raises a
   distinct malformed-evidence diagnostic instead of any suppression and
   is reported via `tdd validate --json`'s diagnostics, not its `voided`
   summary array.
4. Route `TDD_TEST_STALE` staleness comparison and `tdd migrate` to the
   nearest earlier non-voided valid Red-Green cycle when a test ID's actual
   latest cycle is validly voided, so voiding a dangling cycle does not
   silently disable staleness detection or fingerprint migration for that
   test ID.
5. Report a malformed void payload (missing/duplicate/mismatched chain or
   order linkage) as a distinct diagnostic and apply no suppression for it
   — a defective void record must never silently hide a genuine defect.

## Rejected alternatives

- **Hand-edit `tdd.json` to remove the dangling cycle.** Already explicitly
  unsupported by the tool (its own errors state this); would break the hash
  chain's tamper-evidence guarantee for every downstream record.
- **Archive `tdd.json` and regenerate every cycle from scratch.** The only
  currently tool-supported remedy; verified this session to be
  disproportionate for ~175 existing legitimate cycles (wipes all
  unrelated history, or requires reverting dozens of shipped features to
  fabricate new Red states). Rejected as a routine remedy, though it
  remains available as a last resort for chain corruption unrelated to this
  defect shape.
- **Silently extend `supersededCycles` to also cover a later invalid cycle
  after an earlier valid one.** Rejected: this would suppress diagnostics
  for *every* trailing invalid cycle unconditionally and without any human
  review, approver record, or reason — weakening a required check without
  an equally rigorous, audited replacement, which conflicts with this
  project's constitution.
- **A general-purpose evidence-correction/administrative-override command
  covering many evidence kinds at once.** Rejected as broader than the
  concrete defect actually observed; a scoped, single-purpose command is
  easier to review, audit, and reason about, and does not preclude adding
  narrower commands for other evidence kinds later if a similar defect
  shape recurs there.

## Consequences

- `tdd.json`'s schema gains one new optional field and one new chain phase;
  `order.json`'s schema gains one new optional field; existing evidence and
  all other diagnostics are unaffected.
- The one concrete defect hit during Issue #20/CHANGE-0010
  (`TEST-CHANGE-RECORD-FAIL-FAST-001`'s dangling trailing cycle) becomes
  correctable without archiving/regenerating unrelated evidence.
- Void-linkage validity (and, by extension, `TDD_TEST_STALE`/`tdd migrate`
  effective-latest routing) is gated on the *entire* `order.json` log
  validating cleanly, not only the one order record being checked. This is
  an intentional fail-closed choice: a corrupt order log cannot be
  selectively trusted for one phase and distrusted for another, and an
  invalid order log already blocks `appendEvidenceOrder` for every phase
  today, so this does not newly reduce availability — it only means that,
  until any unrelated pre-existing order-log corruption is repaired, no
  cycle's void (or Green) linkage can be recognized as valid, and the
  normal (unsuppressed) diagnostics for those cycles reappear.
- This does not resolve the separate, still-open structural debt
  documented in Issue #1: the `CHANGE_COMPLETENESS_ACCEPTANCE` keyword
  heuristic's false negatives, and the retroactive-recording-order versus
  all-or-nothing release-approval-gate tension. Those remain tracked as
  deferred remediations (2) and (3).
