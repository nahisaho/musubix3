# ADR-0030: Journaled multi-file evidence replacement with explicit recovery

## Status
Proposed

## Context
A merge must replace `order.json`, `tdd.json`, `changes.json`, and
`change-waivers.json` as one logical unit. Filesystems do not provide an atomic
rename covering four independent files. A process can fail after replacing a
subset, and it can terminate after all replacements but before cleanup, so the
mere presence of temporary files cannot distinguish rollback from committed
state.

## Decision
Build and structurally validate all candidate bytes before mutation. Build a
complete prepared journal containing target existence, original and candidate
bytes, original/candidate hashes, temporary paths, and state in a staging file;
fsync it, then publish it atomically and exclusively as the official journal
before any target write. Write/fsync all temporary candidates, replace all
targets, fsync the evidence directory, then fsync a durable `committed` marker
containing every candidate digest and the directory before cleanup.

Provide `evidence merge --recover` as the only command allowed to proceed when a
journal exists at invocation start. Recovery restores the original set for a
prepared journal. For a committed journal it verifies every target against the
candidate hash after structurally validating the journaled candidate bytes,
rewrites mismatches from those bytes, fsyncs and revalidates the directory, and
only then removes merge-owned temporary files and the journal. Recoverable
failures retain the journal for retry. An unpublished staging file is safe for
recovery to remove because publication precedes all target writes; normal merge
and dry-run refuse and direct the operator to recovery. A malformed published
journal is reported as unsafe
with a manual backup/restore/quarantine/revalidation procedure rather than
guessed. All other evidence readers and writers fail fast instead of observing
or extending a potentially torn state. The guard is enforced in shared
analysis-layer evidence I/O entry points, not only in CLI actions. Merge-owned
files are excluded from evidence-directory enumeration.

Only transient I/O or write failures are retryable. Structurally invalid
journaled candidates or targets that still fail digest/structural verification
after rewrite are unsafe recovery states and require the documented manual
remediation instead of an automatic retry loop.

## Rejected alternatives
- **Sequential writes without a journal.** A mid-write failure leaves a
  structurally inconsistent evidence set with no deterministic recovery source.
- **Temporary files only.** They do not prove whether every target replacement
  completed before termination.
- **Always roll back whenever a journal exists.** A crash after the last target
  replacement but before cleanup would silently discard a successfully
  committed merge.
- **Require the original incoming checkout for recovery.** Recovery needs only
  the current root's journal and must remain possible after a temporary incoming
  directory is removed.
- **Introduce a general evidence-writer lock now.** Concurrent writer locking is
  a separate phase of Issue #28. Exclusive journal creation only prevents two
  merge transactions from owning the same recovery record.

## Consequences
- Handled failures restore byte-identical originals, including restoring an
  originally absent `change-waivers.json`.
- Abrupt termination can temporarily block evidence commands, but recovery is
  deterministic and independent of the incoming directory.
- The journal stores original evidence bytes and can be large; this cost is
  increased further by candidate bytes, but is accepted for deterministic
  rollback and roll-forward and is bounded by the four target files.
- Tests need fault injection at each persistence boundary and must cover both
  prepared rollback, committed roll-forward with a missing/mismatched target,
  interrupted unpublished journal staging, and malformed published-journal
  refusal.
- This phase assumes a single writer. If recovery discards another live merge's
  unpublished staging file, that merge fails its later exclusive publication
  before any target mutation. General concurrent-writer coordination remains a
  later Issue #28 phase.
