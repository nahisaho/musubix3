# ADR-0037: Bind npm publishing to GitHub Release asset digests

## Status
Accepted

## Context
The existing release publisher accepts a directory, selects its sole `.tgz`,
and passes that path to npm. A stale local tarball can therefore be selected
without an explicit tag. Local checksums alone are insufficient because a
repacked dirty tree can produce a self-consistent tarball and checksum file for
the same version. The publish workflow must prove that the exact bytes sent to
npm are the bytes exposed by the selected non-draft GitHub Release.

GitHub Release asset metadata exposes a server-reported `sha256:<digest>` for
each uploaded asset through `gh release view --json assets`. The release
workflow already creates a tarball, SBOM, checksum file, and strict GitHub OIDC
attestation before creating the GitHub Release. npm provenance is separately
created by `npm publish --provenance`.

## Decision
Require a stable `vMAJOR.MINOR.PATCH` tag, explicit `owner/repository`, and
explicit local directory for every validation or publish invocation. The
shared Node.js script validates a closed four-file local set, verifies the
prepared SHA256SUMS entries, queries the selected non-draft GitHub Release, and
byte-compares all four local digests with GitHub's asset digests before
inspecting the embedded npm package manifest. Any GitHub CLI, network,
authentication, schema, draft, asset-set, or digest failure blocks publishing.

Both GitHub Actions publishing paths provide GitHub read authentication, check
out the selected release tag, install
that tagged implementation, download the same GitHub Release into a new empty
directory, and call the shared script. The release workflow's npm job runs only
for a validate-job stable-tag output and only after GitHub Release creation. The
standalone workflow accepts stable release tags only. Local operators follow
the identical download and verify path; provenance-enabled publishing is
GitHub-Actions-only because npm cannot generate provenance from an unsupported
local environment.

Only after GitHub digest equality succeeds, the script parses gzip and tar with
Node.js built-ins. It bounds decompression, validates ustar header checksums,
sizes, bounds, prefix/name paths, entry types, entry cardinality, end blocks,
and the complete archive before accepting `package/package.json`. PAX, GNU
long-name/link, sparse, link, device, and vendor entry types are rejected rather
than skipped because they can override extraction semantics. This avoids
platform-specific shell pipelines and avoids adding a runtime package solely
for one manifest entry.

## Rejected alternatives
- **Keep selecting the sole local tarball.** This has no approved tag identity
  and permits a stale historical tarball when it is the only remaining file.
- **Trust filename, embedded version, and local SHA256SUMS only.** A locally
  repacked dirty tree can satisfy all three while differing from the reviewed
  GitHub Release.
- **Duplicate validation in YAML shell.** Local and two GitHub Actions paths
  would drift, and shell behavior would remain platform-specific.
- **Publish directly from the release workflow artifact.** That preserves one
  run's bytes but does not prove the later standalone publish path uses the
  public GitHub Release selected by its explicit tag.
- **Accept prerelease tags without an npm dist-tag policy.** Publishing a
  prerelease without an explicit non-latest dist-tag can change npm's default
  install target. This change therefore limits publishing to stable tags.
- **Require GitHub Release immutability.** Existing repository releases report
  `isImmutable: false`; current per-asset digest equality provides the required
  publish-time byte identity without claiming the release can never change.
- **Use the system `tar` executable or add a tar dependency.** The former adds
  a platform prerequisite and shell parsing; the latter expands the published
  dependency surface for a bounded validation operation.

## Consequences
- Publishing requires GitHub CLI access and a reachable, non-draft GitHub
  Release. Query failure blocks release rather than degrading to local checks.
- Replacing any GitHub Release asset changes its server digest, so a previously
  downloaded directory must be downloaded again before it can pass.
- Direct `release:prepare` output is intentionally insufficient because the
  strict CI attestation is added later; local verification starts from a fresh
  GitHub Release download, and publishing remains CI-only.
- Releases may contain only the four defined assets. Adding another release
  artifact requires an approved requirement/design update.
- Prerelease GitHub Releases remain supported; npm publishing is skipped in the
  release workflow and rejected by standalone publish dispatch validation.
- The custom tar reader becomes security-sensitive validation code and requires
  exhaustive malformed-header, path, truncation, duplicate-entry, and package
  identity tests.
