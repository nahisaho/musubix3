# ADR-0011: Record Red/Implementation/Green change phases as independent per-subset batches, keeping the full-set form unchanged

## Context

`ChangeRecord.phases` records the Red, Implementation, and Green phases of a
staged change exactly once each, always scoped to the change's full
declared requirement ID set. `validateChangeCompleteness`'s
`CHANGE_COMPLETENESS_TDD` check, and the parallel `CHANGE_RED_UNPROVEN`/
`CHANGE_GREEN_UNPROVEN` checks in `validateChangeEvidence`, require every
requirement's TDD cycle to fall between the change's `requirements`/`red`
markers (Red) and `implementation`/`green` markers (Green). Because these
three markers are recorded only once per change, this is satisfiable only by
completing Red TDD for every requirement before recording the single `red`
marker, implementing everything before recording the single `implementation`
marker, and completing Green TDD for every requirement before recording the
single `green` marker (GitHub Issue #12). This blocks the interleaved
per-requirement Red-implement-Green loop that `sdd-change`'s own workflow
guidance describes, for any change spanning more than one requirement.

Existing production change chronology evidence (for example `CHANGE-0001`,
recorded before this change, spanning eight requirements) already relies on
the full-set, once-per-change form; it must keep validating unmodified.

## Decision

Allow `change-record` to record Red, Implementation, and Green evidence
multiple times per change, as independent "requirement batches", each scoped
to a distinct, explicit, non-empty subset of the change's declared
requirement IDs:

- Recording a phase with the **exact full requirement ID set** of the
  change behaves exactly as today: at most one occurrence, validated with
  the existing full-set logic and stored in `ChangeRecord.phases`
  unchanged. No existing evidence file or validation result changes.
- Recording a phase with a **proper, non-empty subset** of the change's
  requirement IDs creates or continues a batch, stored in a new
  `ChangeRecord.tddBatches` array, keyed by that exact requirement ID
  subset. Within a batch, Red must precede Implementation must precede
  Green (same one-shot-per-phase, strict-order guarantee as before, just
  scoped to the batch instead of the whole change); Red still requires the
  change's (singular) Design phase to already be recorded. Quality still
  requires every declared requirement ID to be covered by a recorded Green,
  whether from the full-set form or from any batch.
- `validateChangeEvidence`/`validateChangeCompleteness` evaluate
  `CHANGE_TESTS_UNCHANGED`, `CHANGE_IMPLEMENTATION_UNCHANGED`,
  `CHANGE_RELEVANT_IMPLEMENTATION_UNCHANGED`, `CHANGE_TEST_CHANGED_AFTER_RED`,
  `CHANGE_RED_UNPROVEN`, `CHANGE_GREEN_UNPROVEN`, and
  `CHANGE_COMPLETENESS_TDD` per batch (the full-set form is simply the one
  batch covering every requirement), instead of always against the single
  change-level markers.
- Each batch's Red/Implementation/Green phase evidence is still appended to
  the existing append-only monotonic evidence order log
  (`.musubix/evidence/order.json`), distinguished by including the batch's
  requirement ID subset in the logged phase key, so batches remain
  independently, verifiably ordered without any change to the order log's
  schema or hash-chaining.

## Rejected alternatives

- **Loosen the existing single full-set marker's ordering constraints** (for
  example, drop the requirement that Green TDD occur after the
  `implementation` marker). Rejected: this would weaken the
  `CHANGE_IMPLEMENTATION_UNCHANGED`/`CHANGE_RELEVANT_IMPLEMENTATION_UNCHANGED`
  proof that implementation genuinely changed between Red and Implementation
  for every requirement, without actually enabling independent
  per-requirement interleaving — a requirement's Green evidence would still
  be checked against every other requirement's shared markers.
- **Silently reinterpret a repeated `red`/`implementation`/`green` recording
  call as replacing the prior one.** Rejected: this mutates previously
  recorded, hash-chain-linked evidence in place, which is exactly the
  "hand-editing evidence" pattern this project's evidence model is designed
  to make impossible (see `ADR-0009`).
- **Require a new explicit human-approved operation (analogous to `tdd
  migrate`) to unlock multi-batch recording.** Rejected: unlike the
  fingerprint-algorithm migration in `ADR-0009`, there is no retroactive
  drift to reconcile here — every batch's evidence is freshly recorded,
  forward-only, and mechanically checkable without human judgment, so no
  approval step is needed to keep the append-only guarantee intact.

## Consequences

- A change with multiple requirements can complete a genuinely interleaved
  Red-implement-Green loop, recording each requirement's (or requirement
  group's) phases independently, while a change recorded the old, single
  full-set way keeps validating identically to before this change.
- `ChangeRecord.phases.red`/`implementation`/`green` remain valid, in-place,
  bit-for-bit compatible fields for the full-set form; `tddBatches` is
  purely additive.
- Diagnostics that previously referenced only the change's single Red/
  Implementation/Green markers now also identify which batch (requirement ID
  subset) a violation belongs to, for changes that use batches.
