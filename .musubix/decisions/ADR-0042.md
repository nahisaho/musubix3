# ADR-0042: Fail-fast `tdd red`/`tdd green` change-record phase precondition, gated on staged-change adoption

## Context

GitHub Issue #67 reproduces a real incident from the CHANGE-0047 (Issue #55)
implementation session: `tdd green` was run before `change-record
red`/`implementation` had been recorded for the requirement. `runTddPhase()`
(`packages/analysis/src/tdd.ts`) has no awareness of `.musubix/evidence/changes.json`
at all; it only validates against its own prior recorded TDD cycle
(`previous.red.valid`, matching command name, matching test fingerprint).
`hasValidTddCycle` (`change-evidence.ts`), which does know about change
chronology, only runs later — during `change validate`/`gate` — by which
point `runTddPhase()` had already executed the configured test command and
appended a new hash-chained entry to `.musubix/evidence/tdd.json` and the
monotonic order log. Recovering from the resulting invalid cycle required
stashing the implementation, redoing Red→Implementation→Green in the correct
order, manually repairing the hash-chain tail, and recovering a stale
evidence-writer lock — exactly the costly, risky manual recovery ADR-0013
already eliminated for the narrower testId/requirementId mismatch case.

Not every project using `tdd red`/`tdd green` uses the staged-change
(`change-record`) workflow at all: `gate.ts` already treats `change-history`/
`change-completeness` as optional unless the project has at least one staged
change document (`hasChangeDocuments`, also reused by `tdd.ts`'s existing
`TDD_ADOPTION_PROJECT_WIDE` warning). Any new precondition must not force a
non-staged-change TDD workflow to adopt `change-record`.

## Decision

1. Add a new pure helper, `changeRecordPhasePrecondition(evidence, phase,
   requirementId)`, to `packages/analysis/src/change-evidence.ts` (not
   `change.ts`, which `tdd.ts` cannot import without creating a real module
   cycle, since `change.ts` already imports from `tdd.ts`; `change-evidence.ts`
   only has a type-only import from `tdd.ts`, which is erased at compile time).
   `evidence` may be `null` (no `.musubix/evidence/changes.json` yet); this is
   treated identically to "zero matching candidates" below, not as a
   separate case. For `phase: 'red'`, it is satisfied when at least one `ChangeRecord` whose
   `requirementIds` include `requirementId` has `phases.design` recorded. For
   `phase: 'green'`, it is satisfied only among those same design-satisfying
   candidates: when at least one such change's `effectiveBatches`-resolved
   batch (via the existing `batchFor` selector) for `requirementId` has both
   `red` and `implementation` recorded. Critically, `phase: 'green'` reuses
   the exact same "does any candidate have `phases.design` recorded" check
   first, and reports `missingPhase: 'design'` whenever it fails that shared
   check (rather than ever reporting `missingPhase: 'red'` for a candidate
   that could not legitimately have `red` recorded yet without `design`,
   since `change.ts`'s own `recordChangePhaseUnlocked` already requires
   `phases.design` before a batch `red` can be recorded) — this avoids ever
   naming a `change-record red` command that `change.ts` would itself still
   reject for missing `design`. Only once at least one candidate already has
   `design` recorded does `green`'s check distinguish `missingPhase:
   'implementation'` (a design-satisfying candidate has `red` but not
   `implementation`) from `missingPhase: 'red'` (one has `design` but
   neither). It returns the best-matching candidate `changeId` and the
   single missing phase name, so the caller can name an exact
   `change-record` command that `change.ts` itself would currently accept.
2. In `runTddPhaseUnlocked()`, before any side effect (any preflight command,
   the configured test command itself, or any evidence/order-log write), and
   only when the project already has at least one staged change document,
   call this helper against `loadChangeEvidence(root)` and throw a descriptive
   error naming the exact `change-record <change-id> <phase> --requirement
   <requirement-id>` invocation required first when it is not satisfied.
3. Leave `hasValidTddCycle` and every other existing post-hoc validator
   completely unchanged: this is a complementary, independent, earlier guard,
   not a replacement for the authoritative order-window check that `gate`/
   `change validate` still run.

This mirrors ADR-0013's existing pattern (validate fully before any side
effect, reject with the existing diagnostic shape) extended to a second,
independent precondition source (change chronology rather than the TDD
evidence file's own prior cycle), while reusing the existing
`hasChangeDocuments` gate so this check applies only to projects already
following the staged-change workflow.

## Rejected alternatives

- **Weaken or replace `hasValidTddCycle`'s post-hoc check instead of adding a
  pre-check.** Rejected: the post-hoc check is the authoritative source of
  truth consulted by `gate`/`change validate` across every recording path
  (including direct evidence-file edits in tests); removing or loosening it
  would reduce overall correctness guarantees instead of adding a convenience
  guard in front of them.
- **Always require a satisfied change-record precondition, even with zero
  staged change documents.** Rejected: this would force every TDD-only
  project (that never adopts `change-record` at all) to start using the
  staged-change workflow just to keep using `tdd red`/`tdd green`, a breaking
  change to an already-supported, independently valid usage mode.
- **Have `tdd.ts` import the precondition check from `change.ts` directly.**
  Rejected: `change.ts` already imports several functions from `tdd.ts`
  (`loadTddEvidence`, `validlyVoidedTddCycles`, `validlyArchivedTddCycles`);
  importing `change.ts` back from `tdd.ts` would create an actual runtime
  module dependency cycle. Placing the new helper in the existing
  no-dependency `change-evidence.ts` module (already used for this exact
  purpose by `change-waiver.ts`) avoids the cycle without duplicating logic.
- **Require the CLI `tdd red`/`tdd green` commands to take an explicit
  `--change-id` option instead of searching change chronology by requirement
  ID.** Rejected: every existing post-hoc validator (`hasValidTddCycle`,
  `validateChangeEvidence`, `validateChangeCompleteness`) already resolves a
  requirement's governing change purely from `requirementIds` membership, with
  no `changeId` argument; adding one here would be an inconsistent, redundant
  CLI surface for information already fully recoverable from existing
  evidence.

## Consequences

- An agent or developer that runs `tdd green` (or `tdd red`) out of order in
  a staged-change project now receives an immediate, actionable rejection
  before any evidence is written, instead of corrupting the append-only
  hash chain and needing manual recovery.
- Projects with zero staged change documents are completely unaffected.
- The new helper duplicates no existing order-window/batch-matching logic; it
  reuses `effectiveBatches`/`batchFor` exactly as `hasValidTddCycle` already
  does, so the two checks cannot silently diverge in what they consider "the
  current batch" for a requirement.
