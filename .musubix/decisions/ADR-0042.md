# ADR-0042: Isolate volatile native output and persist a canonical aggregate record

## Context

Native test adapters currently direct their runner output to tracked
`.musubix/evidence/native/<command>/aggregate*` paths. Vitest, Jest, pytest,
TRX, and JUnit reports may contain wall-clock timestamps, elapsed durations,
randomized filenames, or ordering that changes between semantically identical
runs. Keeping those raw reports as durable evidence causes repository-wide
churn and invalidates approval manifests.

The durable result must still prove command identity, current related inputs,
adapter/report provenance, process success, and normalized annotated tests.
Performance and model-correspondence validators also reread the report path and
must remain fail-closed. Targeted TDD report bytes are already bound into
append-only cycle evidence and are outside this aggregate-only correction.

## Decision

For full-command native adapter execution, write raw runner output only below
`.musubix/cache/native/**`. After a successful process and successful native
normalization, replace the tracked aggregate path with one deterministic
canonical JSON record. The record excludes raw timing/output fields and
contains command provenance, a trace-linked path/content input fingerprint,
adapter/source metadata, process result, and normalized tests.

Use the reported TEST IDs and the current trace graph to derive the minimal
related input set: each retained test node's source plus code paths
implementing requirements verified by that test, directly or through a design
node satisfying the requirement. `buildTrace` remains authoritative for
duplicate diagnostics and its retained node is used for this projection;
reported IDs without a retained trace node remain semantic test results but add
no path. Persist sorted path/content hashes and their digest, and recompute both
the path set and contents during downstream validation.

Keep targeted TDD adapter invocation paths and raw-report hashes unchanged.
Remove raw aggregate output and the durable aggregate after any non-successful
or invalid execution. Durable cleanup accepts either a legacy directory or a
file, leaves the path absent, and never recreates a report directory. Existing
raw aggregate files and directory-shaped aggregates are migrated by the next
successful gate run; standalone validation rejects them until refreshed. The
existing extensionless durable `aggregate` path for directory adapters is kept
as the canonical JSON file to preserve report-path identity.

## Rejected alternatives

- **Keep raw aggregate reports and exclude timing fields only from approval
  hashes.** Rejected because tracked bytes, reviews, and merge conflicts would
  still churn even if one consumer ignored the differences.
- **Scrub raw output in place at the tracked path.** Rejected because directory
  adapters need a directory during execution, crashes can leave volatile
  tracked content, and raw filenames remain observable before normalization.
- **Store both raw and canonical reports under tracked evidence.** Rejected
  because the raw copy preserves the original churn and creates two competing
  report authorities.
- **Fingerprint the entire repository.** Rejected because an unrelated
  documentation or feature edit would rewrite every command aggregate and
  recreate repository-wide evidence churn.
- **Canonicalize targeted TDD reports in the same change.** Rejected because
  their raw digest is part of existing append-only TDD evidence and requires a
  separate migration policy.
- **Treat elapsed duration as deterministic performance proof.** Rejected
  because wall-clock duration is environment-dependent; declared operation
  counters remain the deterministic performance mechanism.

## Consequences

- Unchanged successful gate reruns produce byte-identical tracked native
  aggregate evidence.
- Raw test telemetry remains available only during command execution or from
  the runner's own external output, not as durable tracked evidence.
- Source changes related through trace links stale only the affected command
  aggregates; unrelated paths do not.
- A shared implementation file linked to several reported requirements can
  still stale several command aggregates, but the blast radius is limited to
  commands reporting tests whose trace projection reaches that file.
- Performance and model-correspondence validation gain explicit schema,
  command, source, and TEST-resolution diagnostics.
- Upgraded repositories must run gate successfully once to replace legacy raw
  aggregates before standalone downstream validation can pass.
- Targeted TDD native reports retain their existing raw format and evidence
  compatibility.
