# ADR-0025: Bounded, audited severity-downgrade waiver for change recording-order debt

## Status
Accepted

## Context
`sdd-change`'s workflow requires `requirements`/`design` to be human-approved
before `impact` can legitimately be recorded, and TDD Red/Green cycles are
commonly executed before the corresponding `change-record` phase is recorded
at session end. Both are structurally unavoidable without fabricating
evidence or reverting already-shipped, passing code. They cause
`validateChangeEvidence` (`change-history`) to raise
`CHANGE_REQUIREMENTS_UNCHANGED`, `CHANGE_DESIGN_UNCHANGED`,
`CHANGE_RED_UNPROVEN`, `CHANGE_GREEN_UNPROVEN`, and cause
`validateChangeCompleteness` (`change-completeness`) to raise
`CHANGE_COMPLETENESS_TDD`, purely from recording order, not from missing
work. `approval-record.ts`'s release-approval gate then hard-blocks on both
checks reporting `pass`, so release approval becomes permanently unreachable
once several `sdd-change` cycles accumulate in one repository (GitHub Issue
#1, recurrence comment, items 1 and 4).

## Decision
Add an explicit, human-approved `change waiver record <CHANGE-ID> <CODE>
[--requirement <REQ-ID>] [--detail <value>] --reason <text> --approver
<name> --confirm`
command that downgrades one specific, currently-present diagnostic instance
of one of the allow-listed codes (originally five under this ADR;
extended to twelve, with a generalized `--detail` scope key, under
CHANGE-0012 — see "Update (CHANGE-0012)" below) from `severity: "error"` to
`severity: "warning"`, as an appended, self-chained, audited record in
`.musubix/evidence/change-waivers.json`. The diagnostic is never removed
from the report — only its severity changes, and only for the exact
`changeId`/`code`/`requirementId`/`detail` scope recorded. `validateChangeEvidence`/
`validateChangeCompleteness`'s `valid` result (and `gate`'s repo-wide
consumption of it) is redefined as "no error-severity diagnostic remains",
so a validly waived warning no longer fails the check, while any other,
non-waived instance of the same code still fails it. A waiver is bound to a
versioned snapshot hash of the exact evidence fields its code's predicate
reads; if that evidence changes after recording, the waiver becomes stale
and the diagnostic reverts to `error`, plus a separate stale-waiver
diagnostic is raised, so a waiver can never silently keep suppressing an
updated evidence state.

## Rejected alternatives
- **Delete or hand-edit the offending evidence.** `.musubix/evidence/
  changes.json`/`tdd.json` are append-only and hash-chained; deleting or
  editing entries orphans hash-chain/order-log records and is equivalent to
  fabricating history, not pruning it (confirmed empirically for the
  original `CHANGE-0003`/TDD-chain investigation in Issue #1).
- **Loosen the underlying `CHANGE_REQUIREMENTS_UNCHANGED`/
  `CHANGE_RED_UNPROVEN`/etc. predicates themselves** (e.g., allow Red/Green
  to precede `requirements`/`design` phase recording generally). This would
  silently weaken the check for every change, including genuinely
  unreviewed, fresh recording-order violations, not just the specific,
  human-reviewed instances this ADR targets.
- **Blanket per-change "skip these checks" flag.** A flag that disables an
  entire check for a change would also suppress genuinely new violations
  introduced later in that same change's lifecycle, and would not require
  per-diagnostic-instance human review.
- **Fully suppress (remove) the waived diagnostic rather than downgrade to
  `warning`.** Removing it entirely would erase the audit trail from
  `gate --json`'s report; downgrading preserves visibility (`waivers` array,
  and the diagnostic itself with attached waiver metadata) while still
  unblocking the check.
- **Reuse the existing `tdd void` mechanism instead of a new one.** `tdd
  void` targets a single dangling TDD cycle's identity; these codes
  concern change-level or requirement-scoped *evidence-ordering* debt in
  `changes.json`, a materially different evidence shape and validator, so a
  distinct, narrowly-scoped mechanism was chosen instead of overloading
  `tdd void`'s semantics.

## Consequences
- Release approval becomes reachable again once every genuinely
  unaddressed diagnostic (waived or otherwise resolved) is cleared, without
  fabricating evidence or reverting shipped code.
- Every waiver is a permanent, auditable record naming its approver,
  reason, and the exact scope it covers; `gate --json`/`status --json`
  surface active waivers for review.
- Evidence-ordering debt of this specific shape no longer silently
  compounds indefinitely across many `sdd-change` cycles, but each instance
  still requires an explicit human decision, not an automatic pass.
- The original five-code allow-list was intentionally narrow; extending it
  (or the scope-key grammar) to cover a different diagnostic shape
  requires a new, separately reviewed change, not a configuration toggle
  (exactly what CHANGE-0012, below, did).

## Update (CHANGE-0012): generalized allow-list and scope key
`gate --changed` resolution work following Issue #1's recurrence surfaced
seven further diagnostic codes of the identical recording-order nature —
`CHANGE_RECORD_MISSING`, `CHANGE_PHASE_MISSING`,
`CHANGE_ORDER_MIGRATION_REQUIRED`, `CHANGE_TESTS_UNCHANGED`,
`CHANGE_IMPLEMENTATION_UNCHANGED`, `CHANGE_RELEVANT_IMPLEMENTATION_UNCHANGED`,
and `CHANGE_TEST_CHANGED_AFTER_RED` — outside the original five-code
allow-list, following exactly the process this ADR's final consequence
anticipated (a new, separately reviewed requirements/design change, not a
configuration toggle). Two extensions to the original decision:
- **Generalized scope key.** Several of the new codes can report more than
  one simultaneous instance for the same `changeId` (e.g. several
  independently missing TDD batches). Rather than adding an ad hoc third
  scope field per new code, the mechanism gains one additional, optional
  `--detail`/`detail` scope key alongside the existing `--requirement`/
  `requirementId`, with a single canonical grammar
  (`phase:<name>`/`batch:<phase>:<batchKey>`/`requirement:<REQ-ID>`/bare
  `<batchKey>`) computed by one shared function
  (`diagnosticDetail`/`parseDetail`) used identically at emission,
  recording, and matching time, so the scope-key regime stays data (four
  exhaustive sets partitioning the allow-list) rather than scattered
  per-code conditionals.
- **`CHANGE_COMPLETENESS_CODE` deliberately excluded.** Considered and
  rejected for the allow-list: unlike every other candidate, it reports a
  genuine missing Code Graph implementation-linkage gap for a requirement,
  not an after-the-fact recording artifact — the underlying work is
  actually absent, not merely unrecorded. Waiving it would let a
  requirement complete without ever having linked implementation, directly
  contradicting this ADR's founding premise ("not from missing work").
- **`CHANGE_RECORD_MISSING` linkage inversion.** Unlike every other code,
  this diagnostic fires when `changeId` is *absent* from
  `.musubix/evidence/changes.json`, so its valid-linkage rule is the
  logical inverse of the others (valid exactly when the change document
  exists and the chronology entry does not) and its snapshot payload
  additionally tracks an append-only `order.json`-derived "ever recorded"
  sentinel (in addition to the change-document digest and the current
  entry's presence/content) specifically so a waiver cannot silently
  reactivate after an entry is added and later removed.
- **Waiver supersession.** A scope may legitimately accumulate more than
  one validly linked waiver record over time (an earlier one going stale,
  then being explicitly replaced); the record with the greatest `order`
  within a `changeId`/`code`/`requirementId`/`detail` scope is the sole
  authoritative one for staleness evaluation and gate/status visibility,
  so replacement remains possible without orphaning or double-invalidating
  history.
The allow-list is now twelve codes (`CHANGE_COMPLETENESS_CODE` remains
permanently excluded on principle, not merely omitted for this round). Any
future extension follows this same explicit, separately reviewed process.
