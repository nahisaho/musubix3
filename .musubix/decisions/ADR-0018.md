# ADR-0018: Bound file-read concurrency with a shared worker-pool helper

## Context

`snapshot()` (`packages/analysis/src/files.ts`) and the per-language source
loaders in `packages/analysis/src/graph.ts` each read a list of file paths
via a single unbounded `Promise.all(paths.map(async (path) => readFile(...)))`.
The number of simultaneously open file descriptors this launches is exactly
the number of paths in the list. On a project containing a large vendored
or third-party source tree not covered by the standard exclusion list
(GitHub Issue #17: a full Django framework checkout, thousands of `.py`
files), this exceeds the OS file-descriptor limit (commonly 1024 on
WSL/Linux) and aborts `musubix3 init`/`trace build`/`graph index` with a raw
`EMFILE: too many open files` error instead of completing or failing with an
actionable diagnostic.

## Decision

- Add a single shared helper, `mapWithConcurrency(items, limit, worker)`, in
  `packages/analysis/src/files.ts`, that processes `items` with at most
  `limit` `worker` calls in flight at any time and returns results in the
  same order as `items` (not completion order).
- Use a fixed limit (256) chosen to stay comfortably under common default
  OS file-descriptor limits (1024 on Linux/WSL, higher on macOS) even when
  the tool itself already holds a handful of descriptors open, while still
  giving useful I/O parallelism for typical projects.
- Replace `snapshot()`'s unbounded `Promise.all` and each per-language
  `Promise.all(...map(... readFile/readText ...))` loader in `graph.ts`, and
  the Markdown document loader in `knowledge.ts#buildKnowledge`, with calls
  to `mapWithConcurrency`, preserving each function's existing return shape
  (a `Record`/`Map`/array keyed or ordered by path) exactly.
- Scope this change to `files.ts#snapshot`, `graph.ts`'s per-language
  loaders, and `knowledge.ts`'s Markdown loader — the call sites whose
  input size scales with total project-wide file count (`knowledge.ts`'s
  `artifactPaths()` scans every `.md` file under the project root, not
  just `.musubix/features/*` artifacts). The `Promise.all` file-reading
  call site in `gate.ts` operates over `.musubix/features/*/{requirements,
  design}.md`, bounded by feature count, and the one in `adapters.ts`
  operates over per-invocation test-report files, bounded by test-report
  count; neither scales with total project size, so both are out of scope
  for this decision.

## Rejected alternatives

- **Add a third-party concurrency-limiting dependency (e.g. `p-limit`).**
  Rejected: the constitution favors minimal dependencies for a CLI that is
  itself distributed to consumer projects; a ~15-line in-repo helper avoids
  a new supply-chain dependency for a single, narrowly-scoped concern.
- **Raise the process's file-descriptor limit at startup (`process.setrlimit`
  equivalent).** Rejected: Node.js has no supported API to raise
  `ulimit -n` for the current process, and even if it did, silently
  requesting a higher OS limit is invisible to the user and does not bound
  the tool's own resource usage on constrained environments (containers,
  CI).
- **Sequential (`for` loop, concurrency 1) file reads.** Rejected: safe but
  needlessly slow for the common case of a moderately sized project; a
  bounded pool keeps most of the parallelism benefit while capping worst-case
  descriptor usage.

## Consequences

- `musubix3 init`/`trace build`/`graph index` complete on projects with very
  large trace-eligible file counts instead of crashing with `EMFILE`.
- All call sites keep their existing return types and ordering; no
  consumer-visible interface changes.
- Future call sites reading project-size-scaled file lists should reuse
  `mapWithConcurrency` rather than reintroducing an unbounded `Promise.all`.
