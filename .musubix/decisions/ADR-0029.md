# ADR-0029: Base-first semantic merge of evidence histories

## Status
Proposed

## Context
The shared evidence order log is an append-only, hash-linked chronology whose
sequence values are referenced by TDD, change, and waiver evidence. Two Git
branches can each be valid while assigning the same sequence numbers to
different appended records. A text merge cannot resolve those collisions, and
wall-clock `recordedAt` values are not correctness-bearing chronology.

The repository also retains historical order records whose current dependent
payload has been pruned. A supported merge therefore cannot assume every order
record has a current TDD cycle, change record, or waiver payload.

## Decision
Treat the current root as the base history. Preserve every base order record in
its current relative order, then process incoming order records in incoming
relative order. Deduplicate non-waiver order records by their logical
kind/entity/phase/scope identity regardless of whether either side still has a
dependent payload. Retain the only payload when one side has it; when both have
payloads, require canonical semantic equality after removing only fields that
the merge reconstructs. Preserve unpaired waiver order records as distinct
because waiver order identity intentionally includes its sequence.

Map every source sequence to a merged sequence and require that mapping to
remain strictly increasing within both source histories. Reject, rather than
guess, when a duplicate would invert source chronology or when matching
payloads disagree. For a cycle/change entity present on both sides, retain one
base-positioned entity, require identical entity headers, and union its phase
content by logical phase identity; duplicate entity IDs inside one input are
invalid. Persisted change TDD batches are matched by sorted requirement key only
when that key is unique within each input; ambiguous duplicate-key matching is
rejected, the synthesized legacy full-set batch is not treated as a persisted
batch, and unmatched incoming batches append after retained base batches. Emit
payload arrays with stable base-first positions and require post-merge
validation whenever any incoming order record is appended or any incoming
payload is retained.

## Rejected alternatives
- **Sort both branches by `recordedAt`.** Clock skew and rebases make timestamps
  unsuitable for correctness; ADR-0027 established monotonic `order` as the
  authoritative chronology.
- **Interleave by record hash or lexical identity.** This is deterministic but
  invents chronology unrelated to either branch and can invert Red/Green or
  staged-change boundaries.
- **Always prefer the incoming payload on conflict.** This silently discards
  valid base evidence and can manufacture a proof that neither reviewer
  approved.
- **Drop unpaired order records.** The order log is append-only history, and the
  current repository intentionally contains historical entries whose payloads
  are no longer present.

## Consequences
- Merged order is deterministic and auditable: base history remains fixed and
  incoming additions become later chronology.
- Some otherwise-equivalent cherry-pick layouts are rejected when deduplication
  would invert incoming order. The operator must resolve that ambiguity before
  retrying.
- If base Quality is already recorded and incoming history adds a later batch
  phase for the same change, base-first order would place that phase after
  Quality and candidate validation rejects the merge. Histories must be merged
  before recording Quality, then Quality must be recorded against the merged
  history; the merge command does not move or forge terminal evidence.
- `recordedAt` warnings can appear after merge without indicating corruption.
- Stale waiver snapshots remain recorded but inactive; the merge never forges a
  replacement approval hash. Because waiver snapshots bind order values, cycle
  sets, and change payloads, staleness is routine after a real merge; previously
  waived errors become active until the waiver is explicitly re-approved.
- Normal gate/status validation remains mandatory because adding an incoming
  payload can change positional latest-cycle or latest-batch selection even
  when its order record deduplicates, and appended waivers can change the
  greatest-order authoritative waiver for a scope.
- The command merges only `order.json`, `tdd.json`, `changes.json`, and
  `change-waivers.json`. Workflow, approvals, quality, formal, mutation,
  correspondence, performance, attestation, native test reports, and other
  evidence retain their existing regeneration or conflict-resolution
  procedures.
