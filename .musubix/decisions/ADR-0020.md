# ADR-0020: Use OS-level exclusive create (`wx`) instead of shared `writeText()` for scaffold artifact writes

## Context

`packages/analysis/src/files.ts` exposes `writeText()`, the repo's shared
file-write helper. It writes to a staging path and then `rename()`s it onto
the target, which unconditionally replaces whatever is at the target path.
`musubix3 requirements scaffold <slug>` / `musubix3 design scaffold <slug>`
(GitHub Issue #18) must never overwrite an existing `requirements.md` or
`design.md`, including when a second process or a fast-repeated invocation
creates the same target between this command's existence check and its
write. A rubber-duck review of the design for this feature identified that
a "check exists, then call `writeText()`" implementation has exactly this
race: the existence check can pass, another writer can create the file, and
`writeText()`'s `rename()` step will then silently clobber it, defeating
the requirement's whole purpose (no error, no preserved original bytes).

## Decision

- `scaffoldRequirements`/`scaffoldDesign` (`packages/analysis/src/scaffold-artifact.ts`)
  create their parent directory with `mkdir(..., { recursive: true })` and
  then write the target file directly with Node's `fs.writeFile(path,
  content, { flag: 'wx' })` — the POSIX `O_EXCL|O_CREAT` semantics, which
  atomically fail with `EEXIST` if the target already exists, instead of
  routing through the shared `writeText()` helper.
- On `EEXIST`, the call rejects with `Refusing to overwrite existing file:
  <relative-path>` and performs no further filesystem writes; the
  pre-existing file's bytes are left untouched because `wx` never opens an
  existing target for writing.
- `writeText()` itself is not changed: its rename-based "replace atomically,
  overwrite intentionally" contract is correct and still used by every
  existing caller that wants replace-on-write semantics; only the two new
  scaffold functions, which need create-only semantics, bypass it.

## Rejected alternatives

- **Check-then-write with `writeText()`.** Rejected: this is exactly the
  race identified above — an existence check has no atomicity guarantee
  with a subsequent `rename()`-based write, so a concurrent creator can be
  silently overwritten.
- **Add an `overwrite: boolean` option to `writeText()`.** Rejected: making
  `writeText()`'s rename-based implementation conditionally exclusive would
  require re-deriving the same `O_EXCL` logic inside a helper whose every
  other caller relies on unconditional replace; it also risks a subtle
  regression for those callers if the option defaulted incorrectly. A
  narrowly scoped `wx` write in the two new functions carries no such risk.
- **File-lock based mutual exclusion.** Rejected: adds a lock file, a lock
  protocol, and stale-lock cleanup for a case the OS already handles
  atomically via `O_EXCL`; strictly more moving parts for no additional
  correctness.

## Consequences

- `requirements scaffold`/`design scaffold` cannot lose data to a
  concurrent or repeated invocation: at most one writer ever succeeds for a
  given target path, and every loser sees an explicit
  `Refusing to overwrite existing file: <path>` error rather than silent
  data loss.
- Two write paths now exist in `packages/analysis`: `writeText()` (replace
  atomically) and the `wx`-flag write in `scaffold-artifact.ts` (create
  atomically, never replace). Future code choosing between them must pick
  based on whether overwrite is intended.
