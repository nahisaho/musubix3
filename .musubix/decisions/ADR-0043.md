# ADR-0043: Diff-only approval prepare output compares against the last recorded approval and reuses the existing drift helper

## Context
Issue #68: `approval prepare <stage> --json` hashes every tracked+untracked artifact (300+ files in this repository) into `artifacts`/`artifactSha256`. That full manifest is required for cryptographic integrity (ADR's existing approval model binds `approval record` to the exact manifest hash a human reviewed), but presenting all 300+ paths to a human reviewer for every single-file change is impractical. Every one of CHANGE-0043 through CHANGE-0050 required a manual `git diff`/ad-hoc file comparison outside the tool to extract "only the files that actually changed" before asking a human to approve. A reviewer-facing, additive diff view is needed without weakening or replacing the existing full-manifest hash.

Two design questions needed a decision:
1. What is "changed" measured against — the previous `approval prepare` invocation (ephemeral), the last `approval record`ed evidence (persisted), or a live `git diff` against HEAD?
2. How should the new code compute added/modified/removed paths — a new comparison algorithm, or reuse of existing code?

## Decision
`changedFiles` is computed against the last **recorded** approval evidence for that exact stage and domain (`loadApproval(root, stage, domain)`), not against a live `git diff`/`git status` and not against a merely-previously-displayed-but-never-recorded `approval prepare` output. This mirrors the existing `artifactSha256`/`stale` staleness model exactly: `validateApprovalStage` already reports `stale` by comparing the current manifest hash to the last *recorded* evidence, never to an arbitrary prior `prepare` call or to git state directly. Keeping `--diff-only`'s baseline identical to that existing, already-understood model avoids introducing a second, conceptually different notion of "changed" into the same command, and avoids a dependency on `git` being available/exact-root for stages (`requirements`/`design`) whose manifest computation does not otherwise require git at all.

The comparison itself reuses the existing, already-tested `releaseDrift(approved, current)` helper (originally written for `validateReleaseApprovalForTag`'s tag-vs-approval drift report), generalized by a rename to `artifactDrift` since it is now a shared, stage-agnostic primitive rather than release-specific one, instead of writing a second, parallel added/modified/deleted diff implementation. `artifactDrift` already returns exactly the set of paths whose SHA-256 differs between two `Record<string, string>` artifact maps — added, modified, and deleted — pre-sorted by the same `codePointOrder` the rest of `approval.ts` uses for deterministic path ordering. The new `diffOnlyChangedFiles` function is a thin wrapper: `null` baseline → every current path with `diffOnlyBaseline: 'none'`; a present baseline → `artifactDrift(previous.artifacts, manifest.artifacts).map(d => d.path)` with `diffOnlyBaseline: 'approved'`.

Corrupted/invalid prior approval evidence (a `.musubix/evidence/approvals/<stage>.json` that exists but fails `loadApproval`'s schema validation) is deliberately *not* given a new silent-fallback code path to "no prior approval" — `loadApproval` already throws `Invalid <stage> approval evidence.` for this case, and two existing call sites already disagree on how to handle that throw: `validateApprovalStage` catches it and reports a soft, non-aborting `{ status: 'stale', ... }` result (appropriate there, since it aggregates every stage's status in one non-throwing report), while `validateReleaseApprovalForTag` re-throws it as a hard-failing `ReleaseApprovalSchemaError` that aborts the command. `--diff-only` deliberately follows the second (stricter, release-stage-style) precedent: it calls the same unmodified `loadApproval` with no surrounding try/catch, so the same error propagates and aborts the command, because REQ-APPROVAL-PREPARE-DIFF-ONLY-007 requires an aborting failure here, not a soft status — masking a tampered evidence file as "first-ever approval" would be a genuine integrity regression for a feature whose entire purpose is helping a human reviewer trust what they are shown.

`artifactSha256` and `artifacts` are always computed by the exact same `approvalManifest(...)` call used without `--diff-only`; `--diff-only` only adds fields to the output, never removes, filters, or recomputes any existing one.

## Rejected alternatives
- **Live `git diff`/`git status` against HEAD as the comparison baseline**: rejected because it reintroduces exactly the dependency the existing `requirements`/`design` stage manifest computation deliberately avoids (`exactGitRoot`/git availability is only required for the `release` stage today), and because "changed since the git tree's HEAD" is a different, less relevant question for a human approver than "changed since the content I last actually approved" — an uncommitted-but-already-approved draft edit would show as "changed" forever under a git-diff baseline even after being re-approved, which is misleading.
- **Comparing against the previous `approval prepare` invocation's output** (requiring the CLI to persist an ephemeral "last shown" snapshot): rejected as unnecessary new persisted state duplicating the function evidence already serves, and because it would silently reset on every `prepare` call even without an intervening `record`, hiding genuine unreviewed drift from the reviewer across multiple preparation attempts.
- **Writing a new, dedicated added/modified/deleted diff algorithm for this feature**: rejected in favor of reusing `releaseDrift`, which already implements, tests, and sorts exactly this computation; a second parallel implementation would risk subtly different edge-case behavior (e.g. sort order, duplicate handling) between the two code paths for no benefit.
- **Treating corrupted prior evidence as "no prior approval" (`diffOnlyBaseline: 'none'`)**: rejected because it would silently convert a detected integrity problem into an falsely-reassuring "first approval" state, undermining the trust a human reviewer places in the tool's own output.

## Consequences
`--diff-only` is purely additive: existing manifest hashes, evidence files, and `approval record`'s required input are completely unaffected. A reviewer can ask for a short, actionable file list without losing any of the full manifest's integrity guarantee, and the tool's two existing concepts (`artifactSha256`'s full-manifest identity and `stale` detection) are both reused rather than duplicated by the new comparison. The one tradeoff: if a project operator wants to see drift against raw git history rather than against the last human-recorded approval, this feature does not serve that use case (existing `git diff` remains the right tool for that question, as it already was).
