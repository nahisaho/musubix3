# ADR-0032: Use targeted transformations with a rollback-capable release-version transaction

## Context

musubix3 repeats its release version across JSON manifests, an npm lockfile,
TypeScript source/tests, and localized README banners. `npm version` updates
only npm manifests and may rewrite lockfile metadata according to the locally
installed npm version. Repository-wide string replacement can alter historical
release notes and evidence. Validating each release script independently has
already allowed their coverage to diverge.

The filesystem does not offer one atomic rename covering multiple files.
Fail-atomic behavior therefore requires validating and staging the whole plan
before mutation, retaining recoverable originals during commit, and rolling
back a partially committed plan on failure.

## Decision

Create a Node.js-standard-library release-version core module shared by the
release-version command, package check, and release preparation.

The synchronous core uses an explicit surface registry:

- JSON-pointer locations for root/workspace package manifests, package-lock,
  plugin manifest, and marketplace metadata.
- Target-independent, cardinality-checked token locators for the Commander
  version call, two CLI version assertions, and localized README banners.
- Workspace paths expanded only from repository-relative patterns ending in
  `/*`, normalized to POSIX form for lockfile lookup and diagnostics.

Inspection validates the explicit expected version and returns all structural
and version diagnostics before any update.
Transformation changes only the located values while preserving raw formatting
contracts. Commit writes unique same-directory staging files, fsyncs them,
moves originals to unique backups, installs replacements in deterministic path
order, and removes backups only after every replacement succeeds. Immediately
before staging, commit re-reads all targets and rejects any byte-level change
from the inspected snapshot. A failure restores committed originals from
backups and removes staged state. Filesystem operations are injectable solely
for deterministic failure tests, and commit returns the standard report with
the failing normalized path rather than throwing an unstructured error.

Release preparation derives the explicit expected version from an exact
`v<version>` tag, invokes the shared validator before touching release output,
and retains the separate tag-to-`GITHUB_SHA` verification. Package checking
uses the root manifest version as its explicit expected version. Each script
derives the repository root from `import.meta.url`; package checking removes
its duplicate version assertions. Existing success stdout remains unchanged,
while each CLI branch writes shared ordered validation diagnostics to stderr on
a typed validation error. Library exports propagate the typed error instead of
terminating the process. Package checking runs `npm pack` from the same derived
root used for validation.

## Rejected alternatives

- **Use `npm version` as the synchronizer.** Rejected because it does not cover
  plugin, CLI, test, or README surfaces and can cause npm-version-dependent
  lockfile churn.
- **Replace every occurrence of the old version across the repository.**
  Rejected because it can rewrite CHANGELOG history, evidence, examples, and
  dependency ranges outside the declared release surfaces.
- **Keep separate validators in each release script.** Rejected because their
  surface coverage and diagnostics can drift.
- **Write targets directly after validation.** Rejected because a later write
  failure leaves a partially updated repository.
- **Depend on an external transaction or glob package.** Rejected because the
  command must run offline without `node_modules`.

## Consequences

- Release version behavior has one explicit registry and validator.
- Update mode can restore the pre-invocation tree after deterministic injected
  stage or rename failures, but a process or machine crash during the short
  commit window can leave backup/staging files requiring operator inspection;
  this limitation must not be represented as crash-atomic behavior.
- Adding a new release version surface or workspace pattern form requires an
  explicit registry/requirement change.
- The implementation is more involved than direct writes but avoids
  npm-version-specific serialization and broad replacement risk.
- `dist/` is intentionally not a synchronized source surface. A local operator
  can still package stale generated CLI output if they ignore the documented
  mandatory `npm run build` step; CI release validation performs that build
  before packing.
