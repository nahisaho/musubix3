# ADR-0026: Bounded, audited severity-downgrade waiver for workflow reconciliation debt

## Status
Accepted

## Context
`workflow-verify` reconciles self-reported `workflow-record <skill> <phase>
--status completed` declarations against Copilot Skill invocations parsed
from session transcript logs. A declaration recorded in a session whose
transcript log later becomes unavailable (rotated out, from a session
never passed to `workflow-verify`, or predating this reconciliation
feature entirely), or recorded slightly out of step with the exact
invocation the tool can bind 1:1, causes `validateWorkflow` to raise one
of `WORKFLOW_SKILL_NOT_INVOKED`, `WORKFLOW_INVOCATION_ORDER`,
`WORKFLOW_INVOCATION_INCOMPLETE`, `WORKFLOW_INVOCATION_FAILED`, the
declaration-scoped flavor of `WORKFLOW_INVOCATION_REUSED`, and the always-
paired `WORKFLOW_BINDING_MISSING` — in every case where reconciliation
evidence is missing or imperfectly ordered for a declaration, which may
reflect an already-real Skill invocation whose evidence trail is merely
incomplete, or, less commonly, a declaration for which no invocation
actually occurred. `validateWorkflow` cannot itself distinguish the two.
`gate.ts` currently computes the `workflow` check's `status` from
`workflow.verified` (`true` only when `diagnostics` is empty regardless of
severity), and `approval-record.ts` hard-blocks `release` approval when any
required check does not report `pass`. A single unresolved reconciliation
diagnostic in `workflow` therefore permanently blocks release approval even
once every other check is clean (GitHub Issue #1, recurrence comment, item
3/4) — the same class of problem ADR-0025 (`change-evidence-waiver`)
already solved for `change-history`/`change-completeness`, but ADR-0025
deliberately left `workflow`'s zero-tolerance status computation untouched
pending its own requirements review (see this repository's
`workflow-evidence-waiver` requirements intro).

## Decision
Extend the audited waiver pattern established by ADR-0025 to the
`workflow` check, rather than inventing a new mechanism or relaxing
`approval-record.ts`'s hard block directly. Add an explicit, human-approved
`workflow waiver record <CODE> --skill <skill> --phase <phase>
--recorded-at <timestamp> [--index <n>] --approver <name> --reason <text>
--confirm` command that downgrades one specific, currently-present
declaration-scoped diagnostic instance (identified by `skill`/`phase`/the
declaration's own `recordedAt`, disambiguated by `index` only on an exact
timestamp collision) from `severity: "error"` to `severity: "warning"`, as
an appended, self-chained, audited record in a new
`.musubix/evidence/workflow-waivers.json` file. The diagnostic and its
paired `WORKFLOW_BINDING_MISSING` are never removed from the report — only
their severity changes, and only for the exact scope recorded.
`validateWorkflow`'s `workflow` check `status` is redefined from
`diagnostics.length === 0` to "no `error`-severity diagnostic remains" —
the same effective semantics `tdd`/`change-history`/`change-completeness`
already use — so a fully waived, non-stale scope reports `pass` without
any change to `approval-record.ts`'s existing `check.status !== 'pass'`
condition. A waiver is bound to a versioned snapshot hash covering the
declaration event's own fields and `workflowEvidenceHead(workflow)` (an
existing exported digest that covers `invocations` when the `verification`
object carries `mode`/`transcriptSha256`/`sessionId`, and otherwise, for
the narrower legacy shape, only `eventsSha256`/`sourceSha256`); if
reconciliation evidence changes materially after recording, the
waiver becomes stale and the diagnostic reverts to `error`, plus a
separate `WORKFLOW_WAIVER_STALE` diagnostic is raised into the same
non-blocking `waiverDiagnostics` array `CHANGE_WAIVER_STALE` already uses,
never into `workflow.diagnostics` itself.

## Rejected alternatives
- **Relax `approval-record.ts`'s hard block directly** (e.g., allow
  release approval despite one or more required checks reporting `fail`).
  This was considered and explicitly rejected during requirements analysis
  for this feature: it would weaken policy for every future
  `workflow`-check failure, including genuinely fresh reconciliation gaps,
  not just the specific, human-reviewed instances this ADR targets — the
  same reasoning ADR-0025 already applied to `change-history`.
- **Loosen `validateWorkflow`'s binding/order predicates themselves** (for
  example, treat a missing transcript log as automatically satisfied).
  This would silently accept every future reconciliation gap of that
  shape, not just human-reviewed ones, and would not require a per-instance
  approver/reason.
- **Delete or hand-edit `.musubix/evidence/workflow.json`.** Declaration
  events are append-only and (once verified) hash-bound to
  `workflowEvidenceHead`; editing or deleting entries would fabricate
  history rather than prune it, exactly as ADR-0025 already rejected for
  `changes.json`/`tdd.json`.
- **Fully suppress (remove) the waived diagnostic rather than downgrade to
  `warning`.** This would erase the audit trail from `gate --json`'s
  report; downgrading preserves visibility (`workflowWaivers` array, and
  the diagnostic itself with attached waiver metadata) while still
  unblocking the check, matching `change-evidence-waiver`'s existing
  choice.
- **Reuse `change-waivers.json`/`change-waiver.ts` directly instead of a
  parallel `workflow-waivers.json`/`workflow-waiver.ts`.** The scope keys
  (`skill`/`phase`/`declarationRecordedAt`/`index` vs.
  `changeId`/`code`/`requirementId`/`detail`), snapshot payload
  (`workflowEvidenceHead` vs. change/TDD evidence fingerprints), and
  linkage source (`workflow.json`'s declaration events vs.
  `changes.json`/`tdd.json`) are structurally different; a single,
  differently-shaped file and module would need per-domain branching
  throughout, defeating the point of the existing module's specificity.
  A parallel module reusing only the domain-independent primitives
  (`canonicalJson`, the append-only hash-chain shape, the
  authoritative-record-by-`sequence` supersession rule) keeps each domain's
  validator self-contained, mirroring how `change-waiver.ts` itself is
  self-contained relative to `tdd.ts`.

## Consequences
- Release approval becomes reachable again once every genuinely
  unaddressed `workflow` reconciliation diagnostic (waived or otherwise
  resolved) is cleared, without fabricating evidence, deleting evidence,
  or weakening `workflow-verify`/`approval-record.ts` for any non-waived
  scope.
- Every waiver is a permanent, auditable record naming its approver,
  reason, and the exact `skill`/`phase`/`declarationRecordedAt`/`index`
  scope it covers; `gate --json`/`status --json` surface active
  (authoritative, non-stale) waivers via a new `workflowWaivers` array, and
  malformed/stale waiver evidence remains permanently visible in
  `waiverDiagnostics`, mirroring `change-evidence-waiver` exactly.
- The waivable allow-list is intentionally narrow (five declaration-scoped
  codes only); `WORKFLOW_INVOCATION_UNVERIFIED` (no reconciliation attempt
  at all) and the tool-call-scoped flavor of `WORKFLOW_INVOCATION_REUSED`
  are deliberately excluded, so a repository can never reach `pass` by
  skipping reconciliation entirely or by waiving a structurally different
  kind of evidence problem. Extending the allow-list to a different
  diagnostic shape requires a new, separately reviewed change, not a
  configuration toggle — the same governance ADR-0025 established for
  `change-evidence-waiver`.
