# ADR-0010: Reconcile cross-session Workflow declarations by concatenating multiple compatible-mode transcript files, never by discarding or trusting unverifiable declarations

## Context

`workflow.json` accumulates self-reported Skill invocation declarations
across the entire lifetime of the repository, spanning arbitrarily many
distinct Copilot CLI sessions (each with its own
`~/.copilot/session-state/<uuid>/events.jsonl` transcript file). Empirical
investigation (Issue #1 item 3) confirmed a genuine declaration recorded at
`2026-09-09T08:13:50Z` has no matching Skill invocation event in the current
session's transcript (which itself only started at `08:17:52Z`) — its real
invocation evidence exists in a *different*, earlier session's transcript
file. `workflow-verify`/`validateWorkflow` currently accept exactly one
transcript file, so any declaration whose invocation occurred in a prior
session can never be reconciled, permanently blocking the `workflow` gate
check (`WORKFLOW_INVOCATION_UNVERIFIED`) for any repository with more than
one working session — the normal case.

## Decision

Extend `verifyWorkflowLogFile` and the `workflow-verify` CLI command to
accept one or more transcript file paths in **compatible mode only**. All
supplied files are read in the given order and treated as a single
concatenated logical event stream, reusing the existing single-pass byte
hashing, per-line size limits, event-count limit, and `toolCallId` binding
logic in `validateWorkflow` unchanged (binding already keys off each
invocation's `invokedAt`/`completedAt` timestamps, not file order or
position). `--strict`/`--session-id` continue to require exactly one file,
since strict mode's terminal-event contract
(`REQ-WORKFLOW-SHUTDOWN-001`) is inherently a single-session completeness
proof and does not generalize to a concatenation of unrelated sessions.

## Rejected alternatives

- **Automatically discover and concatenate every `events.jsonl` under
  `~/.copilot/session-state/` without an explicit file list.** Rejected:
  that directory layout is an undocumented internal detail of the Copilot
  CLI, not a contract musubix3 can safely depend on; a version change could
  silently break or mis-scope discovery. Requiring explicit file arguments
  keeps the trust boundary at what the operator deliberately supplies.
- **Drop or expire old declarations that predate the current session so
  only "recent" declarations need verification.** Rejected: this would
  silently discard real, previously-recorded Skill invocation evidence
  without ever proving it was invoked, which is exactly the "trust via
  omission" shortcut ADR-0009 warned against for the analogous TDD
  migration case. A declaration with no matching invocation must keep
  failing until it is actually reconciled or explicitly, auditably retired.
- **Treat any declaration older than a configurable age as pre-verified
  ("grandfather" past evidence).** Rejected: it would let a genuinely
  unverifiable (or fabricated) declaration pass merely by being old,
  defeating the purpose of `WORKFLOW_SKILL_NOT_INVOKED`/
  `WORKFLOW_INVOCATION_UNVERIFIED` entirely.
- **Extend strict mode itself to accept multiple sessions/terminal
  events.** Rejected: strict mode's guarantee is "this one session ran to a
  single, unambiguous, routine completion"; multiple terminal events across
  concatenated sessions cannot satisfy the "exactly one terminal event" test
  without redefining what strict completeness means, which would weaken the
  guarantee `REQ-WORKFLOW-SHUTDOWN-001` was written to provide.

## Consequences

- Operators (or the `sdd-change` skill flow) must supply every transcript
  file whose session contains an invocation for an outstanding declaration;
  `workflow-verify a.jsonl b.jsonl c.jsonl` is now a supported, documented
  operation rather than a workaround.
- `WORKFLOW_SKILL_NOT_INVOKED` remains a correct, non-bypassable diagnostic:
  it only clears once the actual matching invocation evidence is supplied,
  never by aging out or deleting the declaration.
- README's `workflow-verify <copilot.jsonl>` documentation must be updated
  to state the transcript file location convention
  (`~/.copilot/session-state/<uuid>/events.jsonl`) and note it is dependent
  on the installed Copilot CLI version, so operators know where to find the
  files they must supply.
