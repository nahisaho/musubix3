# ADR-0039: Scope per-feature trace.json to the feature's reachable subgraph, backed by one canonical full-graph file

## Context

`trace build` previously wrote the complete, unscoped `TraceGraph` (every node
and edge in the whole project) into every single feature's
`.musubix/features/<feature>/trace.json`. As the project grew past a hundred
features, this made each feature's `trace.json` diff on every unrelated
change elsewhere in the repository — large, noisy, and unreviewable — and
made per-feature trace artifacts byte-identical copies of the same growing
file, with no actual feature-scoping value. `loadTrace`'s cache-less fallback
also picked whichever feature's `trace.json` happened to sort first via
`find()`, an arbitrary and non-deterministic source for the full graph when
reconstructing the project graph (e.g. for `trace check --strict` or
`trace impact` without `.musubix/cache/trace.json` present).

## Decision

Introduce a single tracked canonical full-graph file at `.musubix/trace.json`
(`canonicalTracePath`), updated on every persistence attempt but, like the
per-feature files below, written only when its content actually differs
(`writeTraceIfChanged`, ignoring only `generatedAt`) — never left stale, but
also never rewritten byte-for-byte on an unrelated rebuild. Rewrite each feature's own
`.musubix/features/<feature>/trace.json` as a deterministic projection
(`featureTraceProjection`) containing only nodes owned by that feature
directory plus any node reachable from them by following edges (so shared
dependencies, e.g. a common code symbol, are still included), with a
byte-stable, change-detecting write (`writeTraceIfChanged`, ignoring only
`generatedAt`) so an unrelated rebuild leaves the feature file untouched.
`loadTrace`'s cache-less fallback reads `.musubix/trace.json` instead of an
arbitrary first feature file. Approval manifests for the `requirements` and
`design` stages continue selecting only `requirements.md`/`design.md`/ADRs
and are not changed to read any `trace.json`, keeping approval hashes
unaffected by any trace rebuild — an explicit regression invariant covered by
a dedicated test rather than new production code.

## Rejected alternatives

- Keep writing the full graph into every feature's `trace.json`: rejected
  because it does not scale with feature count and produces unreviewable
  diffs unrelated to the feature being changed.
- Scope each feature's `trace.json` strictly to nodes under its own directory
  with no reachability expansion: rejected because it would silently drop
  genuinely shared or cross-feature dependency context that existing callers
  rely on when reading a single feature's trace file.
- Derive the canonical full graph on demand by merging every feature's
  scoped file instead of keeping one tracked `.musubix/trace.json`: rejected
  because it reintroduces a non-deterministic, sort-order-dependent merge
  and extra recomputation cost on every load.
- Route the requirements/design approval manifest through `.musubix/trace.json`
  so approvals could detect trace drift: rejected because approval hashes
  must depend only on the reviewed specification text, not derived build
  artifacts, to remain stable across trace rebuilds.

## Consequences

Feature `trace.json` files stay small, scoped, and stable across unrelated
rebuilds; `.musubix/trace.json` is the single source of truth for the full
graph when no cache is present. Any future caller needing the complete graph
without the cache must read `.musubix/trace.json`, not an arbitrary feature
file.
