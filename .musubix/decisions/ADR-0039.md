# ADR-0039: Share a Windows-scoped transaction directory-sync policy

## Context

Quality refresh and evidence merge currently suppress `EISDIR`, `EPERM`,
`EACCES`, and `EINVAL` from a combined directory open/sync error boundary on
every operating system. Evidence writer-lock instead permits only Windows
`EPERM`, `EINVAL`, and `ENOTSUP` from synchronizing an already-open directory
handle, and keeps recovery strict. The broader transaction behavior can report
success after an actionable Linux or macOS durability failure and can hide an
incorrect directory open.

The Windows Core failure referenced by Issue #43 observed `EPERM` from `fsync`
after directory open succeeded. Node's libuv Windows open path applies
`FILE_FLAG_BACKUP_SEMANTICS`, permitting read-only directory handles, but the
directory flush capability and error mapping remain filesystem/runtime
dependent.

## Decision

Create `packages/analysis/src/filesystem-durability.ts` as the single owner of
the directory-sync policy, Windows error classifier, minimal asynchronous
handle interface, and asynchronous open/sync/close lifecycle. Treat only
Windows `EPERM`, `EINVAL`, and `ENOTSUP` as unsupported. Require every caller to
choose `allow-unsupported` or `strict`; suppression is legal only for
`allow-unsupported` around synchronization of an already-open handle.

Use `allow-unsupported` for evidence writer-lock publication, acquisition
rollback, and release and for every Quality refresh and evidence merge
transaction directory boundary. Keep writer-lock recovery strict. Keep file
sync, directory open and close, all non-Windows errors, and all other Windows
errors fail-closed. In particular, do not add `EISDIR` merely because a future
runtime could map a directory flush failure to it; a new observed errno requires
a separately reviewed policy change.

Preserve helper-level filesystem errors. At transaction boundaries, retain the
existing recovery-required diagnostics after journal publication and use
unsafe-recovery diagnostics during roll-forward recovery, with journal and
owned-file inventory. Do not automatically retry or claim rollback after a
recovery durability failure because target or cleanup mutation may already
have occurred.

## Rejected alternatives

- **Keep the existing cross-platform allowlist.** This silently weakens
  durability on platforms where the failure is actionable and preserves a
  combined open/sync boundary.
- **Suppress every Windows directory error.** Permission, handle lifecycle,
  path, and programming errors are not evidence of an unsupported durability
  capability.
- **Add Windows `EISDIR` preemptively.** The observed supported failure is
  `EPERM`, the existing writer-lock policy excludes `EISDIR`, and accepting an
  unobserved mapping would hide a runtime or open-mode regression.
- **Make every transaction strict on Windows.** This would make normal Quality
  refresh, evidence merge, writer-lock publication, and cleanup unusable on the
  Windows filesystem behavior already observed by Core CI.
- **Ignore directory synchronization entirely.** File synchronization alone
  does not establish directory-entry durability after link, rename, or unlink.
- **Automatically retry recovery synchronization.** Repeated failure can loop
  indefinitely on unsupported storage, and recovery may already have rewritten
  targets or removed transaction files.

## Consequences

Linux and macOS transactions fail instead of reporting durable success for any
directory synchronization error. Windows retains the narrow compatibility
exception already used by writer-lock, with an explicit residual risk that
directory-entry crash durability cannot be guaranteed when synchronization is
unsupported.

The package gains one shared exported policy surface, retains
`EvidenceDirectorySyncPolicy` as a compatibility type alias, and retains the
existing Quality refresh and evidence merge helper call shapes with an additive
platform callback. Recovery diagnostics become more explicit and may require
operator verification when durability fails after rollback or roll-forward
mutation. The provenance of the old `EISDIR` allowance is unknown; a Windows
Core `EISDIR` result is therefore investigated before being classified as
either a regression or an unsupported capability. A future
Node/libuv or filesystem error outside the three-code allowlist intentionally
fails Core or production transactions until reviewed.
