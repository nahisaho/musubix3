# ADR-0040: Extend `tdd migrate` with an identifier-only relink mode on the existing append-only migrate phase

## Context

`ADR-0009` established `tdd migrate <test-id>` as the sanctioned way to
repair stale TDD evidence when only the fingerprinting algorithm changed.
GitHub Issue #57 proposal (1) adds a second legitimate stale-evidence case:
the covered test is renamed from one authoritative ID to another without any
behavioral change in the declaration body or in the non-test source state that
the cycle covered. Requiring a fresh Red/Green cycle for that pure rename would
misrepresent history; silently rewriting existing evidence in place would break
the append-only audit model.

## Decision

Keep `tdd migrate` as the single migration command, but extend it with a
two-ID mode, `tdd migrate <old-id> <new-id>`, that:
1. Reuses the same effective-cycle selection rules as the existing one-ID mode
   (including archive rejection and void rerouting).
2. Proves rename-only equivalence by rewriting only the authoritative `@id`
   annotation and the adapter-matched identity string from `<new-id>` back to
   `<old-id>` before comparing the declaration fingerprint against the covered
   cycle's current effective fingerprint, while also requiring the covered
   cycle's non-test `sourceFingerprint` to remain unchanged.
3. Reuses the existing append-only `migrate` phase, but extends its payload
   and migrate-order scoping so identifier relinks are auditable (`mode`,
   `oldTestId`, `newTestId`) without inventing a second migration-only phase;
   when a relink follows an earlier one-ID fingerprint migration on the same
   cycle, the persisted representation must preserve both migrate records in an
   additive ordered stream rather than overwriting the original one-ID payload.

## Rejected alternatives

- **Require a fresh `tdd red` / `tdd green` cycle for every rename.**
  Rejected: a pure ID rename does not prove new behavior, so fabricating a new
  failing Red run would misstate history and create unnecessary release debt.
- **Introduce a separate `tdd relink` command and a second chain phase.**
  Rejected: the governance boundary is still "approved migration of existing
  covered evidence," already modeled by `migrate`; splitting the command and
  phase would duplicate archive/void targeting rules, validation, and user
  mental model for little gain.
- **Mutate recorded Red/Green evidence to swap IDs in place.**
  Rejected: this would violate the same append-only hash-chain guarantees that
  motivated `ADR-0009`, and would make later audits unable to distinguish the
  original covered ID from the renamed successor.

## Consequences

- Operators get one documented migrate surface with two explicit forms: one-ID
  fingerprint migration and two-ID identifier relinking.
- Identifier-only relinks remain auditable through the existing migrate order
  and chain machinery, with enough persisted identity to reject later
  conflicting relinks of the same covered cycle while preserving any prior
  one-ID fingerprint migration on that cycle as part of the same append-only
  migrate history.
- Rename-only migration inherits existing archive/void targeting semantics, so
  the new mode does not create a second, inconsistent notion of the "effective"
  cycle.
