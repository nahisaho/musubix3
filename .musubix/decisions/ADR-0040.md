# ADR-0040: Retain offline workflow provenance and staged operational evidence

## Context

Moving the repository-owned workflow execution runtime from Node.js 22 to
Node.js 24 changes protected release and publication files. A digest of only
the new files cannot prove what was reviewed before the migration, while a
comparison against Git history would fail in shallow checkouts or after the
source branch is removed.

The first merged CI run and the next natural release and publication runs do
not exist while the change is staged. Treating those unavailable results as
successful would weaken the evidence contract, but triggering a release or npm
publication solely to manufacture evidence would create unnecessary
operational risk.

## Decision

Retain the exact pre-change release and npm-publish workflow source bytes,
including the final newline, in the reviewed publishing fixture. Bind each
source to checker-owned prior commit, Git blob SHA-1, and SHA-256 literals.
Bind the fixture's current digest only to the current workflow bytes. Verify
offline that the prior and current sources have equal line counts and differ
only at the reviewed three release and one npm-publish
`node-version: 22` to `node-version: 24` lines.

Keep the CI baseline comparison structural. Positively require the migrated
core job name and Node.js 24 setup-node value, then normalize only those two
reviewed scalar transitions before comparing the complete parsed documents.
All action-pin and previously reviewed input exceptions remain additive, and
every other difference remains gate-blocking.

Represent operational evidence as explicit staged or completed values in
CHANGE-0047. Require the first merged CI URL and three successful
core-portability conclusions before the change can be completed. Permit the
release and npm-publish entries to remain explicitly pending until those
workflows execute naturally; when recorded, bind them to a run URL and the
absence of the Node.js 20 warning. Validate the six exact bilingual runtime
statements and the evidence grammar offline.

## Rejected alternatives

- **Read prior workflow sources from Git during validation.** Shallow clones and
  deleted source refs make repository-history availability unsuitable for a
  deterministic gate.
- **Store only prior and current digests.** Digests prove identity but do not
  preserve human-auditable source or permit an offline exact-line comparison.
- **Allow any parsed Node.js version change.** Broad normalization could hide
  unrelated setup-node changes in protected jobs.
- **Mark unavailable operational evidence successful.** This would equate a
  planned check with observed workflow behavior.
- **Trigger release and publication workflows immediately.** Manufacturing
  evidence would expand operational scope and could publish artifacts without
  a natural release need.
- **Use prose-only documentation checks.** Whitespace-normalized anchors would
  not protect the six reviewed bilingual source statements.

## Consequences

The repository carries a larger fixture because it preserves exact historical
workflow bytes, but validation remains network-free and independent of Git ref
retention. Any source refresh requires an explicit reviewed provenance update,
and any unenumerated workflow line change fails closed.

CHANGE-0047 remains staged until a real merged CI run supplies the core
conclusions. Release and npm-publish evidence can remain deferred after that
point, so no publication is performed solely for this migration. The checker
proves source correspondence and evidence grammar; it does not claim that
offline equivalence alone proves runtime behavior.
