# ADR-0007: v0.1.9 diagnostic UX additions stay additive and non-authoritative

## Context

Running the full requirements→design→implementation→trace→gate workflow
end-to-end on a real multi-language example surfaced five UX gaps: `trace
impact` output does not state its own semantics, `approval`-stage errors do
not point at the one command that already answers "which stage failed and
why", `.musubix/config.json` can silently reference nonexistent paths,
`gate` has no way to report on a single feature in isolation, and there is no
starting point for a new project's native-command configuration in a
multi-language repository.

## Decision

Each of these gaps is closed with an additive, read-only, or purely-textual
change that cannot change the meaning of an existing passing or failing
check:

- `trace impact` gains a clarifying summary line in text mode only; its
  `--json` shape is unchanged.
- `requireApproval`'s thrown error gains a pointer to `approval validate`;
  no approval logic changes.
- `config lint` is a new, read-only diagnostic command; it never edits
  `.musubix/config.json`.
- `gate --feature <name>` is a reporting view over the same checks, scoped to
  one feature's artifacts; it must never report `ready: true` and never
  replaces the repository-wide gate.
- `config scaffold` only prints proposed command entries; it never writes
  `.musubix/config.json`.

## Consequences

- None of these additions can make an existing failing gate pass by
  themselves; they only add information or optional read-only tooling.
- `gate --feature` in particular must be reviewed carefully so it cannot be
  used to claim repository-wide readiness from a partial view.
