# ADR-0041: Exclude a fixed scratch-file naming convention from the release-manifest untracked candidate set

## Context

`ADR-0033` built the release-manifest candidate set from a union of tracked
Git entries (`git ls-files -z -s --cached`) and untracked, non-ignored Git
entries (`git ls-files -z --others --exclude-standard`), so a newly authored
but not-yet-committed release input is still part of the manifest. GitHub
Issue #66 reports the resulting downside: any ad hoc scratch/debug file an
operator writes into the worktree while inspecting the release hash (for
example redirecting a command's output to `approval-prepare-release.json` or
`relcheck-1.json` in the worktree root, as actually happened twice during
CHANGE-0047/Issue #55) is itself an untracked file and therefore becomes part
of the hashed manifest, changing the reported hash on every subsequent
inspection and causing unnecessary approval-hold/re-report cycles.

`.gitignore`-based exclusion (already relied upon by `--exclude-standard` for
cases like `.test-tools/`, per `ADR-0033`) only helps when the specific
repository's `.gitignore` already lists the exact path an operator happens to
pick; it does not protect a repository (or this very repository, as happened)
that has not yet added such an entry, and it is not something the
`releaseCandidateInventory` implementation itself can rely on existing in
every consuming repository.

## Decision

Add a second, independent, fixed exclusion layer applied only to the
untracked half of the release candidate set, as a final post-filter on the
output of `releaseCandidateInventory` (`packages/analysis/src/approval.ts`):

1. Exclude any untracked path at or beneath `.musubix/scratch/`.
2. Exclude any untracked path whose final path segment matches the fixed,
   case-sensitive regular expression `^[^/]+\.scratch\.[^/.]+$` (a
   `*.scratch.<single-segment-extension>` naming convention, for example
   `*.scratch.json`).
3. Apply both exclusions **only** to the returned `paths` list, and only to
   entries known to have originated from the untracked branch — never to
   `structuralPaths`, and never to a tracked (`git ls-files --cached`)
   entry. A committed file whose name happens to match either pattern is
   still included in the manifest exactly like any other tracked release
   input. Critically, the existing `releaseProjectPaths`/`excludedByStructure`
   structural computation (nested-workspace and language-generated-directory
   boundary derivation) still runs against the *complete*, unfiltered
   tracked-plus-untracked candidate set; only the final output list drops the
   scratch-matching untracked entries. This matters because that structural
   computation derives nested-workspace boundaries from marker paths
   (any path containing `/.musubix/`) found anywhere in the candidate set: if
   a scratch file were removed *before* that computation instead of after,
   its own presence or absence could flip whether an unrelated sibling path
   is treated as part of a nested workspace, silently changing the hash of
   files that have nothing to do with the scratch convention. Filtering only
   the final output avoids that side effect entirely.
4. Hardcode both patterns directly in `approval.ts` source, covered by
   automated tests, with no `.musubix/config.json`, environment variable, or
   CLI-flag override. Document `.musubix/scratch/` and the `*.scratch.<ext>`
   suffix in `README.md`/`README-ja.md` as the sanctioned convention for ad
   hoc operator inspection output during an approval/release session.

## Rejected alternatives

- **Warn when the untracked file count jumps versus a last-known baseline.**
  Rejected: a baseline-drift warning is inherently non-deterministic (depends
  on incidental session history, not on the file's actual relevance to the
  release), does not by itself prevent the hash from still changing, and adds
  a new persisted "last known count" state that itself needs governance.
- **Make the exclusion patterns configurable (e.g. via `.musubix/config.json`
  `approval.release.scratchPatterns`).** Rejected: a configurable exclusion
  list could be quietly widened by an operator to hide a real, relevant
  untracked change from the release manifest hash, which would weaken the
  cryptographic completeness guarantee the release approval mechanism exists
  to provide. A fixed, source-level, test-covered convention requires the
  same `requirements`/`design`/TDD/quality gate as any other change to the
  release manifest to be widened.
- **Rely solely on `.gitignore` plus documentation telling operators to add
  entries themselves.** Rejected: this is exactly the gap that caused Issue
  #66 — the operator (and this repository's own `.gitignore`) had not added
  such entries at the time of the incident, and relying on every consuming
  repository remembering to add them is fragile. A library-level, hardcoded
  convention protects every repository that uses `approval prepare release`
  regardless of its own `.gitignore` content.
- **Exclude untracked files broadly (e.g. all untracked files outside
  `src/`/`tests/`).** Rejected: this would be far more likely to silently
  drop a genuinely new, not-yet-committed release input (the exact
  overreach risk flagged as REQ-RELEASE-APPROVAL-ORDERING-005's own
  "ordinary untracked file" acceptance clause), defeating the purpose of
  including untracked files in the first place.
- **Remove scratch-matching untracked entries before the
  `releaseProjectPaths`/`excludedByStructure` structural computation (that
  is, before nested-workspace/generated-directory boundary derivation) rather
  than after.** Rejected during design review: that structural computation
  derives nested-workspace boundaries from marker paths (any candidate path
  containing `/.musubix/`) found anywhere in the complete candidate set. If a
  scratch file under a nested workspace's own `.musubix/scratch/` were removed
  before that scan, its own presence or absence could flip whether an
  unrelated sibling path in that nested workspace is treated as structurally
  excluded, silently changing the hash of files that have nothing to do with
  the scratch convention — a direct violation of this ADR's own goal that
  scratch-file churn never perturbs any other path's inclusion. Filtering
  only the final `paths` output (gated on untracked origin) instead preserves
  the complete-information structural computation while still excluding
  scratch entries from what gets hashed.

## Consequences

- Operators get one documented, narrow, auditable convention
  (`.musubix/scratch/**` or `*.scratch.<ext>`) for ad hoc inspection output
  that is guaranteed never to perturb the release manifest hash, eliminating
  the exact re-report cycle Issue #66 describes, for any file an operator
  writes going forward under that convention.
- The fix does not retroactively protect arbitrarily-named scratch files from
  a past incident (such as the literal `approval-prepare-release.json` /
  `relcheck-*.json` names used during CHANGE-0047); operators must adopt the
  documented convention to benefit, which is recorded as an accepted residual
  risk in `CHANGE-0048.md`.
- The release manifest's cryptographic completeness guarantee is unchanged
  for tracked files and for untracked files that do not match the fixed
  convention; only the exact two fixed patterns are affected, and widening
  them requires a reviewed source change, not a configuration edit.
