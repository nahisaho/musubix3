# ADR-0019: Scope `upgrade` to bundled skills only, separate from `init --force`

## Context

The only existing mechanism to refresh bundled, package-provided files in an
already-installed project is `musubix3 init --force`. `install()`
(`packages/cli/src/install.ts`) computes one flat `planned` map covering
`.github/skills/sdd-*/*`, `.musubix/config.json`, `.musubix/policy-baseline.json`,
`.musubix/constitution.md`, the starter feature's `requirements.md`/`design.md`,
and `.musubix/decisions/ADR-0001.md`; `--force` replaces every entry in that
map whose content differs from the bundled version, with no way to select a
subset. `.musubix/config.json`, `.musubix/policy-baseline.json`,
`.musubix/constitution.md`, and feature `requirements.md`/`design.md` are
explicitly expected to be customized by users after the initial install (the
README instructs "replace its example, implement and test it, and configure
real check commands"). A user who wants a newer musubix3 version's updated
Skill instructions therefore cannot safely run `init --force` without first
diffing and manually restoring their customized config/constitution/feature
files — there is no documented, safe upgrade path.

## Decision

- Add a new, narrowly-scoped `upgradeSkills(root, packageRoot, options)`
  helper in `packages/cli/src/install.ts` that enumerates only
  `.github/skills/<skillNames>/*` bundled assets, diffs each against the
  project's copy, and writes only the ones that are missing or differ.
- Expose it as a new top-level `musubix3 upgrade` command (with `--dry-run`),
  independent of `init`/`init --force`.
- `upgrade` never touches `.musubix/config.json`, `.musubix/policy-baseline.json`,
  `.musubix/constitution.md`, `.musubix/decisions/`, `.musubix/features/`,
  `.musubix/evidence/`, `.musubix/cache/`, or `.gitignore`, regardless of
  flags — those remain exclusively `init --force`'s (opt-in, explicit)
  responsibility, and stay untouched by default so `upgrade` is always safe
  to run after bumping the npm package version.
- Unlike `init --force`, `upgrade` replaces a stale skill file unconditionally
  (no separate `--force` flag) because bundled skill files are documentation
  assets that users are not expected to hand-edit; if a project intentionally
  forks a skill file's content, that is out of scope for this decision.

## Rejected alternatives

- **Add a `--skills-only` flag to `init`/`--force` instead of a new command.**
  Rejected: `init` already carries `--force`/`--feature`/`--dry-run`
  semantics tied to full project bootstrap (creating starter feature
  artifacts, merging `.gitignore`, generating `trace.json`); overloading it
  with a fourth, narrower "safe subset" mode makes the existing flag
  combinations harder to reason about. A separate `upgrade` command keeps
  each command's blast radius simple to state and document.
- **Make `upgrade` also refresh `.musubix/decisions/ADR-0001.md` (the
  starter ADR template).** Rejected: `ADR-0001.md` is written into the
  user's chosen feature-adjacent decisions directory as a starter example
  meant to be edited or superseded, not a stable bundled skill; refreshing
  it on `upgrade` risks silently overwriting an ADR a user has since edited
  in place.
- **Have `upgrade` also delete skill files removed from a newer package
  version.** Rejected out of this decision's scope: doing so safely requires
  tracking which files were originally installed by musubix3 versus
  user-added, which no current manifest records; a future decision can
  revisit this once such a manifest exists.

## Consequences

- Users can safely run `npm install --save-dev --save-exact musubix3@latest`
  followed by `npx --no-install musubix3 upgrade` to pick up newer Skill
  instructions without risking their customized `.musubix/config.json`,
  `constitution.md`, or feature artifacts.
- `init --force`'s existing broader (and riskier) semantics are unchanged;
  `upgrade` is purely additive.
- README.md/README-ja.md document `upgrade` as the recommended upgrade path,
  distinct from first-time `init`.
