# ADR-0014: Add specific-reason diagnostic text without changing classifyEars's or ID validation's return contracts

## Context

`classifyEars()` returns `EarsPattern | null` and is asserted directly by
existing tests (`tests/domain.test.ts`) and consumed by
`validateRequirements()`, which already computes an obligation-count reason
for the `REQ_EARS` diagnostic. Issues #2 and #3 ask for more specific reason
text (pronoun/bare subject; mixed if-then and while/when/where clause forms)
without changing what counts as valid EARS. Issue #4 asks the `REQ_ID`
diagnostic to state the expected ID pattern. None of these require any
change to classification or validation behavior itself.

## Decision

Add a new, purely diagnostic helper, `earsFailureReason(statement): string |
undefined`, in `packages/domain/src/requirements.ts`, that independently
inspects a statement already known to have failed `classifyEars()` and
returns a specific, human-readable explanation when it recognizes a pronoun
or bare subject, or a mixed if-then/while-when-where clause combination.
`validateRequirements()` appends this reason (when present) to the existing
`REQ_EARS` message, after its existing obligation-count reason. Leave
`classifyEars()`'s exported signature, its recognized-pattern set, and every
existing classification outcome completely unchanged. Change only the
`REQ_ID` diagnostic's message text in `validateRequirements()` to state the
expected `REQ-<FEATURE>-<digits>` pattern; the ID validation regex itself
(`ids.requirement`) is unchanged.

## Rejected alternatives

- **Fold reason detection into `classifyEars()` itself, changing its return
  type to include a reason.** Rejected: this would be a breaking signature
  change for existing direct callers/tests that assert
  `classifyEars(...)` against a bare `EarsPattern | null`, for no behavioral
  benefit — the reason text is diagnostic-only and has no bearing on
  classification.
- **Loosen `classifyEars()` to accept pronoun subjects or mixed clause
  forms.** Rejected: both issues explicitly describe current rejection as
  correct, controlled-EARS behavior; the gap is purely in the diagnostic
  message, not the policy of what is accepted.

## Consequences

- `REQ_EARS` diagnostics gain a more specific, actionable reason for two
  common authoring mistakes, while every currently-valid or
  currently-invalid classification remains exactly as before.
- `REQ_ID` diagnostics state the expected pattern directly, reducing
  guesswork when a requirement ID's final segment is not purely numeric.
- No change to `classifyEars()`'s exported signature or the `ids.requirement`
  regex.
