# ADR-0016: Add an optional per-command cwd, resolved and contained by the existing within() helper

## Context

Every configured command in `.musubix/config.json` always runs with the
project root as its working directory (`packages/analysis/src/tdd.ts:260,315`,
`packages/analysis/src/gate.ts:279`). A polyglot monorepo with per-service
toolchains (a service-local `node_modules`, a Go module in a subdirectory,
etc.) cannot express "run this command from this subdirectory" (GitHub Issue
#6). `configLint()`'s `CONFIG_ORPHANED_PATH` check also always resolves a
command's repository-relative path arguments against the project root, which
would misreport a path that is valid relative to a per-command working
directory as missing.

## Decision

- Add an optional `cwd?: string` field to `CommandConfig`, holding a path
  relative to the project root.
- Add and export `commandCwd(root: string, command: CommandConfig): string`
  in `config.ts`, reusing the existing `within(root, path)` helper (already
  used elsewhere to reject a path that escapes the project root) to resolve
  `command.cwd` when present, or return `root` unchanged when absent. Every
  process invocation site (`tdd.ts`'s Red preflight loop and main command
  execution, `gate.ts`'s command execution) calls `commandCwd()` instead of
  passing `root` directly.
- `configLint()` computes each command's `commandCwd()` result once per
  command (catching an escaping/nonexistent `cwd` as a new diagnostic
  instead of letting `within()`'s thrown error propagate uncaught), and
  resolves that command's `CONFIG_ORPHANED_PATH` argument scan against that
  base directory instead of always the project root, by passing
  `resolve(base, arg)` (already-absolute) into the existing `within(root,
  ...)` escape check, which still enforces overall project-root containment
  regardless of the per-command base.
- Evidence and configuration paths (`tddReport`/`testReport`/`mutationReport`
  paths, the `.musubix/config.json` file itself) are deliberately **not**
  affected by `cwd`; they remain resolved from the project root exactly as
  before. Only the spawned process's OS-level working directory changes.

## Rejected alternatives

- **A `workspaces` mapping referenced by name from each command.** Rejected
  for this change: strictly more config surface (a new top-level schema
  section, a new resolution/validation path) than the issue's actual need,
  which is one directory per command; can be layered on top later as a
  convenience without breaking `cwd` if it is ever added.
- **Infer a working directory automatically from a nearby manifest file
  (`package.json`, `go.mod`, `Cargo.toml`).** Rejected: contradicts the
  project's explicit-configuration-only policy for trusted command
  execution; inference from ambient files is not deterministic across
  differently-shaped repositories and cannot be lint-validated the way an
  explicit field can.

## Consequences

- A configured command can now run inside a service subdirectory,
  independent of any adapter-specific directory flag (`go test -C`,
  `cargo test --manifest-path`), and this applies uniformly to every
  adapter, including ones (like `junit`) that have no such flag of their
  own.
- `config lint` gains a new failure mode (an invalid `cwd`) but does not
  regress its existing `CONFIG_ORPHANED_PATH` check for any command that
  does not declare `cwd`.
