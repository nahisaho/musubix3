# ADR-0022: Detect unchanged-fingerprint change phases before appending evidence, not only during later validation

## Context

`recordChangePhase` (`packages/analysis/src/change.ts`) computes
`currentFingerprints(...)` and unconditionally appends an evidence-order
record and a phase entry to `.musubix/evidence/changes.json`. The check for
whether a phase's fingerprint is a meaningless no-op relative to its
immediately preceding phase (`CHANGE_REQUIREMENTS_UNCHANGED`,
`CHANGE_DESIGN_UNCHANGED`, `CHANGE_TESTS_UNCHANGED`,
`CHANGE_IMPLEMENTATION_UNCHANGED`, `CHANGE_RELEVANT_IMPLEMENTATION_UNCHANGED`)
exists only in `validateChangeEvidence`, run later by `trace check --strict`
and `gate`. Because every phase can be recorded at most once per change, and
`.musubix/evidence/changes.json` plus `.musubix/evidence/order.json` are
treated as append-only ledgers throughout this codebase (no reset/overwrite
command exists), a mistake is only discovered once it is already permanent.
This was independently reproduced in this repository's own working history
(`CHANGE-0009`, GitHub Issue #19) and in an external project (GitHub Issue
#20, `nahisaho/aira2` `CHANGE-0001`/`CHANGE-0004`).

One legitimate case exists where an "unchanged" fingerprint is not a
mistake: `sdd-change`'s own workflow documents that a defect fix which
violates an existing requirement should keep that requirement's text
unchanged (`## 2.2` of the `sdd-change` skill). No other phase transition
has a documented legitimate no-op case.

## Decision

1. Move the five existing "unchanged" comparisons (or their direct
   equivalents) from validation-time-only to also run **inside
   `recordChangePhase`, before `appendEvidenceOrder` and before any write to
   `changes.json`**, for the five phase transitions where an unchanged
   fingerprint is never legitimate: `requirements` after `impact`, `design`
   after `requirements`, batch `red` (tests) after `design`, batch
   `implementation` after `red` (both the aggregate implementation
   fingerprint and each covered requirement's relevant-implementation
   fingerprint). A rejection throws before any evidence file is touched, so
   `changes.json` and `order.json` stay byte-identical to their
   pre-invocation state — no evidence-order sequence number is consumed by a
   rejected attempt.
2. Give each of these five record-time rejections its own diagnostic code
   with an `_AT_RECORD` suffix (`CHANGE_REQUIREMENTS_UNCHANGED_AT_RECORD`,
   `CHANGE_DESIGN_UNCHANGED_AT_RECORD`, `CHANGE_TESTS_UNCHANGED_AT_RECORD`,
   `CHANGE_IMPLEMENTATION_UNCHANGED_AT_RECORD`,
   `CHANGE_RELEVANT_IMPLEMENTATION_UNCHANGED_AT_RECORD`), distinct from the
   five existing validation-time codes, which are kept unchanged and continue
   to protect historical evidence recorded before this change (or recorded
   by a future version of the CLI without these guards, e.g. a downgrade).
3. Add a `requirements`-phase-only `--allow-unchanged` CLI flag. When used,
   `recordChangePhase` records the phase and additionally sets a durable
   `allowUnchanged: true` marker on that specific `ChangePhaseEvidence`
   entry. `validateChangeEvidence` reads this marker and skips
   `CHANGE_REQUIREMENTS_UNCHANGED` for that one change, and only that one of
   the five diagnostic codes. The override is deliberately not offered for
   `design`, `red`, or `implementation`, since no legitimate no-op case for
   those phases is documented; adding it there would let a real mistake
   (e.g. forgetting to actually implement) escape detection entirely.
4. Add a `--dry-run` flag to `change-record` that runs every check (existing
   prerequisite/duplicate/subset/coverage validation and the five new
   fail-fast checks) and reports the outcome without calling
   `appendEvidenceOrder` or writing `changes.json`.
5. Document all three (`_AT_RECORD` fail-fast rejection, `--allow-unchanged`,
   `--dry-run`) in `change-record --help` and `README.md`, not only in the
   `sdd-change` skill file.

## Consequences

- A caller now learns about a no-op phase recording immediately, while the
  mistake is still correctable (edit the file, retry the same command),
  instead of discovering it much later via `gate`/`trace check --strict`
  once it is unfixable.
- Existing recorded evidence (e.g. `CHANGE-0005`, `CHANGE-0009` in this
  repository) that already has an unchanged-fingerprint phase is untouched:
  this feature only guards *new* `change-record` invocations. The five
  original validation-time diagnostic codes keep firing for that historical
  evidence exactly as before.
- `ChangePhaseEvidence` gains one new optional field (`allowUnchanged?:
  boolean`), used only by the `requirements` phase; this is an additive,
  backward-compatible schema change (old evidence without the field is
  treated as `false`).
- The `--allow-unchanged` escape hatch is intentionally narrow (one phase
  only) so it cannot be used to silently mask the exact class of mistake
  this feature exists to prevent.

## Alternatives considered

- **Only add a `change-record --reset`/overwrite command** (letting a
  mistake be fixed after the fact instead of prevented). Rejected: this
  would require deciding how to safely mutate an append-only, hash-chained
  ledger retroactively (the same class of risk this project's own evidence
  files are deliberately designed to avoid), and does not address the
  "silently accepted" root cause the issue calls out.
- **Reject unconditionally with no override for any phase.** Rejected: the
  `sdd-change` skill explicitly documents a legitimate unchanged-requirements
  case (a defect fix that violates, but does not change, an existing
  requirement); an unconditional reject would make that documented workflow
  impossible to record correctly.
