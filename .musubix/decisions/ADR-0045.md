# ADR-0045: Rebase-triggered fast re-approval relies on a human-supplied own-files list, never git-derived auto-detection

## Context
Issue #71: `requirements`/`design`/`release` approval manifests are project-wide (every tracked `requirements.md`/`design.md`/ADR/release-candidate file, respectively), not scoped to one change. When a sibling in-flight branch merges to `origin/main` first, every other branch's already-recorded approval hash goes stale purely because the manifest now includes that sibling's merged content — even though the current change's own files are byte-identical to what a human already approved. Observed live during CHANGE-0049 (Issue #67): requirements/design hashes both changed after Issue #66/CHANGE-0048 merged, confirmed by manual `git diff` inspection to touch only unrelated files.

Two design questions needed a decision:
1. How does the system know which files are "the current change's own files" (so it can tell outside-caused drift from own-content drift)?
2. What level of human re-confirmation is still required when outside-only drift is detected?

## Decision
The set of "own files" is supplied explicitly by the human reviewer via a new `--own-files <path...>` option on `approval record <stage> --fast-reapprove`, never auto-derived from `git diff`/`git log`/commit ranges. The reviewer already performs this inspection today (as evidenced by Issue #71's own report: "diffs confirmed by the orchestrator to touch only the same two files with identical content") — this feature only automates the mechanical per-file hash comparison and evidence recording that follows that inspection, not the inspection itself.

This keeps the feature consistent with ADR-0043's precedent (the `--diff-only` feature deliberately avoided introducing a live-git-diff dependency into the `requirements`/`design` stages, which do not otherwise require git at all): auto-deriving "own files" from git history would need commit-range reasoning that is unreliable across a rebase (a rebase rewrites commit SHAs, so "this branch's own commits since it last diverged" has no single stable git-native answer once the branch has been rebased one or more times), and would silently trust a heuristic for exactly the safety-critical judgment ("did MY content actually stay the same") this feature exists to never get wrong. An explicit, human-supplied list, failed closed (REQ-APPROVAL-REBASE-FAST-REAPPROVAL-004's empty-list and unknown-path rejections), keeps that judgment squarely with the accountable reviewer while eliminating the repeated manual hash/approval-recording toil.

Fast re-approval additionally requires the identical approver as the prior recorded decision (REQ-APPROVAL-REBASE-FAST-REAPPROVAL-003) and still requires `--confirm` plus an exact full-manifest `--artifact-sha256` match (REQ-APPROVAL-REBASE-FAST-REAPPROVAL-005) — the automation only removes the need to re-read content already reviewed, never the explicit confirmation step, never the cryptographic full-manifest binding, and never a change of accountable decision-maker.

## Rejected alternatives
- **Auto-derive own-files from `git diff <merge-base> HEAD`**: rejected because a rebase makes "this branch's own commit range" ill-defined (SHAs change on every rebase), and because it would silently convert a safety-critical reviewer judgment into an unreviewed heuristic — exactly the failure mode this feature must avoid per its own requirements.
- **Allow a different approver for the fast-reapproval**: rejected; Issue #71 explicitly frames this as re-recording "the same original decision," and allowing a new reviewer to fast-approve content they never read would be a real review-bypass, not a friction reduction.
- **Compute a narrower, own-files-scoped hash instead of the full manifest hash**: rejected; this would weaken the exact cryptographic guarantee `approval record` already provides (REQ-APPROVAL-REBASE-FAST-REAPPROVAL-005), reintroducing the very integrity regression Issue #71 explicitly says must not happen ("must preserve the full cryptographic completeness guarantee").
- **Make `--fast-reapprove` fully automatic (no new `--confirm`-equivalent gesture)**: rejected per Issue #71's own proposal text ("must still require a fresh explicit confirmation step (never fully automatic)"); `--confirm` and the exact hash match already serve this role without inventing a second confirmation mechanism.

## Consequences
A reviewer who has already manually confirmed that a rebase only touched files outside their own change can now record the resulting re-approval with one command instead of a full manual re-review, while every existing precondition (`approval record`'s approver/hash/domain/release-prerequisite checks) and the full-manifest hash binding remain exactly as strict as before. The tradeoff: this feature does not eliminate the reviewer's own diffing work (deciding which paths are genuinely "their own"), only the downstream recording friction — a future enhancement could still explore git-assisted own-files suggestion, but only as a reviewer-facing hint to verify, never as an auto-trusted input, to avoid reintroducing the rejected heuristic above.
