# ADR-0024: Broaden the CHANGE_COMPLETENESS_ACCEPTANCE keyword heuristic instead of rewriting requirement text or replacing it with a structural parser

## Context
`validateChangeEvidence`'s `CHANGE_COMPLETENESS_ACCEPTANCE` diagnostic treats an
`Acceptance:` value as "measurable" only if it is non-placeholder, at least 8
characters, and matches a fixed keyword regex. An audit of every
`Acceptance:` block across `.musubix/features/*/requirements.md` found 11
already-approved requirements (`REQ-APPROVAL-DOMAIN-SCOPING-002/003/005/009/011/013/015/020`,
`REQ-CLI-WORKFLOW-UX-002/003`, `REQ-TDD-CYCLE-VOID-003`) whose Acceptance
text is a concrete, human-reviewed, testable outcome description (e.g.
"reports an error naming the feature directory", "exits nonzero listing the
configured domain names") that nonetheless contains none of the current
keywords, producing a false-negative `CHANGE_COMPLETENESS_ACCEPTANCE`
diagnostic. This recurred as a named, disclosed blocker in GitHub Issue #1
(recurrence comment, Issue #19/#20 era) and is one of three residual gate
blockers this round of work addresses.

## Decision
Extend the existing keyword regex with 17 additional case-insensitive
substrings (`report`, `error`, `reject`, `contain`, `unaffected`,
`unchanged`, `invalid`, `missing`, `stale`, `silently`, `substring`,
`naming`, `configur`, `exit`, `omit`, `affect`, `raise`) derived directly
from the 11 audited real false-negative cases, verified to make all 11
pass. To close the regression this broadening would otherwise open (e.g.
"TODO: configure later" would newly match `configur` and pass), also
extend the existing whole-value placeholder rejection to a prefix form:
reject any value beginning (after trim, case-insensitively) with a
placeholder token followed by optional whitespace and a `:`, `-`, or `—`
separator. Both changes stay inside the existing single boolean expression
in `change.ts`; no new function signature, diagnostic code, or requirement
schema field is introduced.

## Rejected alternatives
- **Rewrite the 11 requirements' Acceptance text to include a recognized
  keyword.** Rejected: every one of the 11 requirements already has a
  current, human-approved `requirements` stage approval; editing
  `requirements.md` invalidates that approval and forces a disproportionate
  re-review of unrelated, already-shipped requirements for a heuristic gap,
  not a content defect.
- **Replace the keyword heuristic with a structural parser** (e.g. requiring
  a colon-delimited condition/outcome clause, or an EARS-like grammar
  parse of the Acceptance text). Rejected for this change: a structural
  parser is a larger, higher-risk redesign of an evidence-completeness
  check that would need its own dedicated design and broad regression
  testing against every existing Acceptance block in the repository;
  disproportionate to fixing 11 confirmed false negatives. Recorded here as
  a candidate follow-up if keyword-list drift recurs again.
- **Do nothing and treat the 11 cases as permanently accepted debt** (as
  Issue #1's item 4 originally did for the release-approval blocker).
  Rejected: unlike the TDD-chain and change-history debt, this diagnostic
  is a heuristic defect with a narrow, verifiable, non-destructive fix
  available; leaving it unfixed when a safe fix exists does not meet the
  "never weaken policy, but do fix genuine tooling bugs" standard applied
  elsewhere in this repository.

## Consequences
- All 11 previously-false-negative `CHANGE_COMPLETENESS_ACCEPTANCE`
  diagnostics on `CHANGE-0009` (`approval-domain-scoping`) and pre-existing
  requirements clear without editing any `requirements.md` file or
  reopening any existing approval.
- The keyword list is now longer and slightly more permissive; any future
  Acceptance text that both (i) is at least 8 trimmed characters, (ii) is
  not placeholder-prefixed per the new rule below, and (iii) contains one
  of the new substrings inside otherwise vague prose (e.g. an Acceptance
  value that happens to contain "exit" in an unrelated sense) will also
  pass. This is an accepted, bounded precision/recall trade-off consistent
  with the heuristic's existing design, not a correctness regression for
  any currently-passing or currently-failing case verified in this change,
  other than the intentional reclassifications noted below.
- The new placeholder-prefix rejection is a deliberate, conservative
  lexical heuristic: it reserves a leading `TODO`, `TBD`, `N/A`, `none`, or
  `未定` token followed by `:`, `-`, or `—` for placeholder text. This is
  intentionally stricter than the prior whole-value-only check, so it can
  cause a small number of previously-passing, placeholder-prefixed values
  (e.g. `TODO: test passes`, which the old keyword regex accepted via
  `test`) to newly fail. This reclassification is required by
  REQ-CHANGE-ACCEPTANCE-HEURISTIC-002 and is not itself a defect; no
  currently-approved Acceptance text in this repository was found to match
  this prefix form (verified by the same audit that found the 11 false
  negatives), so no existing approval is invalidated by this change.
