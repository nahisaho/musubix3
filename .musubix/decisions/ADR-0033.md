# ADR-0033: Validate release approval from a clean tracked tag checkout

## Status
Accepted

## Context
Release approval is recorded before the final commit and tag, while release
preparation runs after checkout of that tag. The existing release approval
manifest intentionally covers project inputs beyond files already tracked at
approval time, because newly authored source and specification files may not yet
be committed. GitHub Actions also creates untracked tools such as `.test-tools/`
before preparation. Recomputing approval from every on-disk file would therefore
make valid CI releases stale, while comparing only the tag and ignoring the
working tree could allow local uncommitted tracked changes into `npm pack`.

## Decision
Use one release-specific Git path eligibility model for release approval
preparation and tagged validation. Requirements and design approval continue to
use the existing filesystem inventory unchanged. Git selection is an additional
release-stage boundary, not a replacement for ADR-0002's
generated/evidence/nested-workspace exclusions:

1. Build a complete candidate set from NUL-delimited Git output: tracked index
   entries with modes from `git ls-files -z -s --cached`, plus untracked,
   non-ignored entries from `git ls-files -z --others --exclude-standard`.
   Reject index conflicts, omit missing tracked files to represent deletions, and
   admit only regular files; symlink and gitlink modes are excluded.
2. Apply a pure release path-set filter to the complete candidate set. It derives
   nested workspace and language-specific generated-directory boundaries from
   marker paths in that same set, then applies standard generated, evidence,
   cache, trace, archive, and log exclusions. Release approval keeps
   `.github/skills/**`; the separate evidence-input skill exclusion is not used.
3. Use that inventory for both release approval recording and ordinary release
   approval validation only when the requested project root exactly equals
   `git rev-parse --show-toplevel`. Non-Git projects and Git subdirectory roots
   retain the prior filesystem fallback for those operations; tagged release
   validation itself requires an exact Git top-level root. Candidate inventory,
   release approval recording, ordinary release-stage validation, and tagged
   release validation remain strict at an exact root and propagate typed Git
   precondition errors; they never substitute the materially different
   filesystem artifact set.
4. Resolve the tag commit and always require it to equal `HEAD`; when
   `GITHUB_SHA` is present, require that identity to match as an additional
   condition.
5. Enumerate the committed tag tree with NUL-delimited mode and path data. Reject
   mode/type changes on structurally eligible tracked paths before mode-based
   inventory exclusion; parse NUL-delimited rename/copy status records with both
   new and old paths. Then apply
   the identical release path-set eligibility, and exclude symlink and gitlink
   modes. Limit working-tree dirty checks to the
   union of eligible approved, tagged, and candidate release-input paths, so
   generated evidence outside the release manifest cannot block preparation.
   Eligible non-ignored untracked files block because `npm pack` consumes them;
   ignored runner scratch does not.
6. After release inputs are clean, SHA-256 hash their on-disk bytes. Because the
   tag equals `HEAD` and every eligible release input is clean, this is the tag's
   release-input manifest.
7. Compare that complete manifest with the artifact map stored in release
   approval evidence. Missing required approval fails with no drift entries;
   stale approval reports every added, modified, and deleted path in Unicode
   scalar-value order. Invalid approval schema and Git precondition failures
   remain distinct typed errors. Compatible mode relaxes missing approval only;
   tag identity, dirtiness, and stale approval remain enforced.

Release preparation consumes this validation through the built analysis API.
The script remains the release boundary and emits the typed approval report on
stderr without changing successful stdout or the separate release-version
diagnostic contract. It uses an awaited async entry point and lazily loads the
built analysis API only when no test dependency is injected.

For manual GitHub Actions dispatch, checkout cannot change the event's
`GITHUB_SHA`. The workflow therefore requires the selected workflow ref itself
to be the same tag named by `release_tag`; it rejects branch-ref or mismatched-tag
dispatch before checkout and keeps checkout on `github.ref`. Event ref values
enter the shell only through quoted environment variables.

## Rejected alternatives
- **Hash every on-disk file during CI preparation.** This treats untracked,
  ignored test tools and runner scratch data as release inputs and permanently
  stales otherwise valid approval.
- **Use raw `git ls-files` as the release inventory.** This reintroduces
  `.musubix/evidence`, nested MUSUBIX3 workspaces, symlinks, and other paths that
  ADR-0002 and the filesystem inventory intentionally exclude, including the
  release approval evidence itself.
- **Change `files()` to operate on Git paths.** This would alter requirements and
  design approval manifests and stale unrelated approvals. The Git inventory is
  release-specific and leaves the existing filesystem inventory unchanged.
- **Keep approval preparation filesystem-only and normalize only at validation.**
  Ignored output files can enter approval before the tag and then appear deleted;
  using the same Git candidate inventory at both stages avoids asymmetric drift.
- **Validate only the tag commit and approval hash.** Local `npm pack` consumes
  the working tree, so tracked modifications after checkout could be published.
- **Run `git archive` or create a temporary worktree for every validation.**
  This reads the tag accurately but adds lifecycle cleanup and binary archive
  handling when a clean tracked checkout already provides identical bytes.
- **Duplicate approval-manifest filtering in `scripts/`.** Separate exclusion
  logic would drift from approval preparation and could accept a different
  artifact set.
- **Trust cached quality or approval status.** Cached status does not prove the
  final tagged tree still matches the reviewed artifact manifest.

## Consequences
- Valid CI scratch files do not invalidate approval because they are untracked.
- Staged and unstaged release-input changes block preparation before any release
  output mutation, while tracked generated evidence outside the manifest does
  not.
- Eligible non-ignored untracked files also block because local package creation
  would otherwise publish bytes absent from the tag; ignored scratch remains
  irrelevant.
- Approval preparation no longer binds ignored output artifacts; non-ignored
  newly authored inputs remain bound before commit and must appear in the tag.
- Existing non-Git approval workflows preserve their filesystem behavior, while
  tagged release preparation reports an explicit Git precondition failure.
- At an exact Git root, release approval recording and validation fail explicitly
  if the Git candidate inventory is unavailable; neither path binds ignored
  filesystem scratch or misreports it as approval drift.
- Git release inventory recognizes a nested workspace only when its `.musubix`
  marker has a tracked or non-ignored candidate path. This intentionally differs
  from the non-Git filesystem fallback, which can observe an otherwise empty or
  fully ignored `.musubix` directory.
- Release preparation rebuilds `dist/` from the checked-out source tree before
  approval validation and packaging, so packaging never ships derived output
  from a tree that subsequently fails approval; `dist/` remains outside the
  approval manifest because it is derived output.
- This inventory correction intentionally makes prior release approval stale;
  the first release containing it must record fresh release approval after the
  final commit contents are settled.
- Release preparation depends on the repository build output, matching the
  documented build-before-prepare sequence and existing package generation.
- Local approver identity remains self-reported under ADR-0002; this decision
  strengthens artifact and commit binding, not identity authentication.
