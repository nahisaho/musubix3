# ADR-0028: Advisory `warnings` field on `TddPhaseEvidence`, separate from `diagnostics`

## Status
Accepted

## Context
`runTddPhase` (`packages/analysis/src/tdd.ts`) computes each recorded Red /
Green / Refactor phase's `TddPhaseEvidence.valid` as `!diagnostics.length` —
any entry in `diagnostics` makes the recorded phase invalid. Issue #23 needs
`tdd red` to surface a `TDD_ADOPTION_PROJECT_WIDE` advisory the moment it
persists the project's first TDD cycle (`evidence.cycles.length` becomes
nonzero), listing every other uncovered mandatory requirement. This
diagnostic must never make an otherwise-valid Red invalid, and must never be
silently dropped for a Red that is itself invalid for unrelated reasons.

## Decision
Add a new optional `warnings?: Diagnostic[]` field to `TddPhaseEvidence`,
populated only for the `red` phase and only when `evidence.cycles.length`
was `0` immediately before this call pushes its new cycle. `valid` continues
to be computed exclusively from the existing `diagnostics` array; `warnings`
never participates in that computation. The CLI (`packages/cli/src/main.ts`)
appends each entry's message to the non-JSON `tdd red` summary output in
addition to the existing `RED: PASS|FAIL` line; `--json` output includes
`warnings` as part of the returned `TddPhaseEvidence` object with no
additional code, since it is serialized as-is.

## Rejected alternatives
- **Push the new diagnostic into the existing `diagnostics` array and
  compute `valid` from only `severity === 'error'` entries.** This changes
  the meaning of `diagnostics`/`valid` for every existing and future
  diagnostic code produced by `runTddPhase`, not just this one — a
  blast-radius far larger than this feature's actual scope, for a codebase
  path (`TddPhaseEvidence`) that several other requirements
  (`REQ-TDD-GREEN-REQUIREMENT-SCOPING-*`, `REQ-TDD-CYCLE-VOID-*`) already
  depend on behaving exactly as `!diagnostics.length`.
- **A separate `tdd doctor`/`tdd status`-style command that a user must run
  proactively to see the adoption warning.** This is opt-in and easy to
  never run; the whole point of Issue #23 is that the project-wide
  consequence happens silently on an ordinary `tdd red` call, so the warning
  must appear on that same call by default, not on a separate command the
  user has no reason yet to know they need.
- **Emit the warning only via `gate`'s existing `tdd` check output, once the
  project-wide requirement is already active.** By definition this is
  strictly too late: it reports the consequence after it has already taken
  effect project-wide, rather than warning the user before/as they trigger
  it as REQ-TDD-ADOPTION-WARNING-001 requires.

## Consequences
- `TddPhaseEvidence.valid`'s existing meaning (`!diagnostics.length`) is
  completely unchanged; no other diagnostic code's behavior can regress.
- `warnings` is absent (`undefined`) on every phase this feature does not
  target (`green`, `refactor`, and any `red` call after the first project
  cycle), keeping existing persisted evidence and downstream readers that
  ignore unknown fields unaffected.
- Because the warning is computed and stored inside the persisted
  `TddPhaseEvidence` at Red time (as part of its hashed chain-record
  payload), the exact warning that was surfaced at the time of adoption
  remains durably recorded in `.musubix/evidence/tdd.json`, without needing
  to re-derive "was this the first cycle" after the fact (which would be
  ambiguous once more cycles exist). `tdd validate`/`validateTddEvidence`
  itself is out of scope for this change and does not read or re-surface
  `warnings`; it continues to report only `{ valid, diagnostics, cycles,
  voided }` exactly as before. Surfacing persisted adoption warnings through
  `tdd validate` as well, if ever desired, is a separate, explicitly
  reviewed change.
