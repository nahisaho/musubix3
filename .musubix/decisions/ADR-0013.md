# ADR-0013: Scope Green/Refactor cycle matching by requirement ID and validate before any side effect

## Context

`runTddPhase()` resolves the pending cycle for a `green` or `refactor`
recording as `evidence.cycles.filter(c => c.testId === testId).at(-1)` —
the single latest recorded cycle for that test ID, regardless of
`requirementId`. Since `ADR-0011`/`ADR-0012` and the `change-record`
per-requirement batch feature (GitHub Issue #12) allow one test ID to have
more than one independently pending cycle for different requirement IDs at
once, only the most-recently-created pending cycle can ever receive its
Green; any older pending cycle for that same test ID becomes permanently
stuck. Separately, `appendEvidenceOrder` is called before the
requirement/command mismatch check runs, so a rejected recording still
leaks an entry into the append-only, unique-key monotonic order log. That
leaked entry can never be removed through normal CLI operation, so the
correct cycle's own subsequent `green` recording is permanently rejected as
a duplicate order-log entry (GitHub Issue #14).

## Decision

1. Resolve `previous` for a non-Red phase by matching **both** `testId` and
   `requirementId` against recorded cycles, not `testId` alone.
2. Perform all pre-flight validation for the phase (a matching valid
   pending cycle exists, its Red phase and test fingerprint are valid, and
   its recorded command name matches) strictly before invoking the
   configured test command and before calling `appendEvidenceOrder`.
3. Only after that validation succeeds may the test command run and the
   order-log entry be appended.

This is a purely mechanical correction to existing matching/ordering logic;
it does not change the evidence schema, the CLI surface, or add any new
phase or approval step.

## Rejected alternatives

- **Leave `previous` matching by `testId` only, and instead let users avoid
  interleaving pending cycles for the same test ID.** Rejected: the
  `change-requirement-batches` feature (Issue #12) explicitly enables
  per-requirement independent tracking for a single test; forbidding
  interleaving would silently reintroduce the same limitation through a
  workflow rule instead of a design fix.
- **Add a CLI command to repair/remove a leaked order-log entry.** Rejected:
  this treats a symptom rather than the cause, adds a new surface for
  mutating append-only evidence (undermining its integrity guarantee), and
  does nothing to prevent the same corruption recurring on the next
  mismatch.
- **Buffer the order-log append until after the test command runs, but
  still after validation passes.** Considered and folded into the decision
  above: validation must run first regardless of when the append happens,
  so there is no reason to append after test execution — appending
  immediately after validation succeeds (and before running the command)
  is simplest and matches the existing pattern for the Red phase.

## Consequences

- Two or more independently pending cycles for the same test ID (each for a
  different requirement ID) can each be completed to Green independently,
  regardless of recording order.
- A rejected `green`/`refactor` recording never appends an order-log entry,
  so a subsequent, correctly-matched recording for the same cycle is never
  blocked by a prior rejection.
- No change to the evidence file schema, CLI commands, or approval flow.
