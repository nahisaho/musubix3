# ADR-0036: Upgrade Vitest to the minimum stable fixed 4.x release

## Context

GitHub Advisory GHSA-82fw-gwwq-j7x9 affects `vitest` and
`@vitest/mocker` from 2.1.0 through 4.1.10. The repository directly requires
Vitest 3.x and resolves Vitest 3.2.7, producing two moderate npm audit findings
for the same arbitrary-file-read advisory. The advisory states that maintained
fixes begin at 4.1.11 and that older 2.x and 3.x lines will not receive a fix.
It also identifies a separate affected Vitest 5 prerelease range beginning at
5.0.0-beta.1 and fixed at 5.0.0-rc.2.

The affected code is development-server mock interception. The repository does
not currently expose that path, but contributors still install the vulnerable
code and future test-server configuration could make it reachable. The package
supports Node.js 20 and later, while Vitest 4.1.11 supports the CI lines Node.js
20, 22, and 24.

## Decision

Require `vitest: "^4.1.11"`, regenerate `package-lock.json` with npm, and add an
offline deterministic checker for the manifest, resolved dependency versions,
test configuration, scripts, documentation policy, and recorded advisory
evidence. Run `npm audit --json` separately at verification time and record its
result in CHANGE-0022 rather than making the test suite depend on the registry.

Treat the upgrade as a reviewed major-version migration even when no source
compatibility edit is ultimately required. Preserve the package's production
dependency, export, executable, and packaged-file surfaces.

## Rejected alternatives

### Retain Vitest 3.x and document non-reachability

Rejected because no maintained 3.x fix exists, contributors continue to install
the vulnerable code, and the repository could make the path reachable later.
Non-reachability is useful exposure analysis but is not remediation when a
maintained fix is available.

### Upgrade directly to Vitest 5.x

Rejected because 4.1.11 is the minimum stable fixed version and the smallest
major migration from the current 3.x line. Moving to 5.x would introduce
additional compatibility scope without improving this advisory's disposition.

### Use npm overrides or a patched fork

Rejected because `@vitest/mocker` is version-coupled to the Vitest packages.
Overriding only the transitive dependency risks an unsupported mixed graph, and
maintaining a fork adds provenance and update obligations that the upstream
fixed release avoids.

### Execute `npm audit` inside the deterministic test suite

Rejected because registry availability and newly published unrelated advisories
would make ordinary tests non-deterministic. The lockfile checker proves the
known advisory remediation offline; the live audit remains explicit,
time-stamped release-readiness evidence.

## Consequences

- The project accepts a necessary development-tool major upgrade and validates
  the full suite and package distribution afterward.
- The reviewed Vitest 4 migration surface includes mock restoration/name/order
  changes, automock behavior, Module Runner replacement, pool rework, and
  removed deprecated options. This repository does not use the affected
  restoration/global-history, custom environment, custom pool/reporter,
  browser, or coverage APIs; its `vi.spyOn` calls restore spies explicitly, and
  the complete suite proves the remaining `vi.mock` behavior.
- The resolved Vite dependency requires at least Node.js 20.19 or 22.12. The
  published package retains `engines.node >=20`, while repository test
  development and CI use the latest patch of Node.js 20, 22, or 24.
- Contributors using Node.js 21 or 23 can still run the published package, but
  repository test development requires a Vitest-supported Node.js line.
- Any `package-lock.json` byte change invalidates the recorded audit digest and
  intentionally requires a fresh `npm audit --json` result plus updated
  CHANGE-0022 timestamp/digest evidence before deterministic checks pass.
- Future audit findings require new reachability and remediation evidence; a
  clean result recorded for this change is not a permanent security claim.
