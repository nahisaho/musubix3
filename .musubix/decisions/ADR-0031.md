# ADR-0031: Fail-fast filesystem coordination with async owner context

## Status
Proposed

## Context
musubix3 operations update append-only order evidence, multi-file TDD/change
state, configured command reports, generated traces, caches, attestations, and
quality evidence. Independent processes can otherwise clear or replace these
artifacts concurrently, and nested analysis operations can deadlock or reject
their own reads if ownership is represented only by a process ID. The existing
evidence-merge journal solves crash recovery for four merge targets but is not
a general mutual-exclusion mechanism.

The coordination must fail immediately rather than queue, work for direct
analysis-library callers as well as CLI commands, preserve nested operations,
and never steal a lock when host/process identity is uncertain.

## Decision
Use one canonical project-root lock at
`.musubix/evidence/.writer-lock.json`. Publish complete metadata by writing and
fsyncing a same-directory transaction-qualified staging file and atomically
hard-linking it to the canonical path. The exclusive link provides exactly one
winner without exposing partially written canonical metadata. Treat an existing
canonical path as fail-fast contention; do not poll, queue, or start a daemon.
After publication, verified acquisition-rollback unlink, and verified release
unlink, synchronize the containing directory through synchronous and
asynchronous variants that share capability classification but receive an
explicit per-call-site strictness policy. Publication, acquisition rollback,
and release may treat only Windows `EPERM`, `EINVAL`, and `ENOTSUP`
from synchronizing an already-open directory handle as an unsupported
durability capability after staging-file sync and atomic publication or
verified unlink have succeeded. Recovery uses strict synchronization with no
capability suppression. Preserve fail-closed behavior on every non-Windows
platform and for every non-capability error. Never suppress file sync,
directory open/close, hard-link, metadata verification, unlink, or other
filesystem errors.

Represent in-process ownership with an unforgeable token stored in Node.js
`AsyncLocalStorage`. Maintain a reference-counted lease per canonical root so
nested and concurrent sibling operations in the same owner context reuse the
filesystem lock. Install the root's in-flight acquisition promise synchronously
before awaiting filesystem I/O so `Promise.all` siblings cannot self-contend,
and reuse an existing async store for nested calls. Keep the staging descriptor
open through hard-link publication and capture the published inode's
device/inode identity from that descriptor in private lease state. At zero
references, re-open
the canonical lock and require its canonical root, transaction ID, and
device/inode identity to remain unchanged immediately before unlink. Require the matching context
at protected write choke points; same-process work outside that context remains
an unrelated contender. Canonicalize every guard root with a cached `realpath`
before comparing it with the owner lease. The cache is scoped to one operation
and discarded afterward rather than becoming a process-lifetime symlink cache.

Classify every CLI leaf and resolved mode exactly once as a lock-owning writer,
coordinated reader that fails fast
when an unrelated writer is already present, or source-only/recovery
exemptions. Put writer coordination at analysis-layer operation entries and
retain I/O guards as a backstop. Evaluate the writer lock before the merge
journal guard. Evidence merge acquires the general lock before running the
ADR-0030 journal transaction; merge recovery follows the same order, while
dry-run merge checks the destination and then incoming roots as coordinated
readers. Exported analysis APIs with project-artifact side effects have a
separate exhaustive writer-entry registry.
Represent lock failures with a typed error contract so CLI JSON preserves
stable codes, owner metadata, lock paths, acquisition causes, and structured
acquisition-rollback failures rather than flattening them into `CLI_ERROR`.
Reject a caller-selected output that resolves into protected evidence, cache,
generated feature trace, or configured report storage with
`EVIDENCE_PROTECTED_OUTPUT_REJECTED`; an exempt command cannot use an output
option to bypass writer coordination.

Record hostname plus available boot/session and process-start fingerprint data.
On Linux this includes boot ID, process start identity, and PID-namespace
identity and enables automatic recovery of a demonstrably dead same-host owner.
Other platforms remain inspection-only until equivalent probes are implemented.
`evidence unlock --recover` removes only a same-host lock whose recorded process
is demonstrably dead and whose transaction ID remains unchanged on a final
read. It also requires the same device/inode identity immediately before
unlink. Refuse PID reuse, cross-host/boot/PID-namespace, malformed, changed, or
indeterminate states without mutation. Provide targeted manual
inspection/removal guidance instead of a force option.
An absent, unreadable, malformed, replaced, or mismatched lock at normal release
fails closed as `EVIDENCE_WRITER_LOCK_RELEASE_FAILED`. If protected work already
failed, retain that error as primary and attach the release failure as structured
secondary context.
Record which root and lock-container directories an acquisition created and
remove only those directories when they remain empty. Directory cleanup is
best-effort and never changes the primary operation or release result.

## Rejected alternatives
- **Wait queues, retry loops, or a lock daemon.** They add timeout, fairness,
  lifecycle, and orphan-daemon behavior that Issue #28 does not require and
  obscure which operation owns project mutation.
- **Use only `open(..., 'wx')` on the canonical JSON file.** Exclusive creation
  occurs before the JSON bytes are complete, so contenders can observe empty or
  partial metadata and misclassify a valid acquisition as malformed recovery
  state.
- **Temporary file followed by rename.** Rename can replace an existing lock
  and therefore does not provide an exclusive winner.
- **Atomic lock directory created with `mkdir`.** It offers broad exclusive
  creation support, but the required owner metadata would live at a second path
  inside the directory and readers must handle a created-but-not-populated
  directory. Keeping one canonical JSON metadata path with an exclusive hard
  link makes complete publication and operator inspection one state.
- **Use PID and hostname alone.** PID reuse and container/boot changes can make
  a stale owner look live or a different execution environment look local.
- **Automatically reclaim apparently stale locks during normal commands.** A
  false stale determination can permit concurrent mutation; recovery must be
  an explicit operator action.
- **Add `--force` recovery.** A force path converts uncertainty into possible
  evidence corruption. Exact targeted manual removal after inspection remains
  available without presenting it as a safe automated operation.
- **Use a process-global boolean or PID as reentrancy.** Unrelated operations in
  the same process could bypass the lock, while nested async operations could
  release each other's ownership.
- **Replace the evidence-merge journal with the lock.** Mutual exclusion does
  not provide rollback/roll-forward after a multi-file merge interruption;
  ADR-0030 remains necessary beneath the lock.

## Consequences
- Exactly one process can publish the lock on filesystems that provide the
  required same-filesystem hard-link semantics; unsupported environments fail
  explicitly before project mutation.
- Windows preserves complete staging-file synchronization and exclusive atomic
  publication but cannot promise the same directory-entry crash durability when
  its directory handle rejects synchronization with the narrow unsupported-
  capability codes. A crash can therefore resurrect a published or released
  directory entry, requiring inspection and targeted removal because automatic
  recovery remains unsupported there.
- Protected operations become fail-fast under contention, including
  coordinated readers started while a writer owns the lock.
- Coordinated readers do not hold a read lease: they reject a writer already
  present, but a writer can start after their single entry check. This scoped
  asymmetry is documented rather than represented as a snapshot guarantee.
- Nested operations require correct `AsyncLocalStorage` propagation; context
  loss is visible as `EVIDENCE_WRITER_CONTEXT_LOST` instead of becoming a
  silent bypass.
- Abrupt termination can leave a lock. Same-host recovery is automatic only
  when identity and liveness are conclusive; other cases require documented
  inspection and targeted removal.
- The final identity check and `unlink` are separate POSIX operations because
  Node.js has no portable unlink-if-inode primitive. The device/inode and
  transaction recheck minimizes replacement risk but cannot mathematically
  eliminate a concurrent-recovery TOCTOU window; tests cover deterministic
  replacement before the final check, and documentation requires operators not
  to run concurrent recovery commands.
- Abrupt termination before canonical publication can leave an ignored
  `.writer-lock.<transactionId>.json` staging file. It is not ownership state
  and is not automatically removed because another process cannot prove that
  publication is no longer in flight.
- Configured child commands do not inherit owner context. Recursive musubix3
  writer/reader invocation against the same root fails fast and must be removed
  from the configured command chain.
- Writer-lock and merge-journal diagnostics remain distinct, with lock
  contention taking precedence and unlock recovery preceding merge recovery.
- Concurrency correctness depends on deterministic multi-process tests and
  injected probe outcomes; the requirements' formal consistency remains
  unsupported and is not claimed as behavioral proof.
