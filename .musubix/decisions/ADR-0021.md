# ADR-0021: Feature-domain-scoped approval manifests

## Context
ADR-0002 bound `requirements`/`design` approval to every feature's artifacts repository-wide, by design, so a single manifest hash proves the whole repository was reviewed together. Issue #19 reports that this does not scale once a `.musubix` repository hosts many independently-owned features (for example one per microservice): any single feature's requirement edit staleness-invalidates every other feature's approval, forcing reviewers to either re-review unrelated work or rubber-stamp without reading it. A per-feature (1:1) scope was considered but rejected as too fine-grained for related features that are reviewed together by the same team; a coarser, named grouping ("domain") that maps many features to one approval scope is the requested middle ground.

## Decision
Add an optional `approval.domains: { name, featureGlobs }[]` config array, matched against bare feature **slugs** (not paths). When non-empty ("configured"), `requirements`/`design` stage manifests and evidence become per-domain: each domain's manifest hash is computed over `{ stage, domain: name, features: sortedOwnedSlugs, artifacts }` — the domain's name and resolved owned-feature-slug set are part of the hashed payload, not merely context alongside it, so reassigning a feature between domains changes both affected domains' hashes even if no file content changed. Evidence is stored at `.musubix/evidence/approvals/domains/<domain>/<stage>.json`, distinct per domain and distinct from the pre-existing repo-wide path, whose formula and path are left byte-for-byte unchanged. Every feature directory must resolve to exactly one domain (fail closed on ambiguity or omission) and every domain must currently match at least one feature directory (fail closed on vacuous domains). Recording a domain's `design` approval requires only that same domain's current `requirements` approval (not every domain's), preserving independent per-domain review cadence; recording the repo-wide `release` stage requires every configured domain's `requirements` and `design` approval to be current, preserving ADR-0002's staged guarantee at the point where the whole repository ships. `gate --feature <name>`, `design validate`, and `tdd red` gate on only the owning domain, with a fail-closed target-resolution step (reject a target outside every domain, or an unknown/ambiguous requirement ID, before evaluating any approval). The `release` stage is explicitly kept repository-wide and immune to `--domain` in every case — this repository's own risk profile (a small, single-team OSS project, not the many-service enterprise case the issue describes) does not need release-stage scoping, and scoping the final release gate would let a subset of domains approve a release the others never reviewed. When `approval.domains` is omitted or empty, every command is byte-identical to v0.1.16 (REQ-APPROVAL-DOMAIN-SCOPING-024); domain scoping is a pure additive extension of ADR-0002's manifest model, not a replacement.

## Rejected alternatives
- Per-feature (1:1) approval scoping: rejected as too fine-grained — related features reviewed together by one team would need N separate approvals for a single coherent review, and the issue's own reproduction explicitly asks for a coarser "domain"/"service group" grain, not per-feature.
- Splitting into multiple `.musubix` repositories per domain: the issue names this as a valid alternative for large organizations, but it is an operational/organizational choice outside musubix3's control, not a code change; this ADR addresses the case where a single repository must still support the grouping.
- Making `release` also domain-scoped: rejected because release is the final human sign-off that the whole repository is fit to ship; splitting it would let one domain's approver believe a release shipped without reviewing domains they don't own, silently narrowing the guarantee ADR-0002 established. The user explicitly confirmed release should stay out of scope for this change.
- Treating a domain rename as producing `stale` evidence for the new name: rejected because evidence is keyed by domain name, and no evidence file exists yet at a new name's path; reporting `stale` would imply prior evidence was found and found to differ, which is false. `missing` is the accurate status; a renamed domain is treated as removing the old name and adding a new one, with no dedicated migration command (matching the general principle that renames are additive/removal pairs elsewhere in the config, for example architecture rule names).
- Allowing zero-match domains to persist as an approvable-but-empty state: rejected because an empty domain can never gate anything meaningfully and its "approved" status would be vacuously true forever, silently weakening the model; failing closed at config-load time surfaces the misconfiguration immediately instead of producing a permanently-green scope that is never actually reviewing anything.

## Consequences
Reviewers approve only the domain(s) whose artifacts changed, restoring the intended cost/rigor tradeoff for large multi-feature repositories. The blast radius of `constitution.md` changes (repository-wide invalidation of every domain) is unchanged and intentional, since the constitution is explicitly cross-cutting policy. Projects that adopt domains take on additional configuration surface (glob coverage/ambiguity must be kept exact as features are added or moved) and additional evidence file paths, and a domain rename requires a fresh approval for the new name with no automatic carry-over from the old one. Domain scoping does not reduce the number of approval evidence files a large repository must track — it instead trades one repo-wide file for N domain-scoped files, which is precisely the scaling relief the issue requested.
