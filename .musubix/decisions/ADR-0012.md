# ADR-0012: Suppress blocking TDD diagnostics for mechanically-superseded cycles without a human-approved migration step

## Context

`runTddValidate()` raises `TDD_RED_MISSING`, `TDD_GREEN_MISSING`, and the
Red-side `TDD_LEGACY_OR_UNSCOPED_EVIDENCE` for every recorded cycle of a test
ID, including a cycle superseded by a later, fully valid Red-Green cycle for
the same test ID (GitHub Issue #11). This permanently blocks `gate` for that
test ID even after later valid evidence exists, with no supported remedy
short of discarding all recorded TDD evidence project-wide. `ADR-0009`
previously required a new, explicit, human-approved `migrate` chain phase to
bring stored evidence back in sync after a retroactive fingerprint-algorithm
change, because that reconciliation required comparing a legacy computation
to a corrected one and could not be verified without recomputing history.

## Decision

Scope `TDD_RED_MISSING`, `TDD_GREEN_MISSING`, and the Red-side
`TDD_LEGACY_OR_UNSCOPED_EVIDENCE` diagnostics to non-superseded cycles: a
cycle for test ID T is superseded, and therefore exempt from these three
diagnostics, exactly when a later-recorded cycle for the same T exists whose
Red and Green phases are both present and valid. This uses the already
line-of-record `order` field and each cycle's own recorded `valid` phase
status — a purely mechanical, deterministic comparison requiring no
recomputation of historical evidence and no human judgment. No new chain
phase, CLI operation, or approver is introduced; every other check (chain
hash, order/sequence, duration validity, and `TDD_TEST_STALE`) continues to
apply to every recorded cycle unchanged.

## Rejected alternatives

- **Require a `tdd migrate`-style explicit human-approved operation before
  suppressing these diagnostics**, mirroring `ADR-0009`. Rejected: that
  precedent exists because reconciling a retroactive algorithm change
  requires comparing a legacy recomputation against a corrected one, which
  can silently mask real drift if done incorrectly. Determining whether a
  cycle is superseded requires no recomputation and no drift comparison —
  it is a direct, verifiable read of already-recorded order and validity
  fields, so requiring a separate approved operation would add process
  overhead without adding any integrity guarantee.
- **Delete or archive superseded cycles from the evidence file.** Rejected:
  mutating or removing previously recorded, hash-chain-linked evidence
  breaks the append-only chain-hash integrity guarantee the evidence format
  exists to provide, and destroys the historical record of the earlier
  attempt.
- **Leave the behavior unchanged and document a workaround.** Rejected: the
  only documented workaround is to discard all recorded TDD evidence for the
  entire project and re-record every cycle, which is disproportionate to a
  single test ID's superseded attempt and was never backed by an explicit
  requirement for this specific behavior.

## Consequences

- A test ID with an early incomplete or invalid cycle followed by a later
  fully valid cycle no longer permanently blocks `gate`; only the latest
  cycle (or an earlier cycle with no fully valid successor) is diagnosed.
- Chain-hash, order, duration, and staleness checks are unaffected for every
  cycle, superseded or not; no evidence is deleted, mutated, or requires
  human approval to reconcile.
