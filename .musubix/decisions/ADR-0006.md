# ADR-0006: Nested MUSUBIX3 workspaces are scan boundaries

## Context

`graph index`/`trace build` walk every file under the project root except a
fixed exclusion set (`.git`, `node_modules`, `dist`, `build`, `coverage`,
`.test-work`, `.next`, `vendor`, `__pycache__`, language build caches, and
`.musubix/cache`/`.musubix/evidence`). When a nested directory is itself an
independent MUSUBIX3 workspace (it contains its own `.musubix` directory), the
ancestor's scan still reads its `@id`/`@implements`/`@verifies` source
annotations. Those IDs are registered only in the nested workspace's own
`.musubix/features/**/requirements.md` and `design.md`, not the ancestor's, so
the ancestor's `trace` check reports them as dangling, and its `test-identities`
check reports their tests as unreported, even though the nested workspace is
independently gate-verified on its own.

## Decision

An ancestor's `graph`/`trace` file scan excludes any descendant directory that
itself contains a `.musubix` directory, treating it as a separate workspace's
scan boundary. The scan root itself is never excluded by this rule, even if it
also contains `.musubix` (a workspace always scans itself).

## Consequences

- Nested example/demo workspaces (e.g. `examples/*/`) no longer pollute an
  ancestor repository's trace/test-identity evidence.
- Running the same commands with the nested directory as `--root` is
  unaffected; it continues to scan and gate itself independently.
- A workspace that wants its nested code registered in the ancestor's own
  trace graph must not create its own `.musubix` directory; this is an
  explicit, visible opt-out rather than an implicit one.
