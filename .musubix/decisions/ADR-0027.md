# ADR-0027: Non-blocking, consecutive-pair `recordedAt` inversion diagnostic

## Status
Accepted

## Context
`ChangePhaseEvidence` (`packages/analysis/src/change-evidence.ts`) stores
both a verified, repository-wide monotonic `order` field (assigned by
`appendEvidenceOrder`, `packages/analysis/src/order.ts`) and an
independently captured `recordedAt` wall-clock timestamp
(`new Date().toISOString()`, set in `recordChangePhase`,
`packages/analysis/src/change.ts`). No existing diagnostic
(`CHANGE_ORDER_MISMATCH`, `CHANGE_PHASE_ORDER`,
`CHANGE_ORDER_MIGRATION_REQUIRED`) ever inspects `recordedAt`; it can drift
out of step with `order` (for example under system clock adjustment/skew
between sequential invocations) with no warning (GitHub Issue #22).

## Decision
Add `CHANGE_RECORDEDAT_OUT_OF_ORDER` as a `severity: 'warning'` diagnostic,
computed by sorting each change's valid entries (integer, de-duplicated
`order`; canonical-ISO `recordedAt`) ascending by `order` and comparing only
consecutive pairs in that sorted sequence, emitting one diagnostic per
inverted consecutive pair.

## Rejected alternatives
- **`severity: 'error'`.** Would retroactively fail `gate` for
  already-recorded, otherwise-valid historical evidence the moment this
  feature ships, purely over a wall-clock artifact that never governed
  correctness. `order` (already `error`-enforced via
  `CHANGE_ORDER_MISMATCH`/`CHANGE_PHASE_ORDER`) remains the sole
  correctness-bearing field; `recordedAt` is diagnostic-only.
- **All-pairs (O(n²)) comparison instead of consecutive-pair comparison
  after sorting.** Every inversion detectable by an all-pairs scan is
  already implied by at least one inverted consecutive pair once entries
  are sorted by `order`; reporting every non-adjacent pair as well would
  produce redundant, harder-to-act-on duplicate warnings for what is
  functionally the same underlying gap.
- **A separate CLI subcommand (e.g. `change-record inspect-timestamps`)
  instead of a `gate`/`validateChangeEvidence` diagnostic.** This would
  fragment `change-record` diagnostics across two reporting surfaces
  (`gate --json` vs. a new command) for no functional benefit; every other
  `change`-scoped diagnostic already reports through
  `validateChangeEvidence`/`gate`.
- **Extending `trace check --strict` to also run this check.** `trace
  check` (`checkTrace`, `packages/analysis/src/trace.ts`) validates
  requirement/design/code/test traceability coverage and never loads
  change chronology evidence; wiring change-evidence validation into it
  would be an unrelated, unreviewed scope expansion beyond this feature's
  requirements.

## Consequences
- A caller relying on `gate --json`/the human-readable report is now
  warned, per change, whenever `recordedAt` disagrees with the verified
  `order` sequence, without any existing evidence being retroactively
  failed.
- The diagnostic is deliberately inert with respect to `gate`'s pass/fail
  computation for the `change` check; a repository can freely accumulate
  these warnings without needing a waiver mechanism (unlike the `error`
  severity diagnostics ADR-0025/ADR-0026 already cover).
- Future extension to a stricter (`error`) mode, if ever desired, is a
  separate, explicitly reviewed change, not an implicit consequence of this
  one.
