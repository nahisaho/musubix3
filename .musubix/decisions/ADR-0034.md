# ADR-0034: Keep the latest Quality checkpoint authoritative with ordinal history

## Status
Accepted

## Context
Change chronology originally stored one Quality checkpoint in
`change.phases.quality`. Requirement-scoped corrective batches can legitimately
be recorded after that checkpoint, but the one-shot Quality slot cannot move
past their Green orders. Rewriting the checkpoint would erase audit history,
while waiving `CHANGE_PHASE_ORDER` would weaken a structural invariant.

The monotonic evidence order log is append-only and identifies records by
change, phase, and optional scope. Existing repositories already contain the
first Quality record under phase identity `quality`, so its identity and hash
cannot change.

## Decision
Represent a Quality lineage with the newest checkpoint in
`change.phases.quality` and older checkpoints in optional `qualityHistory`,
ordered oldest to newest. The first order identity remains `quality`; later
identities are `quality:2`, `quality:3`, and so on.

On refresh, move the prior authoritative checkpoint into history without
changing its payload, record the new checkpoint as authoritative, and upgrade
the repository-wide change evidence document to schema version 2. Schema
version 1 remains valid only for evidence without history.

All validation and merge paths resolve Quality through shared ordinal helpers.
The authoritative checkpoint must follow every recorded Green. Retained
checkpoints remain auditable but do not create phase-order failures for later
corrective batches. Merge treats one lineage as compatible only when it is an
exact ordinal prefix of the other, then preserves the longer lineage while
using the existing sequence-remapping and hash-chain rebuild contract.

Quality refresh commits `order.json` and `changes.json` through a dedicated
recoverable two-file transaction. It reuses the evidence-merge transaction
semantics but has a distinct journal path, journal kind, and target inventory.
A prepared transaction rolls back and a committed transaction rolls forward;
all evidence readers and writers refuse while the refresh journal is published
except `change quality-recover`. Merge and refresh publication preconditions
prevent journal coexistence; observed coexistence fails unsafe. Refresh never
adopts an order identity without its journal-bound checkpoint payload.

## Rejected alternatives
- **Make `CHANGE_PHASE_ORDER` waivable.** This would turn structural chronology
  into a policy exception and would not prove a new quality run occurred.
- **Overwrite the single Quality checkpoint.** This loses the reviewed earlier
  checkpoint and breaks append-only auditability.
- **Store the newest checkpoint only in history.** Existing readers of
  `phases.quality` would continue to observe the stale checkpoint.
- **Use timestamps or array position without order identities.** Wall-clock
  order is not authoritative, and merge sequence remapping requires stable
  logical identities.
- **Permit arbitrary divergent lineage merge.** Two different checkpoints at
  the same ordinal are conflicting review histories and cannot be reconciled
  deterministically.

## Consequences
- Existing version-1 evidence remains valid until the first refresh.
- Older binaries reject version-2 evidence and must be upgraded.
- Quality refresh remains unavailable for another correction using an already
  occupied requirement-subset batch key; that correction requires a distinct
  reviewed staged change.
- Merge and order validation gain Quality-specific lineage handling.
- Prior Quality checkpoints remain visible for audit and recordedAt warnings,
  while the newest checkpoint controls readiness.
