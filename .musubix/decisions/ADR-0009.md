# ADR-0009: Migrate stored TDD fingerprints via an explicit, approved, append-only chain record — never by fabricated Red/Green or in-place mutation

## Context

`ADR-0008` corrected `testFingerprint()`'s AST scoping. That correction is
retroactive: every already-recorded cycle for a nested test now computes a
different fingerprint than what is stored, even when the test's own
declaration text never changed (see `ADR-0008` Consequences). Two paths were
considered to bring stored evidence back in sync with the corrected
algorithm.

## Decision

Add a new, distinct, append-only chain phase, `migrate`, recorded only by an
explicit CLI operation (`tdd migrate <test-id> --approver <name> --confirm`)
that:
1. Recomputes the *superseded* algorithm (kept as `legacyTestFingerprint`)
   against the test's *current* source text.
2. Compares that to the cycle's currently effective stored fingerprint.
3. Appends a chain-linked `migrate` record (from/to fingerprint, approver,
   timestamp) only if they match — proving no real content drift occurred,
   only the computation method changed — and refuses otherwise.

`TDD_TEST_STALE` detection is updated to treat a cycle's latest valid
`migrate` record's `toFingerprint` as its effective stored fingerprint.

## Rejected alternatives

- **Silently rewrite `testFingerprint` in place on the existing Green/
  Refactor phase evidence object.** Rejected: every phase evidence object is
  already hash-linked into the append-only chain
  (`TddChainRecord.phaseEvidenceSha256`); mutating a recorded phase's fields
  would invalidate that hash and is exactly the "hand-editing evidence" the
  system's own diagnostics (`TDD_LEGACY_OR_UNSCOPED_EVIDENCE`) explicitly
  say is unsupported.
- **Require operators to run a fresh `tdd red`/`tdd green` cycle for every
  affected test.** Rejected: `runTddPhase` requires Red's stored
  `testFingerprint` to equal the currently live-computed value before
  accepting Green/Refactor — which is exactly the mismatch this migration
  exists to resolve, so this path is mechanically blocked, not merely
  undesirable. It would also require fabricating a failing Red run for
  tests whose behavior never regressed, misrepresenting the change history
  of unrelated features.
- **Add a blanket "rebuild all fingerprints" batch command with no
  per-cycle drift check.** Rejected: would also silently accept and paper
  over genuine drift (a test whose body really did change without a new
  cycle), defeating the purpose of `TDD_TEST_STALE` entirely. The per-cycle
  legacy-recomputation comparison is the safeguard that keeps this an
  algorithm migration, not a bypass.
- **Version the fingerprint algorithm and store an algorithm version tag per
  cycle instead of a migration record.** Rejected: still requires an
  explicit, auditable, human-approved transition step to move a cycle from
  one version to the next; a bare version tag with no comparison check
  would let stale evidence pass silently on every future algorithm bump,
  not just this one.

## Consequences

- Every cycle migrated this way keeps its original Red/Green/Refactor
  evidence completely unchanged and auditable; only a new, additive chain
  record documents the fingerprint-algorithm transition, with an explicit
  human approver named in the evidence.
- A migration is refused, not silently skipped, when the legacy
  recomputation does not match — real drift still requires a genuine
  Red/Green cycle, preserving the integrity guarantee `TDD_TEST_STALE`
  exists to enforce.
- `legacyTestFingerprint` must be retained in source even after `ADR-0008`
  ships, solely to make future migrations of old evidence possible; it must
  never be used for any live (non-migration) fingerprint computation.
