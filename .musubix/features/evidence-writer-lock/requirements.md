# Fail-fast evidence writer coordination

Source: GitHub Issue #28 phase 3. Concurrent gate, TDD, trace, graph, workflow,
approval, and related commands can otherwise clear reports, append order
records, or replace generated evidence while another command is still reading
or validating the same project state.

## REQ-EVIDENCE-WRITER-LOCK-001: Acquire one exclusive project evidence-writer lock
Priority: must
Type: functional
Pattern: event-driven
Statement: When a musubix3 operation is classified as a writer, the system shall atomically acquire one project-wide evidence-writer lock before reading project state that informs the mutation.
Acceptance: The canonical lock path is `<realpath(project-root)>/.musubix/evidence/.writer-lock.json`; path aliases that resolve to the same project share one lock, while different real project roots use independent locks. Every operation that resolves a project root for lock coordination uses the same operating-system-native realpath resolver and therefore the same canonical-root string, including acquisition, in-process lease-map lookup, asynchronous nested ownership checks, coordinated-reader entry checks, and incoming-root coordination; that resolver is injectable so a test can deterministically prove that acquisition and nested guards consume one resolved identity. Owner metadata and the on-disk lock path record exactly this resolved string, with no case folding or other normalization applied afterward. The system publishes complete owner metadata without a visible zero-length or partial-lock state by using a filesystem primitive that both refuses replacement and makes the fully written metadata atomically visible. The lock exists before clearing a configured report, executing a configured command that can write a report, appending `order.json`, or replacing a trace/cache/evidence file. Lock publication and cleanup, including creation and removal of an otherwise empty `.musubix/evidence` container, are coordination state rather than project-artifact side effects; except for the named exempt operations below, evidence, trace, cache, report, source, configuration, and installed-file changes are project-artifact side effects. CLI writer leaves and modes are `init` and its `install` alias except dry-run; `upgrade` except dry-run; `gate`; `evidence refresh`; `evidence merge` except dry-run, including recover; `tdd red|green|refactor|migrate|void`; `change-record` except dry-run; `change waiver record`; `workflow-record`; `workflow-verify`; `workflow waiver record|record-all`; `approval record`; `trace build`; `graph index|gate`; `knowledge build`; and `formal check|generate`. Every exported analysis API with a project-artifact side effect, including order append and mutation, performance, or model-correspondence evidence generation, is also a writer. Any other operation with a project-artifact side effect that is not a named exemption is also a writer. Each writer acquires the project lock before any read that informs a later write or before any project-artifact side effect, whichever occurs first. Coordinated-reader CLI leaves and modes are every resolved dry-run mode that performs no project-artifact side effect, including init/install, upgrade, change-record, and evidence merge dry-run; `status`; `approval prepare|validate`; `design validate|c4`; `trace check|impact`; `graph impact|cycles`; `knowledge query`; `mutation validate`; `model-correspondence validate`; `attestation payload|verify`; and `tdd validate`; any other operation that reads evidence, trace, generated cache, or a configured report without writing is also a coordinated reader. Each coordinated reader checks the project lock before its first coordinated read and fails fast when an unrelated owner exists without acquiring or removing the lock. Named exempt operations are help/version output; the `plugin-install` leaf that delegates outside the project; `requirements validate|scaffold`; `constitution validate`; `design scaffold`; `formal doctor`; `config lint|scaffold`; `mutation doctor|identity`; `workflow-sanitize` writing only its explicitly selected output; `attestation oidc-audience`; and `evidence unlock --recover`. Other operations are exempt only when they perform neither a coordinated read nor a project-artifact side effect. Exempt operations do not require an owner lock, and recovery follows REQ-EVIDENCE-WRITER-LOCK-004. An exempt operation that accepts an output path resolves it before writing and rejects any path under `.musubix/evidence/**`, `.musubix/cache/**`, `.musubix/features/*/trace.json`, or a configured `tddReport`, `testReport`, or `mutationReport` path with nonzero `EVIDENCE_PROTECTED_OUTPUT_REJECTED`; it never uses exemption to bypass protected output coordination. Explicitly named operations take precedence over the writer/reader catch-alls, and a mode-dependent operation is classified after resolving its options. Option-validation failures occur before scope establishment, acquire no lock, and are excluded from resolved-mode enumeration. CLI registry classification is for the primary project root; an operation may coordinate a secondary root as a reader when another requirement explicitly requires it. An exhaustive registry test enumerates the leaf actions and valid option modes registered by `createProgram`, counting a mode-dependent leaf once per valid resolved coordination mode, and proves each is classified exactly once. With a foreign lock held, `status` exits with `EVIDENCE_WRITER_LOCKED`; `requirements validate` and `workflow-sanitize` to an unprotected temporary output retain their specified lock-independent outcomes; `evidence unlock --recover` reports `EVIDENCE_WRITER_LOCKED` only where the platform supports automatic recovery inspection and reports `EVIDENCE_WRITER_LOCK_RECOVERY_UNSAFE` without mutation where the required recovery probes are unsupported, because platform fingerprint support is established before liveness classification; and `graph gate` owns the writer lock before replacing `.musubix/cache/codegraph.json`. A separate exhaustive analysis-entry registry proves that every exported analysis API with a project-artifact side effect establishes a writer scope. The lock file and its private publication temporaries are ignored by Git and excluded from approval manifests, attestations, trace inputs, evidence hashes, and generated-artifact scans. Platform durability is fail-closed except exactly as narrowly permitted for Windows below. A writer must successfully sync the complete staging file before atomic publication. After publication, after verified release unlink, and after verified recovery removal, every non-Windows platform must successfully sync the containing evidence directory. On Windows only, `EPERM`, `EINVAL`, or `ENOTSUP` from syncing an already-open directory handle is classified as unsupported directory synchronization and does not invalidate an otherwise successful staging-file sync plus atomic hard-link publication or verified release unlink. No file-handle sync failure, open/close failure, atomic-link failure, metadata verification failure, or other directory-sync error is suppressed. Platform classification and evidence-directory synchronization are injectable in tests so every suppressed Windows publication and release outcome and every non-suppressed outcome is deterministic. The Windows Core matrix completes without `EVIDENCE_WRITER_LOCK_ACQUIRE_FAILED` or `EVIDENCE_WRITER_LOCK_RELEASE_FAILED` caused solely by unsupported directory synchronization. README.md, README-ja.md, and command help document the Windows directory-entry durability boundary and its inspection-only automatic-recovery behavior.

## REQ-EVIDENCE-WRITER-LOCK-002: Fail a contending operation immediately
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If an unrelated operation already owns the evidence-writer lock, then the system shall reject a contending writer or coordinated reader immediately without waiting or performing project side effects.
Acceptance: The rejected command exits nonzero with `EVIDENCE_WRITER_LOCKED`, does not clear reports, execute configured commands, append order records, or modify evidence/trace/cache targets, and reports the lock path plus the owner's canonical root, command, process ID, hostname, boot/session identity, process-start identity, process-namespace identity, acquisition time, and transaction ID, using explicit unknown values for unreadable fields. Once exclusive publication or an entry check has established contention through an existing canonical lock, unreadable, malformed, or subsequently vanished owner metadata causes at most one immediate re-read and then conservative `EVIDENCE_WRITER_LOCKED` with unknown unavailable fields rather than retrying acquisition; acquisition and contention handling never remove malformed persistent metadata, `evidence unlock --recover` refuses it under REQ-EVIDENCE-WRITER-LOCK-004, and only documented manual inspection and targeted removal can clear it. Before contention is established, a non-contention coordination failure such as `EACCES`, `EROFS`, unsupported atomic publication, exhausted storage, or inability to inspect the canonical lock exits with `EVIDENCE_WRITER_LOCK_ACQUIRE_FAILED`, preserves the underlying cause, and performs no project-artifact side effects. There is no polling loop, timeout queue, daemon, or implicit lock stealing. A deterministic two-process barrier test against one unlocked root produces exactly one successful owner and exactly one `EVIDENCE_WRITER_LOCKED` rejection whose available owner fields match the winner.

## REQ-EVIDENCE-WRITER-LOCK-003: Permit owner-scoped nested evidence access
Priority: must
Type: functional
Pattern: state-driven
Statement: While an operation owns the evidence-writer lock, the system shall permit that operation's nested evidence reads, writes, and internal sub-operations while rejecting unrelated processes.
Acceptance: Lock ownership is propagated through asynchronous analysis calls by an unforgeable transaction token held in Node.js `AsyncLocalStorage`. Every nested guard uses the canonical-root lookup identity defined by REQ-EVIDENCE-WRITER-LOCK-001. Reentrant and concurrent sibling acquisitions for the same canonical root and token reuse the existing filesystem lock, maintain a reference count, and release it only when that count reaches zero. A nested writer operation for a different root acquires that root's independent lock, except that evidence merge coordinates its incoming root only as the REQ-EVIDENCE-WRITER-LOCK-005 reader and never acquires an incoming writer lock. Shared evidence, trace, cache, report, order, workflow, and merge-journal I/O guards accept only the matching root and token; a coordinated-reader guard for the same canonical root succeeds inside the active owner context, while merely running in the same process without that context does not bypass the lock. If an owner-required internal path loses its async context, it fails closed before I/O with `EVIDENCE_WRITER_CONTEXT_LOST`. Worker threads and child processes do not inherit ownership and must coordinate as unrelated operations unless the parent keeps all protected I/O in the owner context.

## REQ-EVIDENCE-WRITER-LOCK-004: Release safely and recover an abandoned lock explicitly
Priority: must
Type: functional
Pattern: event-driven
Statement: When lock release or explicit abandoned-lock recovery is requested, the system shall remove only a conclusively identified evidence-writer lock.
Acceptance: Normal success and handled failure remove the lock in `finally` only when the REQ-EVIDENCE-WRITER-LOCK-003 reference count reaches zero and only after re-reading complete metadata and verifying that the canonical root, on-disk transaction ID, and observed device/inode identity match the owner context immediately before unlink. Absent, unreadable, malformed, or mismatched release-time metadata fails closed without deleting any lock and reports `EVIDENCE_WRITER_LOCK_RELEASE_FAILED`, the exact lock path, and documented manual inspection and targeted-removal guidance; if project work succeeded the command exits nonzero with that release error, while if project work already failed its original error remains primary and the release error is attached as structured secondary context. Release-time metadata reads and device/inode observations are injectable in tests so refcount-zero release, mismatch after successful work, and mismatch after failed work are deterministic. Owner metadata contains the canonical root, command, PID, hostname, acquisition time, transaction ID, and a platform process fingerprint containing boot/session identity, process-start identity, and process-namespace identity. Abrupt process termination may leave the lock. On Linux the system provides boot-ID, process-start, and PID-namespace probes, and `evidence unlock --recover` removes a well-formed same-host lock when those recorded identities match the current environment, the recorded PID is demonstrably not alive in the recorded namespace, and final metadata plus device/inode rechecks still identify the same transaction and file. On a platform that cannot provide all required probes, automatic removal is unsupported and recovery always fails without mutation as `EVIDENCE_WRITER_LOCK_RECOVERY_UNSAFE` with inspection guidance. With no lock recovery succeeds idempotently as `nothing-to-recover`; with a matching live owner it fails with `EVIDENCE_WRITER_LOCKED`; with PID reuse, a different hostname or boot/session/process-namespace identity, unavailable required fingerprint data, malformed metadata, a changed transaction ID, changed device/inode identity, or indeterminate liveness it fails without mutation as `EVIDENCE_WRITER_LOCK_RECOVERY_UNSAFE` and prints the complete readable owner metadata plus manual inspection and targeted-removal guidance. Normal commands never reclaim a stale lock automatically, and the recovery command has no force or implicit cross-host mode. Host identity, process-fingerprint, process-liveness, release metadata-read, and device/inode probes are injectable in tests so successful dead-owner recovery and live, reused, different-host, unsupported-platform, indeterminate, and release-failure outcomes are deterministic.

## REQ-EVIDENCE-WRITER-LOCK-005: Keep transaction recovery and operator guidance deterministic
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The system shall coordinate the general writer lock with existing evidence-merge recovery and document the concurrency contract.
Acceptance: Automated integration tests verify these five coordination and non-interference rules with zero cross-deletion or state-reinterpretation failures: (1) a normal evidence merge checks/acquires the destination project's general writer lock before inspecting merge-journal state, then uses the existing journal transaction beneath that lock; (2) `evidence merge --recover` checks/acquires the destination project's general writer lock before inspecting or mutating the merge journal, a lock conflict reports only `EVIDENCE_WRITER_LOCKED`, and a pending journal owned by the successful lock holder reports or resolves `EVIDENCE_MERGE_RECOVERY_REQUIRED` under existing merge rules; (3) `evidence unlock --recover` inspects and may remove only the writer lock and never reads, deletes, or reinterprets a merge journal; (4) when both an abandoned writer lock and a pending merge journal exist, `evidence merge --recover` fails with `EVIDENCE_WRITER_LOCKED` while leaving the merge-journal file byte-identical, then after successful `evidence unlock --recover`, `evidence merge --recover` handles that unchanged journal under the existing merge rules; and (5) normal and dry-run merge both coordinate the destination root before the canonical incoming root and before reading incoming evidence, normal merge acquires the destination writer lock while dry-run merge performs a destination coordinated-reader check, both report the destination owner when both roots are contended, both fail with `EVIDENCE_WRITER_LOCKED` before destination or incoming project-artifact side effects when an unrelated writer owns the incoming root, and neither locks the incoming root for writing or modifies it. Writer-lock checks execute before the existing merge-ready guard on every merge entry path. Recovery never represents a lock-only state as a merge transaction or a journal-only state as a writer lock. JSON and human CLI output use the stable codes and owner fields from these requirements. README.md, README-ja.md, and command help document command classification, fail-fast behavior, the lock path, stale-lock and merge-recovery ordering, unsafe cross-host/malformed/PID-reuse handling, targeted manual remediation, filesystem atomicity assumptions, the coordinated-reader non-snapshot limitation, abandoned staging-file semantics, and that commands run directly outside musubix3 are not coordinated; `.gitignore` ignores the canonical lock, its transaction-qualified publication temporaries, and merge transaction staging files.
