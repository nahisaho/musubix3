# Design / 設計

## DES-APPROVAL-DOMAIN-SCOPING-001: Domain configuration schema and validation
Responsibilities: Parse an optional `approval.domains` array of `{ name, featureGlobs }` entries in `config.ts`; reject entries whose `name` is not lowercase kebab-case, is one of the reserved words `requirements`/`design`/`release`, is a duplicate, or has an empty `featureGlobs` array; additionally reject any individual glob string in `featureGlobs` that is empty or contains a `/` (slugs are single path segments, so a slash can never match one — rejecting it at parse time, rather than silently accepting a pattern that can only ever contribute zero matches, is what makes DES-APPROVAL-DOMAIN-SCOPING-002's zero-match domain check a reliable, complete coverage guarantee rather than one that only catches a domain whose *every* pattern is dead); treat an omitted or `[]` value for `domains` as "not configured".
Interfaces: `DomainConfig { name: string; featureGlobs: string[] }`; `ApprovalConfig { mode; domains: DomainConfig[] }`; parsing extends the existing `rawApproval` block in `parseConfig`.
Constraints: Config parsing is synchronous and pure (no filesystem access) so it cannot yet check feature-directory coverage; that check runs after `files(root)` is available (DES-APPROVAL-DOMAIN-SCOPING-002). An empty/omitted `domains` array must parse to a value that every downstream function treats identically to v0.1.16 (no `domains` key at all): specifically, every hash-bearing manifest computed by DES-APPROVAL-DOMAIN-SCOPING-003 in this state must use the exact pre-existing `digest(JSON.stringify({ stage, artifacts }))` formula, byte-for-byte, so a config that merely adds `approval: { domains: [] }` (or omits the key) never changes any existing manifest hash.
Requirements: REQ-APPROVAL-DOMAIN-SCOPING-001
ADRs: ADR-0021
Depends-On: none

## DES-APPROVAL-DOMAIN-SCOPING-002: Domain resolution service
Responsibilities: Given the parsed `approval.domains` and the current repository's feature slugs, compute the resolved domain membership by matching each `featureGlobs` pattern with the existing `matchGlob` helper (`graph.ts`) directly against the **bare feature slug** (the `<slug>` segment of `.musubix/features/<slug>/`, no leading path, no trailing slash) — for example `inventory-*` matches slug `inventory-service`; a bare `inventory-service` matches only that exact slug; `**`/`*` match every slug. A "current feature slug" is defined identically to every other existing consumer of feature directories in this codebase (`gate.ts`'s `featureDir` existence check, `main.ts`'s `designResult` requirement/design ID collection): the sorted, de-duplicated set of `<slug>` values captured from every path in `files(root)` matching `^\.musubix/features/([^/]+)/requirements\.md$` — i.e., a feature "exists" for domain-resolution purposes exactly when it already exists for every other approval/trace/design purpose (has a `requirements.md`). This component introduces no new directory-scanning mechanism; a `.musubix/features/<slug>/` directory containing only non-canonical files and no `requirements.md` is already invisible to every existing v0.1.16 command and remains so here. Reject the whole configuration (throwing, matching the existing `parseConfig`/`loadConfig` error-on-invalid-config convention) if any feature slug matches zero or more than one domain's `featureGlobs`, or if any domain matches zero feature slugs.
Interfaces: `resolveDomains(root, config): Promise<{ name: string; features: string[] }[]>` — `features` is the sorted list of bare feature slugs owned by that domain (not paths); `domainOwning(resolved, slug): string | null`.
Constraints: Runs once per command invocation against the current feature-slug inventory; never caches across invocations. An ambiguity error names the offending slug and lists every conflicting domain name (sorted); a coverage error names the unassigned slug; a zero-match error names the domain — each is a distinct, deterministic message so a config author is never left guessing which glob is wrong. Matching is against the bare slug (no `/`); any glob containing `/` is already rejected outright at parse time by DES-APPROVAL-DOMAIN-SCOPING-001, so this component never has to reason about a dead-on-arrival pattern hiding behind another pattern that happens to match — every pattern this component evaluates is capable of matching at least one slug in principle.
Requirements: REQ-APPROVAL-DOMAIN-SCOPING-002, REQ-APPROVAL-DOMAIN-SCOPING-003, REQ-APPROVAL-DOMAIN-SCOPING-004
ADRs: ADR-0021
Depends-On: DES-APPROVAL-DOMAIN-SCOPING-001

## DES-APPROVAL-DOMAIN-SCOPING-003: Domain-scoped manifest and evidence service
Responsibilities: Extend `approval.ts` so that, when domains are configured, `requirements`/`design` stage manifests for a given domain are computed from — and cryptographically bind — that domain's **name**, its **resolved sorted owned-feature-slug array**, `constitution.md`, and only the `requirements.md`/`design.md`/referenced `ADR-*.md` files of features currently owned by that domain; evidence is persisted at a path distinct per domain. The repo-wide (non-domain) manifest formula and evidence path are unchanged from v0.1.16 in every case (used for `release` always, and for every stage when domains are not configured).
Interfaces: `ApprovalManifest` gains optional `domain?: string` and `features?: string[]` fields, present only for a domain-scoped manifest. `approvalManifest(root, stage, domain?: string)` returns, for a domain-scoped call, `{ stage, domain, features, artifacts, artifactSha256 }` with `artifactSha256 = digest(JSON.stringify({ stage, domain, features, artifacts }))` — the domain name and resolved feature-slug array are part of the hashed payload, not just carried alongside it, so reassigning a feature between domains (even one with no `requirements.md` of its own) changes both affected domains' hashes. A repo-wide call keeps `artifactSha256 = digest(JSON.stringify({ stage, artifacts }))` unchanged. Evidence path becomes `approvalPath(stage, domain?)`: `.musubix/evidence/approvals/domains/<domain>/<stage>.json` when a domain is given, else the existing `.musubix/evidence/approvals/<stage>.json`. `ApprovalEvidence` schema gains the same optional `domain`/`features` fields, validated identically to the existing fields in `loadApproval`.
Constraints: `constitution.md` remains a bound input for every domain's manifest, so a constitution edit invalidates every domain simultaneously. A domain rename is not a distinct code path: the new name has no evidence file at its path and reports `missing`; the old name's now-orphaned evidence file is never read again once no configured domain matches that name. This component is the **single** place stage-relevant paths and the hash payload are computed for domain mode; every caller in DES-APPROVAL-DOMAIN-SCOPING-004/005/006 must call through it (never recompute independently), which is how REQ-APPROVAL-DOMAIN-SCOPING-023's cross-site consistency is achieved structurally.
Requirements: REQ-APPROVAL-DOMAIN-SCOPING-011, REQ-APPROVAL-DOMAIN-SCOPING-012, REQ-APPROVAL-DOMAIN-SCOPING-013, REQ-APPROVAL-DOMAIN-SCOPING-014, REQ-APPROVAL-DOMAIN-SCOPING-015, REQ-APPROVAL-DOMAIN-SCOPING-023
ADRs: ADR-0021, ADR-0002
Depends-On: DES-APPROVAL-DOMAIN-SCOPING-002

## DES-APPROVAL-DOMAIN-SCOPING-004: Domain-scoped validation result shapes, prerequisite recording, and CLI wiring
Responsibilities: Define four explicit result shapes built on DES-APPROVAL-DOMAIN-SCOPING-003 so every caller (CLI `validate`, `gate --feature`, full `gate`/`status`) requests exactly the scope it needs instead of inferring one from a single ambiguous parameter:
  - **repo-wide** (`validateApprovals(root, config)`, domains not configured): unchanged v0.1.16 flat `{ stages: [requirements, design, release] }`.
  - **full breakdown** (`validateApprovals(root, config)`, domains configured, used by full `gate`/`status` and `approval validate` with no `--domain`): `{ domains: { name, stages: [requirementsForName, designForName] }[], release: ApprovalStageValidation, valid }`, where `valid` is true only when every domain's two stages and `release` are `approved` (REQ-022).
  - **single-domain-only** (`validateApprovalsForDomain(root, config, domain)`, used by `approval validate --domain <name>`): `{ domain: name, stages: [requirementsForName, designForName], valid }` — no `release` entry (REQ-009).
  - **single-domain-plus-release** (`validateApprovalsForFeatureGate(root, config, domain)`, used only inside `gate --feature <name>`'s `approval` check): `{ domain: name, stages: [requirementsForName, designForName], release: ApprovalStageValidation, valid }` — combines D's requirements/design with the repo-wide release status into the one `approval` check entry gate/status already expose (REQ-019/020).
  Add `--domain <name>` to the `approval prepare`, `approval record`, and `approval validate` CLI commands (`main.ts`) and to `recordApproval`/`requireApproval` (`approval-record.ts`, `approval.ts`), enforcing: required for `requirements`/`design` `prepare`/`record` when domains are configured; rejected for those same commands when domains are not configured; rejected outright for `release` regardless of configuration; and, for `validate`, dispatching to **full breakdown** when omitted, **single-domain-only** when a known name is given, and rejected when an unknown name is given. Scope `validateStageArtifacts`/prerequisite checks to the target domain: recording domain D's `design` approval requires only D's current `requirements` approval (not every domain's); recording D's `requirements`/`design` approval validates only D's own artifacts (plus `constitution.md`), never other domains' files. Recording `release` (always repo-wide, never `--domain`) requires, when domains are configured, **every** configured domain's `requirements` and `design` approval to be current, in addition to the existing non-approval gate conditions — preserving ADR-0002's staged guarantee across all domains.
Interfaces: `approval prepare <stage> [--domain <name>]`, `approval record <stage> --approver <name> --artifact-sha256 <hash> --confirm [--domain <name>]`, `approval validate [--domain <name>]`; `recordApproval(root, stage, approver, expectedHash, domain?)`; `requireApproval(root, stage, config, domain?)`.
Constraints: Validation order for every command: reject `--domain` for `release` first (independent of configuration state), then reject/require based on whether `approval.domains` is configured, then (for `validate` only) reject an unknown domain name. All error/listing output enumerates the exact configured domain names from DES-APPROVAL-DOMAIN-SCOPING-002. The four result shapes above are the only ones ever produced; no call site invents a fifth ad hoc shape.
Requirements: REQ-APPROVAL-DOMAIN-SCOPING-005, REQ-APPROVAL-DOMAIN-SCOPING-006, REQ-APPROVAL-DOMAIN-SCOPING-007, REQ-APPROVAL-DOMAIN-SCOPING-008, REQ-APPROVAL-DOMAIN-SCOPING-009, REQ-APPROVAL-DOMAIN-SCOPING-010
ADRs: ADR-0021
Depends-On: DES-APPROVAL-DOMAIN-SCOPING-003

## DES-APPROVAL-DOMAIN-SCOPING-005: Domain-aware prerequisite gates for design validate and TDD Red
Responsibilities: Change the `requireApproval` call sites in `design validate <file>`/`design c4 <file>` (`main.ts`) and `tdd red <test-id> --requirement <req-id>` (`tdd.ts`) so that, when domains are configured, each resolves an owning domain and gates on only that domain's approval, with a fail-closed target-resolution step before any approval check:
  - `design validate <file>`/`design c4 <file>`: canonicalize `<file>` to a portable path relative to `root` and require it to exactly match `^\.musubix/features/([^/]+)/design\.md$`; if it does not match that pattern (any other file, including one merely located inside a domain-owned feature directory), reject as outside every domain (REQ-017) without evaluating any domain's approval. If it matches, look up the captured slug's owning domain via DES-APPROVAL-DOMAIN-SCOPING-002 and gate on that domain's `requirements` approval only (REQ-016).
  - `tdd red <test-id> --requirement <req-id>`: resolve `<req-id>` to its owning feature slug via the same requirement-ID-to-feature lookup `gate.ts` already builds (parsing every `.musubix/features/<slug>/requirements.md`, matching `requirementIds` per slug); if `<req-id>` is not found in exactly one feature's `requirements.md`, reject (unknown or ambiguous requirement ID) before any approval check. Once a unique owning slug is found, look up its owning domain via DES-APPROVAL-DOMAIN-SCOPING-002 and gate on that domain's `design` approval only (REQ-018).
Interfaces: `requireApproval(root, stage, config, domain?)`; a shared `domainForFeatureSlug(resolved, slug): string | null` helper (DES-APPROVAL-DOMAIN-SCOPING-002) used by both call sites; a shared `featureOwningRequirement(root, reqId): Promise<string | null>` helper reused from/aligned with `gate.ts`'s existing per-feature requirement-ID indexing.
Constraints: The "outside every domain" (design validate) and "unknown/ambiguous requirement ID" (TDD Red) rejections are distinct, prior errors that never fall through to a repo-wide or unchecked evaluation. When domains are not configured, both call sites are unchanged from v0.1.16 (`requireApproval(root, stage, config)` with no domain argument, no target-resolution step).
Requirements: REQ-APPROVAL-DOMAIN-SCOPING-016, REQ-APPROVAL-DOMAIN-SCOPING-017, REQ-APPROVAL-DOMAIN-SCOPING-018
ADRs: ADR-0021
Depends-On: DES-APPROVAL-DOMAIN-SCOPING-003, DES-APPROVAL-DOMAIN-SCOPING-004

## DES-APPROVAL-DOMAIN-SCOPING-006: Domain-aware gate/status approval check
Responsibilities: Change `gate.ts`'s `approval` check so that, when domains are configured:
  - `gate --feature <name>` evaluates the `approval` check using DES-APPROVAL-DOMAIN-SCOPING-004's **single-domain-plus-release** shape for the domain owning `<name>`'s feature directory, and — unlike v0.1.16, where `approval` is excluded from the feature-mode aggregate status — **includes** this check's pass/fail in the feature-mode aggregate `status` (removing `approval` from the current `featureScopedCheckNames` exclusion whenever domains are configured), so that domain D's staleness or repo-wide release staleness both make `gate --feature <name>` report non-`pass`, satisfying REQ-020's "identically to a full-repo gate run" requirement. When domains are not configured, `approval` remains excluded from the feature-mode aggregate exactly as in v0.1.16 (no behavior change outside domain mode).
  - A full-repo `gate`/`status` run (no `--feature`) uses DES-APPROVAL-DOMAIN-SCOPING-004's **full breakdown** shape: the `approval` check object gains a new sibling field `domains?: { name: string; requirements: ApprovalStatus; design: ApprovalStatus }[]` (present only when domains are configured, absent otherwise) alongside its existing `release`-derived `status`/`diagnostics`; this is a distinct structured field on the check, not encoded into the existing human-readable `summary: string` field (which continues to hold a short prose sentence, now describing the per-domain/release count, e.g. `"2/2 domain(s) and release are current."`), so machine-readable consumers read `domains` directly instead of parsing prose. `approval.valid`/the check's pass/fail is true only when every domain and release are current.
  - `projectStatus` (`gate.ts`) and the CLI `status` formatter (`main.ts`), both existing consumers of `validateApprovals(...).stages`, are updated together with the shape change: when domains are not configured, `projectStatus.approvals` keeps its existing flat `{ stages }` shape and the CLI keeps rendering it exactly as in v0.1.16. When domains are configured, `projectStatus.approvals` instead carries the **full breakdown** shape (`{ domains, release, valid }`) and `projectStatus.next` (the suggested next commands) is generated per entry: each non-`approved` domain stage yields `musubix3 approval prepare/record <stage> --domain <name> ...`, and a non-`approved` `release` entry yields the existing repo-wide `musubix3 approval prepare/record release ...` (no `--domain`). The CLI `status` formatter renders one line per domain per stage plus one `release` line instead of iterating a flat `.stages` array, and never accesses `.stages` when domains are configured.
Interfaces: The existing `add('approval', ...)` block in `gate.ts` branches on `domainsConfigured(config)` and, when `featureDir` is set, on the owning domain of `options.feature`; `gate --json`/`status --json` schema adds a `domains` field directly to the `approval` check object (a sibling of `summary`, not nested inside it) when domains are configured; `projectStatus.approvals` and `projectStatus.next` follow the same branch, and the CLI `status` text formatter branches on the presence of `approvals.domains` rather than assuming `approvals.stages`.
Constraints: Must call DES-APPROVAL-DOMAIN-SCOPING-004's shapes rather than recomputing manifests independently, so `gate --feature <name>`'s reported status for domain D always matches `approval validate --domain D`'s requirements/design entries for the same repository state. If `<name>` in `gate --feature <name>` is not owned by any configured domain, reject the invocation the same way DES-APPROVAL-DOMAIN-SCOPING-005 rejects an out-of-domain `design validate` target (fail closed, no silent repo-wide fallback).
Requirements: REQ-APPROVAL-DOMAIN-SCOPING-019, REQ-APPROVAL-DOMAIN-SCOPING-020, REQ-APPROVAL-DOMAIN-SCOPING-021, REQ-APPROVAL-DOMAIN-SCOPING-022
ADRs: ADR-0021
Depends-On: DES-APPROVAL-DOMAIN-SCOPING-004

## DES-APPROVAL-DOMAIN-SCOPING-007: Backward-compatibility guard
Responsibilities: Ensure every component above is a pure extension gated on `approval.domains` being non-empty: when a project has no configured domains, `approval.ts`, `approval-record.ts`, `tdd.ts`, `gate.ts`, and `main.ts` execute the identical code paths, produce the identical manifest formula/evidence paths, and accept the identical CLI options as musubix3 v0.1.16.
Interfaces: A single `domainsConfigured(config): boolean` predicate (`config.approval.domains.length > 0`) used by every branch point introduced in DES-APPROVAL-DOMAIN-SCOPING-003 through -006, so "not configured" is checked in exactly one place per call site rather than re-derived.
Constraints: Regression coverage for this component uses two separate assertions, since `config.json` is itself a hashed `release`-stage input and an intentional key addition there legitimately changes the release manifest hash: (1) an **unchanged-fixture** assertion — a fixture repository whose `.musubix/config.json` has no `approval.domains` key at all, run against this version, produces byte-identical `requirements`/`design`/`release` manifest hashes, evidence paths, and CLI/gate/status JSON structure to a musubix3 v0.1.16 run of the identical fixture; and (2) an **omitted-vs-empty equivalence** assertion — the same fixture with `.musubix/config.json` differing only by an explicit `approval: { domains: [] }` key produces byte-identical `requirements`/`design` manifest hashes and evidence paths (since neither is a bound input of those two stages) as the omitted-key fixture, while the `release` manifest hash is permitted (and expected) to differ between the two solely because `config.json`'s bytes differ — this expected release-hash difference is not a backward-compatibility violation.
Requirements: REQ-APPROVAL-DOMAIN-SCOPING-024
ADRs: ADR-0021
Depends-On: DES-APPROVAL-DOMAIN-SCOPING-003, DES-APPROVAL-DOMAIN-SCOPING-004, DES-APPROVAL-DOMAIN-SCOPING-005, DES-APPROVAL-DOMAIN-SCOPING-006
