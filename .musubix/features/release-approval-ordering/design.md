# Release approval ordering design

## DES-RELEASE-APPROVAL-ORDERING-001: Tagged release manifest validation
Responsibilities: Define a release-specific Git inventory from a complete candidate path set without changing the existing filesystem inventory used by requirements and design approval; prepare and validate release approval with the same Git inventory and release-stage filters; resolve the requested tag, `HEAD`, and optional `GITHUB_SHA`; reject a different commit or release-input working-tree change; rebuild the tagged release manifest; compare it completely with recorded release approval evidence.
Interfaces: `releaseCandidatePaths(root, runner?) -> Promise<string[]>`; `releaseTaggedPaths(root, tag, runner?) -> Promise<string[]>`; `validateReleaseApprovalForTag(root, tag, approvalConfig, options?) -> Promise<ReleaseApprovalReport>`; `ReleaseApprovalReport = { valid, stage: "release", status: "approved" | "missing" | "stale", diagnostics }`; `ReleaseApprovalDrift = { path, change: "added" | "modified" | "deleted", approvedSha256: string | null, currentSha256: string | null }`; typed schema and Git-precondition errors; injectable process runner support for deterministic Git tests.
Constraints: Git inventory is used only when `git rev-parse --show-toplevel` resolves exactly to `root`; ordinary release approval recording/validation preserves the existing filesystem-inventory behavior for non-Git roots and Git subdirectories. In an eligible Git root, `releaseCandidatePaths`, `approvalManifest(root, "release")`, ordinary release-stage validation, and `validateReleaseApprovalForTag` remain strict and propagate candidate-enumeration failures, so approval is never recorded or evaluated against a materially different filesystem artifact set. Tagged validation additionally requires an exact Git top-level root and propagates unresolved tag, index conflict, malformed Git output, and Git command failures as typed precondition errors. Candidate tracked entries come from NUL-delimited `git ls-files -z -s --cached`, reject unmerged index stages, exclude mode `120000` symlinks and `160000` gitlinks, and omit tracked entries absent from the working tree; candidate untracked entries come from `git ls-files -z --others --exclude-standard` and include only regular files after `lstat`. A pure release path-set filter derives nested workspace and language-generated-directory boundaries only from the complete Git candidate set, preserves evidence/cache and standard generated-directory exclusions, and is applied identically to candidate and tagged path sets; the existing `files()` return value and requirements/design approval manifests remain unchanged. Release-stage filtering excludes feature `trace.json`, `*.tgz`, and log/session-log directories only; `.github/skills/**` remains in release approval, and the skill exclusion in `evidenceInputPaths` is not reused. Tag validation always requires tag commit = `HEAD` and additionally = `GITHUB_SHA` when present. Dirty detection rejects mode/type changes on structurally eligible tracked paths before symlink/gitlink mode exclusion, then limits content/path checks to the union of eligible approved, tagged, and candidate release-input paths; it rejects staged or unstaged additions, modifications, renames, deletions, and eligible non-ignored untracked files because packaging consumes the working tree. The NUL-delimited porcelain parser handles rename/copy records as status plus new path plus old path rather than treating every NUL field as an independent record. Ignored scratch and excluded generated evidence do not block. Required and compatible modes both enforce tag identity, clean release inputs, and stale-manifest rejection; compatible mode relaxes missing approval only. Missing required evidence is invalid with an empty diagnostic array; stale reports every drifted path with a Unicode scalar-value comparator rather than JavaScript default UTF-16 sorting; malformed approval evidence is a typed schema failure rather than drift.

ADRs: ADR-0033

## DES-RELEASE-APPROVAL-ORDERING-002: Release preparation enforcement
Responsibilities: Run the existing tag syntax, version surface, and `GITHUB_SHA` checks first; rebuild derived `dist/` output from the checked-out source tree; then validate the additional tag=`HEAD` and tagged release approval constraints; complete all validation before mutating the release output directory; lazily load the rebuilt analysis API from the repository-derived build path unless an analysis dependency is injected; convert missing or stale approval reports into a typed library error; keep library calls throwable and make only the release-preparation CLI serialize failures.
Interfaces: `verifyReleaseApproval(tag, directory, dependencies?) -> Promise<ReleaseApprovalReport>`; `prepareRelease(tag, output, directory, dependencies?) -> Promise<{ tarball, sbom, checksums }>`; `ReleaseApprovalValidationError` carries a `ReleaseApprovalReport`; dependencies may inject the analysis API and filesystem/subprocess boundaries for tests.
Constraints: The CLI uses top-level `await` through an async `main()` and one terminal catch; it writes successful stdout only after `prepareRelease` resolves, maps `ReleaseVersionValidationError` and `ReleaseApprovalValidationError` to `process.exitCode = 1`, writes no stdout on those failures, and writes exactly one JSON document to stderr. Missing/stale approval uses `{ valid: false, stage: "release", status, diagnostics }`; typed schema or Git-precondition errors use a separate deterministic error code and are never disguised as stale drift. Version-validation errors retain precedence and their existing report and reason contract; the existing version-layer `GITHUB_SHA` assertion remains unchanged and precedes build and the approval-layer `HEAD` check. `prepareRelease` runs the repository's existing `npm run build` through the same injectable subprocess boundary before loading the canonical approval API, ensuring ignored `dist/` bytes are regenerated from the checked-out source tree; build failure is explicit and prevents approval validation and release-output mutation. Approval validation completes before release output removal or creation, and injected tests may supply analysis/version/process dependencies without importing `dist`.
Requirements: REQ-RELEASE-APPROVAL-ORDERING-001 REQ-RELEASE-APPROVAL-ORDERING-002 REQ-RELEASE-APPROVAL-ORDERING-003
ADRs: ADR-0033
Depends-On: DES-RELEASE-APPROVAL-ORDERING-001

## DES-RELEASE-APPROVAL-ORDERING-003: Workflow, tests, and documentation
Responsibilities: Require a manual `workflow_dispatch` to be launched from the same tag ref named by its `release_tag` input, keep checkout on that event ref, and keep the Release workflow ordered as metadata/CHANGELOG finalization, validation and build, release approval, unchanged tag, then release preparation; test required and compatible modes, tag/commit identity and error precedence, approved candidate-to-tag binding, ignored scratch exclusion, eligible non-ignored untracked rejection, malformed evidence, Unicode scalar-value drift order, complete drift classification, CLI streams, output-tree preservation, ambient CI identity isolation, safe workflow ref handling, and rebuild-before-validation ordering; assert the English and Japanese release sections describe the enforced sequence; migrate existing release-version integration tests to the asynchronous preparation API without changing their version-validation assertions.
Interfaces: `.github/workflows/release.yml`; `tests/release-approval-ordering.test.ts`; `tests/release-version-synchronization.test.ts`; shared `caseSafeEnvironment(overrides)` exported from `tests/helpers.ts`; `README.md`; `README-ja.md`; a focused configured quality command with exact `TEST-RELEASE-APPROVAL-ORDERING-*` identities.
Constraints: Release-approval and release-version test subprocess environment overrides use the shared helper,
which removes existing keys case-insensitively before applying overrides.
Setting `npm_execpath` therefore prevents Windows from
retaining an ambient differently-cased npm executable path instead of the
fixture executable. For tag pushes the event ref is already the release tag. For `workflow_dispatch`, a deterministic preflight requires `github.ref_type == "tag"` and `github.ref_name == inputs.release_tag`; mismatch fails before preparation, and checkout uses `${{ github.ref }}` with full history so event `GITHUB_SHA`, `HEAD`, and the requested tag identify the same commit. English and Japanese instructions tell operators to select the target tag in the workflow ref selector and enter that identical tag as `release_tag`. Tests use temporary Git repositories with deterministic commits/tags and injected process or analysis dependencies; existing `prepareRelease` callers use `await` or rejected-promise assertions, split mixed synchronous/asynchronous assertion loops where needed, and inject approval validation in fixtures that intentionally test only version behavior. Tests prove release manifests retain `.github/skills/**` while ignored scratch and nested workspace source are excluded. Red and Green use unchanged authoritative tests; tests set `GITHUB_SHA` explicitly when exercising its contract and do not depend on ambient repository tags, network access, or OS permission denial. Documentation names renewed release approval as mandatory after any committed release-input change, and this change's release process records a fresh release approval after the new manifest semantics are committed.
Requirements: REQ-RELEASE-APPROVAL-ORDERING-001 REQ-RELEASE-APPROVAL-ORDERING-002 REQ-RELEASE-APPROVAL-ORDERING-003 REQ-RELEASE-APPROVAL-ORDERING-004
ADRs: ADR-0033
Depends-On: DES-RELEASE-APPROVAL-ORDERING-002
