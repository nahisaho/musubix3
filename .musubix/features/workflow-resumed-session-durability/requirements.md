# Workflow resumed-session durability

Source: GitHub Issue #32.

## REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-001: Persist and merge verified invocation evidence
Priority: must
Type: functional
Pattern: event-driven
Statement: When a persisting workflow verification succeeds, the system shall persist the verified Skill invocations in a durable ledger and merge later successful persisting verification results into that ledger without requiring previously verified transcript files again.
Acceptance: The ledger is stored in the `reconciliation` field of `.musubix/evidence/workflow.json` as `{ schemaVersion: 1, mode, expectedSessionId?, skewMs, ledgerSha256, bindingsSha256, invocations, bindings }`. Each persisting run has a **run mode** resolved from config plus optional tightening overrides; run mode controls transcript lifecycle validation, multi-file eligibility, and the new provenance source's `mode`. The reconciliation **ledger mode** is `strict` when either the existing ledger mode or current run mode is strict, otherwise compatible; persisted strict is sticky until `workflow-verify --reset-ledger --confirm`. Thus a compatible run may merge compatible sources into a sticky-strict ledger, but those sources remain excluded from strict binding classification. Configured `strict` cannot be weakened: an explicitly supplied persisting API mode of `compatible` fails before writing with `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH` rather than being silently coerced. Only normalized lowercase `config.workflow.expectedSessionId` is initially persisted as `reconciliation.expectedSessionId`; per-run CLI/API session constraints validate the supplied strict transcript and its provenance source but are never promoted into that field. Once persisted, that configured anchor remains sticky even if later config omits it, and only confirmed reset can clear or replace it. When configured and persisted anchors both exist they must match case-insensitively or verification fails before writing with `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH` and names confirmed reset as the only replacement path; any per-run constraint must match the configured-or-sticky anchor when present. Persisted `skewMs` is always exactly `config.workflow.maxEventSkewMs ?? 0`; a supplied persisting-API skew option must equal that value or verification fails before writing with `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH`, while non-persisting transcript validation may use its explicitly supplied lifecycle option. Persisting entry-point options are optional with no synthetic `{ mode: "compatible" }` default, so omitted and explicitly weakening modes remain distinguishable. Both persisting API entry points, `verifyWorkflowLog` and `verifyWorkflowLogFile`, resolve these values, run the same ledger merge and waiver migration, accept the same confirmed reset option, and return `{ workflow, warnings }`, where warnings are non-persisted structured command results; the internal non-persisting sanitizer path does not merge, reset, migrate, or return persistence warnings. A ledger invocation contains exactly `skill`, `toolCallId`, `invokedAt`, optional `completedAt`, `status`, and a nonempty sorted `sources` array; `completedAt` is required for `completed` and `failed` statuses and omitted for `incomplete`, with any violation reported as `WORKFLOW_RECONCILIATION_MALFORMED`. Every source contains `mode` and `sourceSha256`; a `mode: "strict"` source additionally requires non-empty `sessionId` and `transcriptSha256`, while a compatible source omits both strict-only fields. The semantic invocation identity excludes `sources` and is keyed by `toolCallId`; a first verification containing invocation A followed by a later verification containing invocation B produces a ledger containing A and B; re-presenting byte-equivalent semantic A in a later verification is idempotent and unions only its distinct provenance sources, while the cross-file duplicate case within one verification remains rejected by REQ-WORKFLOW-MULTI-SESSION-001. An existing `status: "incomplete"` invocation may be monotonically promoted to `completed` or `failed` when `skill` and `invokedAt` are identical and the later evidence supplies its terminal `completedAt`; the terminal semantic fields replace the incomplete semantic fields and provenance sources are unioned. Re-presenting consistent incomplete evidence after a terminal state is an idempotent no-op on semantic fields that only unions distinct sources, so incomplete/terminal verification runs commute. Any other conflicting skill, start timestamp, completion, or terminal status causes `workflow-verify` to exit nonzero with an error containing `WORKFLOW_INVOCATION_CONFLICT`, the conflicting `toolCallId`, and no evidence modification. `verification.invocations` remains the current-run attested projection only; `reconciliation.invocations` is the authoritative cross-run identity set. Invocations sort by parsed `invokedAt`, parsed optional `completedAt` with missing values last, `skill`, then `toolCallId`; sources sort by `mode`, `sessionId` or empty string, `transcriptSha256` or empty string, then `sourceSha256`; `ledgerSha256` is SHA-256 of the project's exported `canonicalJson` applied to the sorted `invocations` array. The exported `workflowReconciliationLimits` constant is exactly `{ maxInvocations: 10000, maxSources: 50000, maxBytes: 16777216 }`: `maxInvocations` counts ledger invocations, `maxSources` counts all source entries across all ledger invocations, and `maxBytes` measures the UTF-8 byte length of `canonicalJson(reconciliation)`. These durable limits are independent of per-transcript `workflowVerificationLimits` and `config.workflow.maxTranscriptBytes`. An attempted merge exceeding a bound exits nonzero with `WORKFLOW_RECONCILIATION_LIMIT` and preserves prior workflow-evidence bytes; loading out-of-band oversized persisted reconciliation reports the same error-severity diagnostic at `.musubix/evidence/workflow.json`. Recovery is available only through `workflow-verify --reset-ledger --confirm`, which does not modify `workflow.events` and has no prior-verification staleness precondition: after validating the existing declaration-event structure and supplied transcript input, it ignores prior reconciliation, rebuilds reconciliation solely from that input under current run/config values, and atomically replaces workflow evidence. Reset without `--confirm` fails with `WORKFLOW_RECONCILIATION_RESET_CONFIRMATION_REQUIRED`; an invalid event document or transcript, or any rebuilt bound failure, exits nonzero and preserves prior bytes. Every successful update writes workflow verification, ledger, and bindings in one evidence-writer-lock-owned atomic workflow-evidence replacement. `recordWorkflow` invalidates current declaration verification but retains any present `reconciliation` value as clarified below. The internal non-persisting verification path (`persist = false`) used by `workflow-sanitize` validates its selected input/output only and never creates, merges, resets, or writes reconciliation.

`recordWorkflow` clarification for REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-001/004: recording a declaration preserves any present `reconciliation` own-property value byte-for-byte, including a present-invalid value, while clearing current verification as before. It never drops malformed reconciliation into legacy absence; the fail-closed diagnostic remains until confirmed reset or successful persisting verification replaces it.

Configured-session clarification for REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-001: config validation permits `expectedSessionId` only with strict mode. When existing reconciliation omits `expectedSessionId` and current config supplies it, the next successful persisting verification populates the normalized configured value as a monotonic tightening. This absent-to-present case is not a writer-side config mismatch. Once present, the persisted anchor remains sticky if config later omits it; whenever current config supplies an anchor, a different present persisted value is a read- and write-side mismatch requiring confirmed reset.

Source-hash clarification for REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-001: for file-based compatible verification, each invocation source uses SHA-256 of the individual file's own bytes as read from disk, excluding any synthetic inter-file boundary newline used to build the combined stream and independent of other files supplied in the same run; a single-file run therefore uses the same source hash as `verification.sourceSha256`. Strict single-file verification likewise uses that file's own bytes for each source's `sourceSha256`. The text API uses the supplied-text bytes, while multi-file `verification.sourceSha256` remains the complete deterministic combined-stream hash.

## REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-002: Persist deterministic one-to-one declaration bindings
Priority: must
Type: functional
Pattern: state-driven
Statement: While durable invocation evidence exists, the system shall persist and validate a deterministic one-to-one binding from each reconciled completed workflow declaration to exactly one completed Skill invocation.
Acceptance: Each binding contains exactly the declaration's zero-based `eventIndex`, `skill`, `phase`, `recordedAt`, and one ledger `toolCallId`; bindings sort by `eventIndex`, and `bindingsSha256` is SHA-256 of `canonicalJson(bindings)`; no invocation is bound more than once. Verification persists the sticky ledger mode, optional normalized configured `expectedSessionId`, and configured `skewMs`; all later binding and waiver read-side recomputation uses those persisted values. Gate passes its already-resolved configuration into workflow validation rather than reloading it, while status and single/bulk waiver commands load config normally; supplied run options never substitute for those command-resolved config values during the mismatch rule in REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-004. The candidate set for a declaration is every same-skill ledger invocation with `invokedAt <= recordedAt + reconciliation.skewMs`, regardless of status. An invocation is binding-eligible only when it is a candidate, completed successfully, and its `completedAt` is no later than the same boundary. Completed declarations are processed in event order and bind to the earliest unused eligible invocation whose canonical-ledger index is greater than the globally previous bound index across all completed declarations, retaining the existing `WORKFLOW_INVOCATION_ORDER` semantics over canonical ledger order; equal `invokedAt` values are resolved deterministically by the remaining canonical sort keys (`completedAt` missing last, `skill`, then `toolCallId`). Bindings are recomputed from the complete durable ledger and therefore do not change when the same transcripts or verification runs are supplied in a different order. Compatible and strict verification both reconcile declarations against the durable ledger; strict run mode's terminal/session completeness claims apply only to the newly supplied single transcript and do not retroactively classify historical ledger sources as strict. When ledger mode is strict, the strict-source and persisted optional configured `expectedSessionId` filter is applied to all candidates before classifying them as completed, incomplete, failed, reused, or out of order; when persisted `expectedSessionId` exists, at least one strict source's `sessionId` must equal it using the existing case-insensitive UUID comparison, and when it is absent any valid strict source session is accepted. A compatible-only invocation or strict source only for another persisted configured session is excluded from classification and therefore may produce the existing declaration-scoped reason diagnostic (`WORKFLOW_SKILL_NOT_INVOKED`, `WORKFLOW_INVOCATION_ORDER`, `WORKFLOW_INVOCATION_INCOMPLETE`, `WORKFLOW_INVOCATION_FAILED`, or declaration-scoped `WORKFLOW_INVOCATION_REUSED`) paired with `WORKFLOW_BINDING_MISSING`; no new waivable reason code is introduced. Malformed, duplicate, or hash-mismatched persisted bindings always report global `WORKFLOW_RECONCILIATION_MALFORMED` with `severity: "error"` at `.musubix/evidence/workflow.json`. A persisted binding difference from fresh recomputation reports that diagnostic only while current verification is present, its event hash is non-stale, and current config satisfies the reconciliation mismatch rule; after `recordWorkflow`, stale verification, or a config mismatch, the corresponding `WORKFLOW_INVOCATION_UNVERIFIED`, `WORKFLOW_VERIFICATION_STALE`, or `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH` diagnostic is authoritative instead. Cross-session backward clock skew is never rejected as a transcript-lifecycle error solely for being globally non-monotonic; when canonical timestamp order places a later-session invocation before an already-bound invocation, the affected declaration reports waivable `WORKFLOW_INVOCATION_ORDER` when no higher-precedence declaration-scoped reason applies.

## REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-003: Preserve reviewed residuals across unrelated verification updates
Priority: must
Type: functional
Pattern: state-driven
Statement: While an authoritative workflow waiver covers an unchanged declaration-scoped residual, the system shall keep that waiver active when later verification changes only unrelated transcript or invocation evidence.
Acceptance: The exported `workflowScopeEvidenceHead(workflow, eventIndex)` function in `packages/analysis/src/workflow-waiver.ts` hashes with `canonicalJson` exactly the freshly recomputed binding for that declaration or `null`, the persisted `reconciliation.skewMs`, and the semantic fields (excluding provenance `sources`) of canonical-ledger invocations with the same skill whose `invokedAt <= recordedAt + reconciliation.skewMs`; including invocations whose completion is later than that boundary is a deliberate conservative superset of binding eligibility so a potentially material same-skill invocation cannot be omitted from the head. The waiver snapshot uses the declaration fields, disambiguating index, current allow-listed reason code, and that scope-local head. The internal optional `WorkflowReconciliationInstrumentation` callback records `canonicalLedgerBuild` and `scopeHeadComputed(eventIndex)` operations without changing results; during one validation or migration pass, the implementation reports exactly one canonical-ledger build and at most one scope-head computation per distinct `eventIndex`. A deterministic fixture with at least 1,000 ledger invocations and 100 authoritative version-2 waivers over 100 distinct declarations asserts exactly one `canonicalLedgerBuild`, exactly 100 `scopeHeadComputed` callbacks, and no repeated `eventIndex`, rather than elapsed time. A new verification `sourceSha256`, `transcriptSha256`, `verifiedAt`, session identity, duplicate provenance source, invocation for another skill, or same-skill invocation after `recordedAt + reconciliation.skewMs` does not by itself stale the waiver; adding, removing, or changing an invocation included in the scope head, changing canonical order or the recomputed binding, changing the declaration, changing persisted `skewMs`, or changing/resolving the scoped diagnostic changes the snapshot. No previously reviewed unchanged historical residual requires repeated approval solely because a resumed session was verified.

## REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-004: Remain fail-closed under unverified evidence, conflicts, and clock skew
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If current declarations are unverified, a ledger or binding hash is invalid, an invocation identity conflicts, or event timestamps are clock-skewed across sessions, then the system shall reject unsafe reconciliation while preserving source-order lifecycle validation within each transcript.
Acceptance: Throughout validation, waiver evaluation, recording, migration, and attestation, reconciliation is absent only when the workflow object has no `reconciliation` own property; a present `null`, array, primitive, or malformed object is present-invalid and never selects legacy behavior. A legacy workflow document with no `reconciliation` field remains readable and uses its existing verification behavior until the next successful verification creates the ledger and bindings; a workflow with declarations but no current verification continues to report `WORKFLOW_INVOCATION_UNVERIFIED`, and that diagnostic remains non-waivable. A present malformed reconciliation schema, ledger/binding hash mismatch, out-of-band duplicate/conflicting ledger identity, lifecycle error, or reconciliation-limit overflow is error-severity and leaves prior workflow-evidence bytes unchanged; `WORKFLOW_RECONCILIATION_MALFORMED` and `WORKFLOW_RECONCILIATION_LIMIT` are global `workflow.diagnostics` errors at `.musubix/evidence/workflow.json`, while a conflict discovered during an attempted merge uses the non-persisted `WORKFLOW_INVOCATION_CONFLICT` command failure defined by REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-001. Current config mismatches persisted reconciliation only when configured `maxEventSkewMs ?? 0` differs from persisted `skewMs`, configured mode is `strict` while persisted mode is `compatible`, or configured strict `expectedSessionId` is present and persisted `expectedSessionId` is absent or differs after lowercase normalization; persisted strict evidence remains acceptable when current configured mode is compatible or current strict config has no session constraint. Gate, status, and single/bulk waiver-command validation reports such a mismatch as global, non-waivable `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH` in `workflow.diagnostics` with `severity: "error"` at `.musubix/evidence/workflow.json`. While `WORKFLOW_INVOCATION_UNVERIFIED` or any `WORKFLOW_RECONCILIATION_MALFORMED`, `WORKFLOW_RECONCILIATION_LIMIT`, or `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH` error is raised, declaration binding/reason classification, per-scope snapshot recomputation, `WORKFLOW_WAIVER_STALE`, every waiver downgrade, and every active `workflowWaivers` listing are suppressed for both snapshot versions with no fallback to current-run legacy invocation binding. `workflow waiver record` and `workflow waiver record-all` reject every attempted append and preserve waiver evidence until reconciliation is repaired or a persisting `workflow-verify` successfully recomputes it. Compatible multi-session verification does not require globally monotonic timestamps and produces the same ledger and bindings when session files are reversed, while each transcript preserves its own source-order start/completion validation. For declaration binding, absent `maxEventSkewMs` deliberately means zero allowance; existing strict transcript lifecycle checks retain their distinct current absent-value behavior and the setting additionally gates declaration eligibility and scope heads without replacing start/completion or final-terminal skew checks. Strict verification retains its existing one-file terminal-session requirements. Tightening config from compatible to strict requires a new successful strict verification; historical compatible-only sources remain excluded and may produce newly reviewed declaration residuals that can be waived only after mismatch repair, or the operator may revert the config change.

`recordWorkflow` preserves present-invalid reconciliation while clearing current verification as further clarified under REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-001; it never converts that state into legacy absence.

Read-side clarification for REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-004: until absent-to-present configured-session tightening is persisted, read-only gate/status/waiver surfaces report `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH`; the persisting verification path may repair that exact absence but must still reject a different present anchor. A successful persisting verification also repairs skew and mode mismatches by rewriting persisted `skewMs` from current config and applying monotonic ledger-mode tightening; only a differing present `expectedSessionId` blocks the write and requires confirmed reset.

## REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-005: Migrate existing workflow waivers without repeated approval
Priority: must
Type: functional
Pattern: event-driven
Statement: When a successful persisting durable-ledger verification encounters authoritative validly linked workflow waivers recorded with snapshot version 1, the system shall migrate every pending scope to a scope-local snapshot version 2 successor without requiring the operator to approve the same historical residual again.
Acceptance: A **pending migration** is an authoritative, shape-valid, chain-valid, declaration-linked snapshot-version-1 record while reconciliation is present and free of `WORKFLOW_RECONCILIATION_MALFORMED`, `WORKFLOW_RECONCILIATION_LIMIT`, and `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH`, whose fully classified current declaration reason is either the record's same allow-listed `code` or `null`; a suppressed or unavailable reason set is never interpreted as resolved. This single predicate applies both to persisted read-side evaluation and to a successful persisting verification's fully classified in-memory next state. Legacy global-head snapshot staleness does not affect the predicate. An invalid declaration linkage or a scope whose current non-null reason differs is not pending and does not prevent other scopes from migrating. Under the existing evidence-writer lock, after the atomic workflow-evidence replacement succeeds, the system appends exactly one version-2 successor for each pending scope in ascending position of its authoritative version-1 record in the persisted `waivers` array, preserving `skill`, `phase`, `declarationRecordedAt`, optional `index`, allow-listed `code`, `approver`, `reason`, and original `waiverRecordedAt`, assigning `snapshotVersion: 2` plus normal next `sequence`/`previousSha256`/`payloadSha256` values, and computing `snapshotHash` from the post-replacement in-memory next workflow document's version-2 scope-local payload so each successor is non-stale immediately after the waiver write; superseded version-1 records remain byte-identical and non-authoritative, and already-version-2 scopes are not duplicated. This is a system-initiated successor migration, not a `workflow waiver record` invocation, so the human-recording preconditions in REQ-WORKFLOW-EVIDENCE-WAIVER-002/011 do not apply. Validation and successor construction against that in-memory next workflow complete before either write. Migration append is unsafe, and therefore skipped for the whole file, when the waiver document JSON/top-level shape, any record field shape/type including allow-listed `code`, or any `sequence`/`previousSha256`/`payloadSha256` chain value is invalid; these whole-file checks run before pending selection. After they pass, declaration-resolution or scope-linkage failure excludes only that record. The workflow replacement may still succeed in the unsafe-file branch, but the successful `workflow-verify` result and human-readable stderr include warning code `WORKFLOW_WAIVER_MIGRATION_SKIPPED`, distinct from gate/status `WORKFLOW_WAIVER_EVIDENCE_MALFORMED`, stating migration was skipped and remains pending; it is not persisted in `workflow.diagnostics` or `waiverDiagnostics`. After human repair, every later successful persisting verification retries migration without reapproval while any pending version-1 scope remains. If the workflow replacement fails, neither file changes. If the workflow replacement succeeds but waiver replacement fails or execution is interrupted, `workflow-verify` exits nonzero with `WORKFLOW_WAIVER_MIGRATION_WRITE_FAILED`, explicitly states that workflow reconciliation committed and waiver migration remains pending, and the same pending selection is recomputed from authoritative linked version-1 records and retried idempotently on every later successful persisting verification. `workflow-verify --reset-ledger --confirm` follows the same migration rule and therefore does not discard pending approval migration. A successfully returned verification completes every required write; in the unsafe-file branch no waiver write is required. The non-persisting verification path used by `workflow-sanitize` never performs migration. After migration, unchanged residuals remain warning-severity with their waiver object, resolved scopes remain resolved without stale audit noise or active-waiver listing from the superseded version-1 record, and later scope-relevant evidence changes follow REQ-WORKFLOW-EVIDENCE-WAIVER-012. Because version-1 records did not persist their declaration-local payload separately from the global head, this migration cannot distinguish unrelated global-head staleness from an out-of-band historical declaration edit; valid linkage and same-or-resolved next reason are the bounded migration trust criteria. Migration reason classification and successor `snapshotHash` computation use the just-written next state's persisted reconciliation values (including sticky ledger mode, configured anchor, and skew) plus resolved `config.workflow` wherever the read path applies config mismatch rules. Raw per-run option values are not a separate classification input; tightening affects migration payloads only through values persisted into that next state, which later gate/status reads use identically.

## REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-006: Bind durable reconciliation into workflow attestation evidence
Priority: must
Type: functional
Pattern: state-driven
Statement: While durable reconciliation is present, the system shall include its authoritative digest fields in `workflowEvidenceHead` so evidence attestations detect reconciliation changes.
Acceptance: Own-property presence is authoritative: only a document with no `reconciliation` own property uses the legacy branch; a present `null`, array, primitive, or object uses the malformed reconciliation projection. When `reconciliation` is absent, `workflowEvidenceHead` returns its byte-identical pre-CHANGE-0048 digest or `null` when verification is absent. When `reconciliation` is present, it returns SHA-256 of the exported `canonicalJson` serialization of exactly `{ verification, reconciliation }`. The embedded `verification` value is explicit `null` when absent; otherwise it is the exact current full projection object, except that a legacy-short verification is embedded as the object `{ eventsSha256, sourceSha256 }` rather than its old intermediate string or digest. The embedded valid `reconciliation` value contains exactly `schemaVersion`, `mode`, optional `expectedSessionId`, `skewMs`, `ledgerSha256`, and `bindingsSha256`; invocation and binding arrays are represented only through their validated digests. For any present malformed reconciliation value, including `null`, array, primitive, or object, the non-throwing projection contains the five required keys with `null` for missing/wrong-typed values and includes `expectedSessionId` only when it is a valid string. Therefore reconciliation remains attested after `recordWorkflow` clears verification. Two workflow documents differing in any included reconciliation field produce different digests for representative tests, including documents whose verification block uses the legacy short projection or is absent.

## REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-007: Document reconciliation recovery and diagnostics
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The system shall document the operator-visible durable reconciliation controls, limits, and fail-closed diagnostics.
Acceptance: `README.md` documents `workflow-verify --reset-ledger --confirm`, its destructive ledger-only rebuild semantics and transcript requirement, `workflowReconciliationLimits`, monotonic distinct-source growth and reset trade-offs, `WORKFLOW_INVOCATION_CONFLICT`, `WORKFLOW_RECONCILIATION_MALFORMED`, `WORKFLOW_RECONCILIATION_LIMIT`, `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH`, `WORKFLOW_RECONCILIATION_RESET_CONFIRMATION_REQUIRED`, `WORKFLOW_WAIVER_MIGRATION_SKIPPED`, and `WORKFLOW_WAIVER_MIGRATION_WRITE_FAILED`; it explains run mode versus sticky ledger mode, configured-only sticky session anchoring, automatic version-1-to-version-2 migration, the valid-linkage/same-or-resolved trust criterion, that unsafe waiver evidence commits reconciliation with a successful migration-skipped warning, that a post-workflow waiver-write failure throws after reconciliation committed and migration remains pending, and that repairing waiver evidence then re-running persisting `workflow-verify` retries migration. It distinguishes mismatches repaired by a successful persisting verification — rewriting `skewMs`, monotonic compatible-to-strict ledger-mode tightening, and absent-to-present configured session anchoring — from a differing present `expectedSessionId`, which is a mismatch requiring confirmed reset. It separately explains that persisted strict reconciliation remains acceptable and diagnostic-free under compatible config but cannot be relaxed to compatible without confirmed reset, and that an explicitly supplied compatible persisting-API mode under strict config fails with `WORKFLOW_RECONCILIATION_CONFIG_MISMATCH`. It states that changing `maxEventSkewMs` first produces a suppressing config mismatch; after the next successful persisting verification rewrites persisted `skewMs`, affected version-2 scope heads change and their workflow waivers become stale under REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-003, while still-pending version-1 scopes are migrated to non-stale version-2 successors during that same run under REQ-WORKFLOW-RESUMED-SESSION-DURABILITY-005. It explains that tightening compatible evidence to strict may require new residual review when historical strict transcripts are unavailable. The workflow-waiver section states that config mismatch blocks both `record` and `record-all`, and the attestation evidence-head section is updated under REQ-ATTESTATION-EVIDENCE-STABILITY-004.
