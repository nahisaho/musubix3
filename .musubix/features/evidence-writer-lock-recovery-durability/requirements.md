# Accurate post-unlink recovery durability reporting

Source: GitHub Issue #42.

## REQ-EVIDENCE-WRITER-LOCK-RECOVERY-DURABILITY-001: Report post-unlink recovery durability failure accurately
Priority: must
Type: functional
Pattern: event-driven
Statement: When abandoned writer-lock recovery has verified and unlinked the canonical lock but cannot synchronize the containing evidence directory, the system shall report a distinct post-unlink durability failure that accurately states the current lock-removal state.
Acceptance: Recovery keeps every refusal or failure before successful unlink on `EVIDENCE_WRITER_LOCK_RECOVERY_UNSAFE`, performs no mutation for those outcomes, and retains the existing inspection-before-targeted-removal guidance; this is the unchanged unsafe-removal boundary of REQ-EVIDENCE-WRITER-LOCK-004. After verified unlink succeeds, a failure to open, synchronize, or close the containing evidence directory throws `EVIDENCE_WRITER_LOCK_RECOVERY_DURABILITY_FAILED` rather than `EVIDENCE_WRITER_LOCK_RECOVERY_UNSAFE`. Recovery directory synchronization remains strict on every platform and does not apply the Windows unsupported-capability suppression permitted for acquisition and release by REQ-EVIDENCE-WRITER-LOCK-001. The durability error contains the exact canonical lock path, the verified readable owner metadata, always-present `lockRemoved: true`, the original synchronization failure as structured cause, and guidance stating that the path is absent now but crash durability is unconfirmed and that the operator must inspect only the exact reported path before retrying; it never says that the verified lock could not be removed and never instructs the operator to remove a lock known to be absent. `EvidenceWriterLockErrorCode` includes the stable durability code and the analysis error exposes `lockRemoved: true`. JSON CLI output adds top-level `error.lockRemoved: true` for this durability error, omits the top-level field when the property is undefined, and preserves the existing nested `error.rollbackError.lockRemoved` contract unchanged. Human CLI output preserves the existing primary message line, then appends `musubix3: EVIDENCE_WRITER_LOCK_RECOVERY_DURABILITY_FAILED (lockRemoved: true)` and each guidance line to stderr only for this durability error; existing human output for other writer-lock codes remains unchanged. A successful unlink plus successful strict directory synchronization still returns `{ action: "recovered", recovered: true }`. Deterministic injected tests prove the pre-unlink no-mutation unsafe outcome, the post-unlink filesystem absence and durability error fields for a synchronization failure, successful recovery, JSON and human rendering, and guidance text. README.md, README-ja.md, and `evidence unlock --help` document the stable code and distinction between an untouched unsafe lock and an absent lock whose directory-entry durability is uncertain.
