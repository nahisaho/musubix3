# Preflight per-requirement TDD evidence before change phase append

Source: GitHub Issue #47. `change-record` currently validates phase order,
requirement subsets, and changed fingerprints before append, but it does not
prove that every requirement in a Red, Implementation, or Green batch has the
corresponding bounded TDD evidence. A partially covered batch can therefore be
persisted and fail only during later Quality or gate validation.

## REQ-CHANGE-RECORD-TDD-PREFLIGHT-001: Require eligible Red evidence before recording Red
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If `change-record` is invoked for the Red phase, then the system shall reject the recording unless every requested requirement ID has a pending non-void valid TDD Red phase with no Green phase, recorded after that requirement's applicable preceding persisted batch boundary.
Acceptance: Given a staged change requesting requirements A and B where only B has an eligible pending TDD Red phase, `change-record <id> red --requirement A B` exits non-zero with `CHANGE_RED_TDD_PREFLIGHT_FAILED`, identifies A as uncovered, and does not append change or order evidence. After eligible pending Red evidence exists for both A and B, the same recording succeeds. Each requirement uses a Red-specific open-ended window whose exclusive lower bound is the maximum integer Red order across all applicable persisted batches and the Requirements order. Existing malformed change-phase order evidence retains its earlier global record-time rejection; within preflight, a candidate TDD Red with a missing/non-integer order or without matching order-log linkage is uncovered with `missing-order`. If any non-void persisted TDD cycle for the requirement lacks an integer Red order, the requirement is fail-closed with `missing-order` even when another eligible candidate exists. This invocation-time check preserves only the missing-Red-order part of the existing requirement-keyed order-migration condition; a pending cycle's absent future Green order is not a Red or Implementation preflight failure. A cycle for another requirement, a validly voided cycle, a Red with `valid: false`, a Red outside that requirement-specific window, or a cycle that already has Green evidence does not satisfy the preflight. A candidate that fails cycle-local persisted integrity checks for hash-chain payload, command hash, stored test-fingerprint consistency, or phase order linkage is not accepted; filesystem-dependent test staleness, repository-wide requirement coverage, and cross-cycle evidence reuse remain full TDD/gate validation concerns. Because preflight runs before the new change marker is allocated, every already-persisted eligible TDD phase is necessarily earlier than that future marker and no prospective order is consumed to prove this.

## REQ-CHANGE-RECORD-TDD-PREFLIGHT-002: Require bounded Red evidence before recording Implementation
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If `change-record` is invoked for the Implementation phase, then the system shall reject the recording unless the requested batch is the latest applicable Red batch for every requested requirement ID and each ID has a pending non-void valid TDD Red phase with no Green phase inside that current batch window.
Acceptance: Given a recorded Red batch for requirements A and B whose bounded pending TDD evidence proves only B, `change-record <id> implementation --requirement A B` exits non-zero with `CHANGE_IMPLEMENTATION_TDD_PREFLIGHT_FAILED`, identifies A as uncovered, and writes neither phase evidence nor an order entry. For each requirement, the eligible window uses the persisted canonical current window defined by REQ-CHANGE-REQUIREMENT-BATCHES-005 and ends inclusively at the requested batch's Red marker. If a later overlapping Red batch is current for any requested requirement, the older requested batch is rejected for that requirement rather than appending evidence that later validation would supersede. Existing malformed change-phase order evidence retains its earlier global record-time rejection; candidate TDD order/linkage defects are `missing-order`. If any non-void persisted TDD cycle for the requirement lacks an integer Red order, the requirement is fail-closed with `missing-order` even when another eligible candidate exists. Candidates rejected because they name another requirement, are outside the window, are validly voided, have an invalid Red result, already contain Green evidence, or fail cycle-local persisted integrity checks for hash-chain payload, command hash, stored test-fingerprint consistency, or phase order linkage are not accepted. Filesystem-dependent test staleness, repository-wide requirement coverage, and cross-cycle evidence reuse remain full TDD/gate validation concerns and are not duplicated by this preflight.

## REQ-CHANGE-RECORD-TDD-PREFLIGHT-003: Require bounded Red-Green evidence before recording Green
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If `change-record` is invoked for the Green phase, then the system shall reject the recording unless the requested batch is the latest applicable Red batch for every requested requirement ID and each ID has a matching non-void valid TDD Red-Green cycle whose Red is inside that current batch window and whose Green occurs after the requested batch's Implementation marker and before the candidate change Green marker.
Acceptance: Given requirements A and B where both have eligible Red evidence but only B has a matching eligible Green, `change-record <id> green --requirement A B` exits non-zero with `CHANGE_GREEN_TDD_PREFLIGHT_FAILED`, identifies A as uncovered, and does not mutate change or order evidence. If a later overlapping Red batch is current for any requested requirement, the older requested batch is rejected for that requirement. Existing malformed change-phase order evidence retains its earlier global record-time rejection; candidate TDD Red/Green order or order-log linkage defects are `missing-order`. If any non-void persisted TDD cycle for the requirement lacks an integer Red order, the requirement is fail-closed with `missing-order` even when another eligible candidate exists. A cycle for another requirement, a cycle outside the persisted canonical current Red window, a validly voided cycle, an invalid Red or Green result, a Green at or before the requested batch's Implementation marker, or a cycle that fails cycle-local persisted integrity checks for hash-chain payload, command hash, stored test-fingerprint consistency, or phase order linkage does not satisfy the preflight. Filesystem-dependent test staleness, repository-wide requirement coverage, and cross-cycle evidence reuse remain full TDD/gate validation concerns. After matching bounded Red-Green evidence exists for both requirements, the same recording succeeds. The future change Green marker is not allocated during preflight; monotonic append ordering makes every accepted persisted TDD Green earlier than that marker.

## REQ-CHANGE-RECORD-TDD-PREFLIGHT-004: Report deterministic diagnostics without preflight side effects
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The system shall report change-record TDD preflight failures deterministically by phase and requirement while leaving durable evidence unchanged.
Acceptance: Existing format, prerequisite, duplicate, requirement-subset, Quality-coverage, malformed change-phase order, and `CHANGE_*_UNCHANGED_AT_RECORD` checks execute before this TDD preflight and retain their existing diagnostic precedence; the preflight executes after those checks and before candidate construction, order allocation, or evidence writes. It evaluates only the invocation-time persisted `changes.json`, `tdd.json`, and `order.json` snapshot for acceptance; an unpersisted phase or newly allocated empty batch must not participate in batch selection or window calculation. The current authoritative trace mapping may be read only to classify a cycle whose verifying test targets the requested requirement but whose persisted `requirementId` differs as `wrong-requirement`; trace membership is not an additional acceptance condition for a same-requirement cycle. A failed Red, Implementation, or Green preflight reports the phase-specific stable code and the complete sorted set of uncovered requirement IDs. JSON CLI mode returns `error.code` equal to the phase-specific stable code, `error.phase` with value `red`, `implementation`, or `green`, `error.uncoveredRequirementIds`, and `error.rejections`. `rejections` contains exactly one entry per uncovered requirement ID, sorted by `requirementId`; each entry has `{ requirementId, categories }`, where `categories` is a non-empty array of `{ category, details }`. Category entries are deduplicated and ordered by this fixed precedence: `no-candidate`, `wrong-requirement`, `superseded-batch`, `outside-window`, `validly-voided`, `invalid-result`, `missing-order`, `green-already-recorded`, `green-not-after-implementation`, `tdd-validation`. `no-candidate`, `wrong-requirement`, `outside-window`, `validly-voided`, `invalid-result`, `missing-order`, and `tdd-validation` apply to all three phases; `superseded-batch` applies to Implementation and Green; `green-already-recorded` applies to Red and Implementation; and `green-not-after-implementation` applies only to Green. Each `details` value is a sorted, deduplicated string array. `no-candidate` has an empty details array. Every other candidate-related category includes stable candidate references: use a non-empty TDD `cycleId`, otherwise `${testId}@${red.order ?? "unordered"}#${persistedCycleIndex}`, where `persistedCycleIndex` is the zero-based index in the complete persisted `TddEvidence.cycles` array. `superseded-batch` details contain the canonical sorted key of the superseding current batch. `tdd-validation` details use `${candidateReference}:${diagnosticCode}` and include only cycle-local persisted integrity failures, not filesystem-dependent staleness, repository-wide coverage, or cross-cycle reuse. Given requirements A, B, and C where only C has eligible evidence, the diagnostic names A and B in sorted order, contains exactly two rejection entries, and every category other than `no-candidate` has non-empty details. Non-JSON mode includes the same phase-specific code and uncovered IDs. `.musubix/evidence/changes.json` and `.musubix/evidence/order.json` remain byte-identical, including no consumed sequence number. `--dry-run` evaluates the identical preflight and has the same no-write behavior. Existing full-set and subset batch recording that has complete eligible evidence remains compatible. New public-API appends cannot persist a Red, Implementation, or Green phase that lacks its required bounded TDD evidence, and after Green is recorded they cannot create fresh `CHANGE_RED_UNPROVEN` or `CHANGE_GREEN_UNPROVEN` states; the transient `CHANGE_RED_UNPROVEN` diagnostic after Red and before Green remains existing behavior. The existing waivable-code allow-list remains unchanged so historical or deliberately synthesized evidence can still be validated and waived. Change waivers and Quality history do not authorize a new invalid append; they continue to govern only validation of historical evidence.
