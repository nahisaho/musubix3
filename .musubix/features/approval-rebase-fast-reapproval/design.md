# Design / 設計

## DES-APPROVAL-REBASE-FAST-REAPPROVAL-001: Pure eligibility helper reusing the existing drift primitive
Responsibilities: Add a new pure function `fastReapprovalEligibility(previous: ApprovalEvidence, current: Pick<ApprovalManifest, 'artifacts'>, ownFiles: string[]): FastReapprovalEligibility` in `packages/analysis/src/approval.ts`, built on the existing `artifactDrift(previous.artifacts, current.artifacts)` rather than a new comparison algorithm. It normalizes `ownFiles` into a `Set<string>`, computes `drift = artifactDrift(previous.artifacts, current.artifacts)`, then partitions `drift` into `ownChanged` (paths present in the `ownFiles` set) and `outsideChanged` (the remainder). It also computes `unknownOwnFiles`: every `ownFiles` entry absent from both `previous.artifacts` and `current.artifacts` keys. The function returns a discriminated result: `{ eligible: false, reason: 'no-own-files' }` when `ownFiles` is empty; `{ eligible: false, reason: 'unknown-own-files', paths: unknownOwnFiles }` when `unknownOwnFiles` is nonempty (checked before drift classification, since an unrecognized path can never be meaningfully classified as changed-or-not); `{ eligible: false, reason: 'own-files-changed', changes: ownChanged }` when `ownChanged` is nonempty; otherwise `{ eligible: true, outsideChanged }`. This function never touches the filesystem, never writes evidence, and is independent of stage/domain/CLI concerns, matching `artifactDrift`'s own existing purity.
Interfaces: A genuine discriminated union (each variant's fields are required, not independently optional, so a caller can never construct/receive an incomplete diagnostic shape):
```ts
export type FastReapprovalEligibility =
  | { eligible: false; reason: 'no-own-files' }
  | { eligible: false; reason: 'unknown-own-files'; paths: string[] }
  | { eligible: false; reason: 'own-files-changed'; changes: ReleaseApprovalDrift[] }
  | { eligible: true; outsideChanged: ReleaseApprovalDrift[] };
export function fastReapprovalEligibility(previous: ApprovalEvidence, current: Pick<ApprovalManifest, 'artifacts'>, ownFiles: string[]): FastReapprovalEligibility;
```
`ReleaseApprovalDrift.change` uses the existing `'added' | 'modified' | 'deleted'` values verbatim (no new enum); DES-APPROVAL-REBASE-FAST-REAPPROVAL-002's error-message construction is responsible for rendering `'deleted'` as the user-facing word "removed" to match REQ-APPROVAL-REBASE-FAST-REAPPROVAL-002's added/removed/modified acceptance wording — this function itself does not rename it.
Constraints: Never computes or returns any hash narrower than the full manifest hash; `outsideChanged`/`changes` are diagnostic/reporting data only, never used to compute a substitute hash. Empty-`ownFiles` is checked strictly before calling `artifactDrift` (an empty set would otherwise vacuously classify everything as "outside", which REQ-APPROVAL-REBASE-FAST-REAPPROVAL-004 forbids). Unknown-path detection runs before own/outside classification so an unrecognized path is never silently folded into "outside changed".
Requirements: REQ-APPROVAL-REBASE-FAST-REAPPROVAL-002, REQ-APPROVAL-REBASE-FAST-REAPPROVAL-004
ADRs: ADR-0045
Depends-On: none

## DES-APPROVAL-REBASE-FAST-REAPPROVAL-002: Fast re-approval recording path reusing existing preconditions, in a fixed check order
Responsibilities: Add `recordFastReapproval(root, stage, approver, expectedArtifactSha256, ownFiles, config, domainName?)` in `packages/analysis/src/approval-record.ts`, called by the CLI only when `--fast-reapprove` is set, under the same `withEvidenceWriterLock` wrapper `recordApproval` already uses. Extract `recordApprovalUnlocked`'s existing input-shape/structural checks — approver nonempty-after-trim, hash-format, `requireDomainOption`, domain resolution via `resolveDomains`, `validateStageArtifacts`, (for `design`) the existing `if (stage === 'design') await requireApproval(root, 'requirements', requiredApproval, domain)` check, and (for `release`) the per-domain `requireApproval('requirements'/'design', ...)` loop plus `runGate`/non-approval-blockers check — unchanged, in their existing position and order, into a private `validateRecordPreconditions(root, stage, approver, expectedArtifactSha256, config, domainName): Promise<{ normalizedApprover: string; domain: ResolvedDomain | undefined }>`. This helper does **not** compute the manifest or check the hash — manifest computation, the empty-manifest rejection ("No artifacts are available for <stage> approval."), and the exact-hash-match rejection stay as literal, unmoved statements inside `recordApprovalUnlocked` (normal path) and are duplicated verbatim (same code, same message, same position relative to the shared-helper call) inside `recordFastReapproval` (fast path) — this keeps the normal path's statement sequence, computed-manifest count (exactly one `approvalManifest(...)` call), and error messages byte-for-byte identical to before the extraction, with nothing reordered or removed.
`recordFastReapproval`'s full check order, after `validateRecordPreconditions` returns: (1) compute `manifest = await approvalManifest(root, stage, domain)`; if `Object.keys(manifest.artifacts).length === 0`, throw the existing "No artifacts are available for <stage> approval." error; (2) `previous = await loadApproval(root, stage, domainName)`; if `null`, throw `"No prior <stage> approval exists to fast-reapprove against."` (REQ-004); (3) if `ownFiles.length === 0`, throw `"--own-files must list at least one path."` (REQ-004); (4) compute `unknownOwnFiles` (every `ownFiles` entry absent from both `previous.artifacts` and `manifest.artifacts` keys); if nonempty, throw naming those paths (REQ-004); (5) if `normalizedApprover !== previous.approver`, throw `"Fast re-approval requires the original approver (<previous.approver>)."` (REQ-003) — `normalizedApprover` is the same post-trim value `validateRecordPreconditions` already computed for format validation, so this applies the one normalization (surrounding whitespace) the rest of the system already applies to every approver input, not a new or different normalization than the non-fast path uses; (6) if `manifest.artifactSha256 !== expectedArtifactSha256`, throw the existing "Approval artifact manifest changed: expected ..., current ..." error verbatim (REQ-005); (7) call `fastReapprovalEligibility(previous, manifest, ownFiles)`; if `eligible` is `false`, throw a reason-specific error built from its `changes`/`paths` (REQ-002), rendering any `'deleted'` drift entry as "removed". On success, write `{ schemaVersion: 1, ...manifest, approver: previous.approver, approvedAt: new Date().toISOString(), fastReapproval: true, priorArtifactSha256: previous.artifactSha256 }`.
This order checks structural/baseline-existence conditions (steps 1-4) before identity (step 5) before the full-hash binding (step 6) before content-drift classification (step 7), so each REQ-APPROVAL-REBASE-FAST-REAPPROVAL-002/003/004/005 acceptance scenario (each of which varies exactly one condition at a time, with every earlier-in-order condition satisfied) deterministically surfaces its own designated error.
Interfaces: `export async function recordFastReapproval(root: string, stage: ApprovalStage, approver: string, expectedArtifactSha256: string, ownFiles: string[], config: ApprovalConfig, domainName?: string): Promise<ApprovalEvidence>`. Internal refactor: `private async function validateRecordPreconditions(root: string, stage: ApprovalStage, approver: string, expectedArtifactSha256: string, config: ApprovalConfig, domainName?: string): Promise<{ normalizedApprover: string; domain: ResolvedDomain | undefined }>`, called identically by both `recordApprovalUnlocked` (which then continues with its own existing manifest/hash/write statements, completely unmoved) and `recordFastReapproval`.
Constraints: `recordApprovalUnlocked`'s observable behavior (statement order, error messages, exact single manifest computation, written evidence shape) for every existing passing and failing scenario is unchanged by the extraction — verified by the existing `tests/approval.test.ts`/`tests/approval-domain-scoping.test.ts` suites passing unmodified. The approver persisted in fast-reapproved evidence is always `previous.approver` (already proven equal to the CLI's trimmed `--approver` input by step 5), never a value that could silently diverge. `artifactSha256`/`artifacts` in the written evidence come from the same `approvalManifest(...)` call used by the non-fast path, byte-for-byte (REQ-APPROVAL-REBASE-FAST-REAPPROVAL-005).
Requirements: REQ-APPROVAL-REBASE-FAST-REAPPROVAL-001, REQ-APPROVAL-REBASE-FAST-REAPPROVAL-002, REQ-APPROVAL-REBASE-FAST-REAPPROVAL-003, REQ-APPROVAL-REBASE-FAST-REAPPROVAL-004, REQ-APPROVAL-REBASE-FAST-REAPPROVAL-005, REQ-APPROVAL-REBASE-FAST-REAPPROVAL-006, REQ-APPROVAL-REBASE-FAST-REAPPROVAL-007
ADRs: ADR-0045
Depends-On: DES-APPROVAL-REBASE-FAST-REAPPROVAL-001

## DES-APPROVAL-REBASE-FAST-REAPPROVAL-003: Evidence schema extension and CLI wiring
Responsibilities: Extend `ApprovalEvidence` in `approval.ts` with two optional fields, `fastReapproval?: true` and `priorArtifactSha256?: string`, added via conditional spread wherever evidence objects are constructed (per this repository's `exactOptionalPropertyTypes: true` convention — never assigning an explicit `undefined`). Extend `loadApproval`'s schema validation to accept evidence with either field absent (existing shape, unchanged acceptance) or both fields present and well-formed (`fastReapproval === true` and `priorArtifactSha256` matching the existing 64-hex-character pattern already used for `artifactSha256`); reject evidence where exactly one of the two is present, or where `fastReapproval` is present but not exactly `true`, with the same existing `"Invalid <stage> approval evidence."` error. Add a `--fast-reapprove` boolean option and a `--own-files <path...>` variadic option (Commander, matching the existing `--requirement <ids...>` variadic pattern) to the `approval record <stage>` command in `main.ts`; when `--fast-reapprove` is set, the action calls `recordFastReapproval(...)` instead of `recordApproval(...)`, passing `options.ownFiles ?? []`; `--own-files` without `--fast-reapprove` is rejected by the CLI action with a clear "`--own-files` requires `--fast-reapprove`" error (prevents a confusing no-op flag combination), and `--fast-reapprove` without `--own-files` reaches the same empty-list rejection REQ-APPROVAL-REBASE-FAST-REAPPROVAL-004 already requires.
Interfaces: `approval record <stage> --approver <name> --artifact-sha256 <hash> --confirm [--domain <name>] [--fast-reapprove --own-files <path...>]`. `ApprovalEvidence` gains `fastReapproval?: true; priorArtifactSha256?: string;`.
Constraints: `--json`/non-JSON output rendering for `approval record` is otherwise unchanged; the same `Recorded explicit <stage> approval by <approver> for <hash>.` summary line is printed for both paths (no new divergent summary format), since the evidence shape difference is already fully captured by the JSON output's new optional fields.
Requirements: REQ-APPROVAL-REBASE-FAST-REAPPROVAL-001, REQ-APPROVAL-REBASE-FAST-REAPPROVAL-006
ADRs: ADR-0045
Depends-On: DES-APPROVAL-REBASE-FAST-REAPPROVAL-002
