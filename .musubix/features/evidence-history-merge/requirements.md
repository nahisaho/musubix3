# Deterministic merge of append-only evidence histories

Source: GitHub Issue #28. Independent Git branches can each contain valid
append-only `.musubix/evidence` histories whose repository-wide order sequences
overlap. Standard text conflict resolution cannot safely resequence the merged
history and rewrite every dependent order/hash reference.

## REQ-EVIDENCE-HISTORY-MERGE-001: Merge the current and incoming valid evidence histories
Priority: must
Type: functional
Pattern: event-driven
Statement: When `evidence merge --incoming <directory>` is invoked, the system shall merge the current root's evidence history with the evidence history under the incoming directory.
Acceptance: Given two directories whose `.musubix/evidence/order.json`, `tdd.json`, `changes.json`, and optional `change-waivers.json` files are individually structurally valid, and given that the current worktree already contains the non-evidence requirement, design, change, source, and test files needed by newly introduced incoming payloads, the command preserves the current root's order records in their existing relative order, appends every non-duplicate incoming order record in the incoming history's relative order, and reports order-record counts named `preserved`, `deduplicated`, and `appended`. `EVIDENCE_MERGE_WORKTREE_INCOMPLETE` and no write result only when an incoming `changes.json` entry that is not already represented by an equivalent base payload lacks `.musubix/changes/<changeId>.md`, or an incoming waiver payload that is not already represented by an equivalent base payload references a change document absent from the current worktree. Existing base records and order records with no dependent payload are exempt. The incoming directory is read-only, and its real path after symlink resolution must neither equal, contain, nor be contained by the current root's real path. The command accepts an absent optional `change-waivers.json` as an empty waiver history, including when unpaired waiver order records exist, but rejects a missing required order, TDD, or change evidence file. Base-first ordering is intentional: every appended incoming order record has a later correctness-bearing order than every base record regardless of `recordedAt`; an incoming payload retained on a deduplicated base order record keeps that base chronology. Any resulting `CHANGE_RECORDEDAT_OUT_OF_ORDER` diagnostic remains a warning rather than merge corruption.

## REQ-EVIDENCE-HISTORY-MERGE-002: Rebuild all merged order and hash-chain references
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The system shall deterministically rebuild every sequence, predecessor hash, record hash, and dependent order reference in the merged evidence.
Acceptance: Given a successful merge, `.musubix/evidence/order.json` contains consecutive sequences starting at 1 with valid `previousSha256` and `recordSha256` values; every retained TDD phase, migrate, and void `order` points to its corresponding merged order record; every retained change phase or requirement-batch phase `order` points to its corresponding merged order record; and every retained change waiver payload `order` points to its corresponding merged waiver order record. The TDD `chain` is rebuilt in merged logical order with each `phaseEvidenceSha256` recomputed from the resequenced phase evidence and each chain sequence, predecessor hash, and record hash recomputed. The change-waiver `previousSha256` and `payloadSha256` chain is rebuilt in merged logical order without changing its approval-bearing fields or `snapshotHash`. Every non-reconstructed property is carried through verbatim; rebuilt known fields use a fixed documented property order for existing JSON-string hash functions, and unknown fields retain their original relative property order. Duplicate comparison uses canonical key-sorted JSON after excluding only sequence, order, predecessor-hash, record-hash, payload-hash, and phase-evidence-hash fields. Candidate structural validation permits no `EVIDENCE_ORDER_*`, `TDD_CHAIN_*`, `TDD_ORDER_MISMATCH`, `TDD_ORDER_SEQUENCE`, `TDD_VOID_EVIDENCE_MALFORMED`, `CHANGE_ORDER_MISMATCH`, `CHANGE_PHASE_ORDER`, or `EVIDENCE_MERGE_QUALITY_ORDER` diagnostic, and separately verifies waiver record shape, `previousSha256`/`payloadSha256` chain continuity, and each waiver payload `order` against its merged waiver order record. For each retained change independently, `EVIDENCE_MERGE_QUALITY_ORDER` is emitted when that change's Quality order is not greater than a Red or Implementation order in that same change's retained persisted batches; Green ordering remains covered by the existing `CHANGE_PHASE_ORDER`, so the Green case does not additionally emit `EVIDENCE_MERGE_QUALITY_ORDER`. Each diagnostic names the offending `<changeId>:<phase>`. A candidate failure reports `EVIDENCE_MERGE_CANDIDATE_INVALID` with every underlying diagnostic code, target file, and entity or phase identity and performs no write. For a base change whose Quality order precedes an appended incoming batch phase, the report directs the operator to combine histories before recording Quality, then record Quality against the merged history. A `CHANGE_WAIVER_EVIDENCE_MALFORMED` instance caused only by missing change documents, missing change chronology payloads, a requirement declaration mismatch outside REQ-001's explicit incoming-payload precondition, or a waived condition that no longer holds because the merge supplied the missing evidence (including `CHANGE_RECORD_MISSING` superseded by a merged chronology record) is reported separately rather than treated as structural merge corruption. Worktree-dependent coverage, fingerprint, completeness, other document-presence diagnostics, and `CHANGE_WAIVER_STALE` are also reported separately. The `cycles`, `changes`, and `waivers` arrays, plus each retained change's persisted `tddBatches` array, use a stable base-first merge: retained base entries keep their relative array positions, distinct incoming entries follow in incoming relative order, and an equivalent duplicate retains the base position.

## REQ-EVIDENCE-HISTORY-MERGE-003: Deduplicate identical records and reject ambiguous conflicts
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If the current and incoming histories contain an ambiguous logical-record conflict, then the system shall reject the merge without selecting either record implicitly.
Acceptance: A logical TDD phase is identified by cycle ID and phase; a logical non-waiver change phase is identified by change ID and exact phase or sorted requirement-batch key; a waiver order record is exactly an order record with `kind === "change"` and `phase === "waiver"`; and a logical change waiver is identified by its change/code/requirement/detail scope plus approver, reason, recordedAt, snapshot version, and snapshot hash. Including `recordedAt` is intentional: otherwise identical waivers recorded independently remain distinct superseding records. Within each input history, an order record is paired to a dependent payload by the payload's pre-merge `order` equaling that order record's pre-merge `sequence`, then by the order record's entity/phase/scope fields; this permits multiple superseding waivers with the same scope. Non-waiver order-record deduplication first matches `kind`, `entityId`, `phase`, and optional `testId`, `code`, `requirementId`, and `detail` scope regardless of whether either side currently has a dependent payload. An equivalent base order record is retained and counted as deduplicated; if only one side has a payload, that payload is retained and rewritten to the base order sequence; if both sides have payloads, their logical identities and canonical payloads must be equivalent. Two non-waiver order records with the same `kind`, `entityId`, and `phase` but different `testId` fail with `EVIDENCE_MERGE_CONFLICT` even when both dependent payloads are absent, preventing a later `EVIDENCE_ORDER_DUPLICATE`. A paired waiver order record deduplicates when both waiver payloads have the same logical waiver identity: the base order record and payload are retained, the incoming pair is dropped, and the base order record is counted as deduplicated. Only an unpaired waiver order record remains sequence-distinct and is never deduplicated. Persisted change `tddBatches` are matched by sorted requirement-batch key only when that key is unique among persisted batches on each input side; the synthesized legacy full-set batch derived from top-level change phases does not participate in persisted-batch matching. If a key that must be matched occurs more than once in either input's persisted `tddBatches`, the command fails with `EVIDENCE_MERGE_CONFLICT` naming `<changeId>:<batchKey>` rather than selecting one by array position. The assigned merged sequence must be strictly increasing when traversing each input's pre-merge order; if deduplication would map a later incoming record behind an already mapped incoming record, the command fails with `EVIDENCE_MERGE_CONFLICT` naming that record rather than invert chronology. Given the same cycle ID with different `requirementId`, `testId`, `testPath`, or `commandName`; the same change ID with different top-level `requirementIds`; the same change/batch key with different batch membership; matching TDD/change phase identities with different evidence payloads; duplicate cycle IDs or change IDs within one input; a missing, extra, or duplicate TDD chain identity relative to the retained `(cycleId, phase)` payload set; a dependent payload with no order record; a dependent payload with more than one order record; or an order record with more than one dependent payload, the command fails with an `EVIDENCE_MERGE_CONFLICT` diagnostic naming the conflicting entity or `<cycleId>:<phase>` identity. Different cycle IDs remain distinct even when they use the same test ID, and distinct compatible TDD batches remain distinct.

## REQ-EVIDENCE-HISTORY-MERGE-004: Apply a merge atomically
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If validation, reconstruction, or persistence of an evidence merge cannot complete, then the system shall leave the current root's evidence files byte-identical to their pre-command state.
Acceptance: Before replacing any target file, the command constructs and validates the complete merged `order.json`, `tdd.json`, `changes.json`, and `change-waivers.json` candidate set in memory. It records the original bytes and existence plus the merged candidate bytes and SHA-256 digest of every target in a transaction journal, writes the candidate set through temporary sibling files, and replaces targets only after all candidates and temporary files are valid. After every replacement succeeds, it durably records a commit marker containing the candidate digests before removing merge-owned temporary files and the journal. A malformed input, conflict, failed candidate validation, or injected failure at any write or replace boundary exits nonzero and restores the original bytes or original absence of every target. `evidence merge --recover` requires no incoming directory and resolves a pending valid journal before input resolution: with no canonical journal or staging file it exits successfully with a deterministic `nothing-to-recover` report; with staging files but no canonical journal it removes the unpublished staging files and exits successfully with `nothing-to-recover` plus `discardedStaging: true`; it restores the original target set when no durable commit marker exists; when the marker exists, it validates the journaled candidate bytes structurally, compares every on-disk target SHA-256 with the marker, rewrites a missing or mismatched target from the journaled candidate bytes, and removes recovery files only after all target digests and structural checks pass. A normal merge that encounters staging files but no canonical journal exits with `EVIDENCE_MERGE_RECOVERY_REQUIRED` and directs the operator to run `--recover`; under this phase's documented single-writer assumption, recovery may discard a concurrent merge's unpublished staging, whose later exclusive publication then fails before any target mutation. A transient I/O or write failure exits nonzero with `EVIDENCE_MERGE_RECOVERY_REQUIRED`, preserves the journal and candidate bytes, and permits the same recovery command to be retried. Structural invalidity of the journaled candidate bytes or a target digest/structural verification failure that persists after rewriting from those bytes causes `EVIDENCE_MERGE_RECOVERY_UNSAFE` and uses the manual-remediation report defined below instead of entering a retry loop. Journal publication is the atomic operation that makes a complete journal visible at `.musubix/evidence/.merge-transaction.json`; an unpublished staging file is not a present journal for general evidence-command fail-fast purposes because publication precedes every target mutation. An unreadable, unparseable, or schema-invalid published journal also causes `EVIDENCE_MERGE_RECOVERY_UNSAFE`, exits nonzero, and mutates neither targets nor recovery files; every unsafe-recovery diagnostic reports the journal path and merge-owned temporary-file inventory plus documented manual remediation steps to back up the evidence directory, restore or verify the four targets from a trusted source, quarantine the invalid recovery files, and rerun structural validation. If the canonical merge journal is already present when a command starts, every command that reads or writes `.musubix/evidence` except `evidence merge --recover`, including normal merge and dry-run modes, fails fast with `EVIDENCE_MERGE_RECOVERY_REQUIRED` and does not inspect or mutate the potentially torn evidence set.

## REQ-EVIDENCE-HISTORY-MERGE-005: Preview and document the deterministic merge
Priority: must
Type: functional
Pattern: event-driven
Statement: When `evidence merge --incoming <directory> --dry-run` is invoked, the system shall report the deterministic merge plan without modifying evidence.
Acceptance: With no canonical merge journal and no staging file, dry-run performs the same input validation, conflict detection, resequencing, hash reconstruction, waiver-staleness detection, and candidate structural validation as a real merge; returns the same order-record `preserved`/`deduplicated`/`appended` counts, candidate-invalid underlying diagnostics, non-fatal follow-up diagnostics, stale-waiver entries, affected waiver-supersession scopes, revalidation-required flag, and per-file changed/unchanged summary; writes no target, journal, or temporary file; and exits nonzero for the same invalid or ambiguous inputs. With a canonical journal, or with staging files but no canonical journal, dry-run exits nonzero with `EVIDENCE_MERGE_RECOVERY_REQUIRED` and writes nothing, matching normal merge; recovery requires `evidence merge --recover`. A successful dry-run or merge reports `EVIDENCE_MERGE_REVALIDATION_REQUIRED` when any incoming order record is appended or any incoming dependent payload is retained, explains that base-first incoming precedence, restored payload array position, or greatest-order waiver selection may change latest-cycle, latest-batch, or authoritative per-scope waiver selection, lists every `(changeId, code, requirementId?, detail?)` scope whose greatest-order validly-linked authoritative waiver differs between the base history and merged candidate, and does not claim that the current worktree is release-ready until normal gate validation is rerun. It also reports non-fatal `EVIDENCE_MERGE_WAIVER_STALE` entries for every retained waiver whose unchanged approval-bearing `snapshotHash` no longer matches the merged worktree/evidence state; such waivers remain in the hash chain but inactive and require explicit re-approval through the normal waiver workflow. `evidence merge --help`, `README.md`, and `README-ja.md` document the worktree precondition, incoming-directory contract, canonical duplicate comparison, base-first ordering, possible `recordedAt` warnings, candidate-invalid diagnostics and the Quality-before-merge remedy, inactive stale-waiver and waiver-supersession reporting, transaction recovery and `--recover`, `EVIDENCE_MERGE_RECOVERY_UNSAFE` manual remediation, dry-run usage, post-merge revalidation, and the requirement that both histories be individually structurally valid.
