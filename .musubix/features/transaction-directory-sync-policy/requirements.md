# Platform-scoped transaction directory synchronization policy

Source: GitHub Issue #43.

## REQ-TRANSACTION-DIRECTORY-SYNC-POLICY-001: Apply platform-scoped transaction directory synchronization policy
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The system shall use one explicit platform and error-code classification for every supported transaction directory synchronization operation.
Acceptance: A shared classifier returns unsupported only for Windows `EPERM`, `EINVAL`, or `ENOTSUP`; it returns actionable for `EISDIR`, `EACCES`, unknown codes, every Linux or macOS error, and every non-error value. This exactly preserves the evidence writer-lock allowlist and the observed `EPERM` result from the Node 22 Windows Core failure referenced by Issue #43. The origin and intended platform of the old combined-boundary `EISDIR` allowance are not documented; it is removed deliberately rather than treated as evidence of a Windows capability. A future Node/libuv version or filesystem that reports `EISDIR` remains fail-closed, and a Windows Core failure with that code is investigated as an allowlist-provenance or runtime-change question before any policy expansion. Asynchronous and synchronous directory synchronization use this same classifier and an explicit `allow-unsupported | strict` policy. Evidence writer-lock publication, acquisition rollback, and release remain `allow-unsupported`; evidence writer-lock recovery remains `strict`. The policy applies only around synchronization of an already-open directory handle: directory opening and closing are outside the suppression boundary and every open or close failure propagates. Windows read-only directory opening relies on libuv's unconditional `FILE_FLAG_BACKUP_SEMANTICS` assignment in `fs__open` and is exercised without injection by the Windows Core temporary-directory test; if it nevertheless fails with `EISDIR`, `EACCES`, or another open error, the transaction fails rather than broadening suppression. If both synchronization and close fail, the close failure is primary, matching the deterministic native `finally` cleanup contract; an allowlisted synchronization failure followed by a close failure therefore still fails, and no secondary sync cause is promised. Module-local writable-file synchronization remains outside the directory-error suppression boundary.

The single classifier, policy type, and minimal asynchronous directory handle interface `{ sync(): Promise<void>; close(): Promise<void> }` are defined and exported by `packages/analysis/src/filesystem-durability.ts`, carry the requirement's `CODE-*`/`@implements` trace annotation, and are re-exported from `packages/analysis/src/index.ts`. Evidence writer lock imports and re-exports the same policy symbol without a local redeclaration; Quality refresh and evidence merge import that definition rather than retaining local allowlists. Quality refresh and evidence merge continue to retain their existing module-local writable-file `fsyncFile` helpers, synchronize transaction files through those helpers, and open transaction directories read-only. Their package-reachable helper signatures remain source-compatible as `fsyncQualityRefreshDirectory(path, openDirectory?, platform?)` and `fsyncEvidenceMergeDirectory(path, openDirectory?, platform?)`, where `platform` has the fixed type `() => NodeJS.Platform`; the optional platform callback is additive, an explicitly omitted `openDirectory` does not shift `platform` into another parameter position, and `openDirectory` returns the minimal handle interface so deterministic tests require no unsafe cast. A call shaped as `helper(path, undefined, platform)` uses the default read-only directory opener and passes `platform` positionally to the shared helper; the classifier effect is demonstrated separately with an injected opener. The synchronous writer-lock helper retains its direct `openSync`/`fsyncSync`/`closeSync` lifecycle and consumes the same classifier and policy; its existing injected synchronization callback and shared-classifier tests provide deterministic sync-error coverage, while existing writer-lock integration tests retain lifecycle coverage. Every normal commit, rollback, roll-forward, journal publication, commit-marker publication, and cleanup directory synchronization site uses `allow-unsupported`, because those transaction operations must remain usable when Windows cannot synchronize an already-open directory handle.

At the shared directory-helper boundary, an actionable open, sync, or close failure rejects with the original Node filesystem error without wrapping or mutating any `code`, `path`, `syscall`, or other fields present on that error; a descriptor-based sync error is not required to gain a `path` field it did not originally contain, and a close failure remains primary when it supersedes an earlier sync failure. The open boundary follows the already-shipped evidence writer-lock lifecycle, which opens outside its suppression catch and is exercised on `windows-latest`. At the transaction API boundary, a non-injected directory-sync failure after journal publication follows the existing transaction contract without attempting rollback: normal Quality refresh reports `CHANGE_QUALITY_REFRESH_RECOVERY_REQUIRED`, normal evidence merge reports `EVIDENCE_MERGE_RECOVERY_REQUIRED`, and each message includes the original error message while leaving the journal and transaction-owned files in their actual post-failure state for explicit recovery or inspection; code never recreates a file already removed before a cleanup durability failure.

The existing normal-catch rollback branch remains limited to its test-only injected operation failures while the journal is prepared; it is not broadened to production filesystem failures. If directory synchronization fails inside that injected rollback branch, the failure reports the corresponding unsafe-recovery diagnostic and derives its owned-path snapshot from the in-memory canonical journal path and journal target temporary paths. During explicit prepared-journal rollback or committed-journal roll-forward recovery, an actionable directory-sync failure likewise reports `CHANGE_QUALITY_REFRESH_RECOVERY_UNSAFE` or `EVIDENCE_MERGE_RECOVERY_UNSAFE`, includes the original error message, canonical journal path, and a snapshot of transaction-owned paths identified at recovery entry, exits nonzero, and performs no automatic retry. The snapshot may identify a path that was subsequently removed before the failing durability boundary and is labeled as an owned-path inventory rather than a claim of current existence. Files already rewritten or removed remain exactly as observed, and the diagnostic directs manual verification rather than claiming rollback. Only directory-sync durability failures use the new inventory-bearing unsafe formatter; all pre-existing unsafe validation, coexistence, digest, and file-I/O diagnostics retain their current formatter and message contract. On Linux and macOS, or for a Windows open, close, `EISDIR`, `EACCES`, or unknown-code failure, these rules prevent success from being reported. This fail-closed result is intentional on network/shared filesystems and on non-Windows permission-constrained directories as well as other filesystems that cannot synchronize directories; documentation directs the operator to use storage and permissions that support directory synchronization.

TEST-TRANSACTION-DIRECTORY-SYNC-POLICY-001 verifies the shared classifier matrix and strict behavior. TEST-TRANSACTION-DIRECTORY-SYNC-POLICY-002 verifies Quality refresh and evidence merge open, sync, close, and original-error propagation boundaries with injected handles. TEST-TRANSACTION-DIRECTORY-SYNC-POLICY-003 verifies normal recovery-required and explicit prepared-journal rollback unsafe diagnostics, original error message, journal/owned-path reporting, and absence of automatic retry for actionable directory-sync failures. TEST-TRANSACTION-DIRECTORY-SYNC-POLICY-004 calls both production helpers against a real runner-local temporary directory without injection and asserts only successful completion: on Windows, the fail-closed open and close boundaries mean completion proves both succeeded while sync either succeeded or encountered an allowlisted unsupported code; on Linux and macOS, completion means synchronization succeeded because no failure is suppressible. This production-path smoke test proves integration only for the runner-local temporary filesystem and current runtime; injected tests prove the accepted and rejected policy outcomes, while network, shared, and permission-restricted filesystems remain documented fail-closed cases rather than simulated portability claims. TEST-TRANSACTION-DIRECTORY-SYNC-POLICY-005 verifies that an omitted `openDirectory` does not shift the supplied `platform` callback into the opener position, unchanged evidence writer-lock policy assignments, the injected normal-catch rollback unsafe boundary, and committed-journal roll-forward unsafe recovery for both transaction implementations. In `tests/transaction-directory-sync-policy.test.ts`, the two exported helpers and legacy `EvidenceDirectorySyncPolicy` name are imported through the package index; raw helper exports are assigned directly, without casts, to the declared legacy and current function shapes so positional signature drift fails type checking. TEST-WINDOWS-CORE-PORTABILITY-003 and TEST-WINDOWS-CORE-PORTABILITY-004 prove at runtime that the third-position platform callback controls classification by using an injected already-open handle and passing `() => 'win32'` explicitly so their result is host-independent; they retain links to REQ-CHANGE-QUALITY-REFRESH-001 and REQ-EVIDENCE-HISTORY-MERGE-004 and add links to this requirement. README.md and README-ja.md document the Windows-only durability boundary, non-Windows fail-closed behavior including permission-constrained directories, preserved filesystem diagnostic, and remediation.
