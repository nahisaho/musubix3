# Safe evidence writer-lock acquisition rollback

Source: GitHub Issue #41.

## REQ-EVIDENCE-WRITER-LOCK-ACQUISITION-ROLLBACK-001: Roll back only the failed acquisition's published lock
Priority: must
Type: functional
Pattern: event-driven
Statement: When writer-lock acquisition has published the canonical lock but fails before returning a lease, the system shall perform a verified fail-closed rollback that preserves the acquisition failure as primary.
Acceptance: Immediately after atomic hard-link publication and before directory synchronization, the system captures the published lock's device/inode identity from the still-open staging descriptor whose inode the hard link published, without resolving the canonical path again; capture failure is itself a post-publication acquisition failure and never returns a lease. Before rollback unlink, the system re-reads complete owner metadata and re-observes device/inode identity, then requires the owner canonical root and transaction ID to equal the failed acquisition and the device/inode identity to equal the captured published identity. Because acquisition has not returned a lease or established an externally usable ownership guarantee, a lock that is already absent during verification or vanishes with `ENOENT` at unlink is a completed rollback with no directory synchronization requirement, no guidance, and no `rollbackError`; this pre-lease absence differs intentionally from REQ-EVIDENCE-WRITER-LOCK-004 release-time absence. If the published identity was not captured, or an existing lock is unreadable, malformed, canonical-root-mismatched, transaction-ID-mismatched, or device/inode-replaced, the system performs no unlink and rollback fails. After a verified rollback unlink, the system synchronizes the containing evidence directory under the same platform policy as normal release: non-Windows open, sync, and close failures are fail-closed; on Windows only `EPERM`, `EINVAL`, or `ENOTSUP` from syncing an already-open directory handle is classified as unsupported. When the lock is already absent, vanishes at unlink, or verified unlink and required directory synchronization both succeed, rollback is successful and the existing best-effort empty-directory cleanup applies only to directory levels created by that acquisition. Every failure after canonical publication is normalized to a primary `EVIDENCE_WRITER_LOCK_ACQUIRE_FAILED` error that retains the original failure as structured cause. If published-identity capture, identity verification, unlink, or required post-unlink directory synchronization prevents a complete rollback, that primary `EvidenceWriterLockError` exposes a public `rollbackError` property containing one secondary `EvidenceWriterLockError` with code `EVIDENCE_WRITER_LOCK_ROLLBACK_FAILED`, message, exact lock path, always-present `lockRemoved: boolean`, structured cause, any readable owner in its `owner` property, and targeted inspection/removal guidance; `lockRemoved` is true only when unlink completed, including when subsequent synchronization failed. A failure before unlink reports that the lock may remain and distinguishes the failed acquisition's own readable owner, unavailable owner metadata, and a readable root/transaction/device/inode mismatch that identifies a foreign replacement lock which must not be removed as failed-acquirer cleanup. A post-unlink synchronization failure reports that the path is absent now but crash durability is unconfirmed and instructs the operator to inspect only the exact path before retrying. JSON CLI output includes the same fields under `error.rollbackError` and uses the existing cause projection of `{ name, message, code? }` for an `Error` or `{ message }` for another defined value. Human CLI output keeps the existing primary message on stderr, then appends the rollback code, message, lock-removed state, and guidance to stderr when present; successful rollback has no `rollbackError`. README.md, README-ja.md, command help, the `sdd-change`, `sdd-implementation`, and `sdd-quality` skills, and rollback guidance document the rollback code and lock-removed state; they state that a retained lock can record the still-live failed acquirer even though no lease was returned, owner metadata may instead be unavailable, a mismatched readable owner is a replacement lock that must not be removed as failed-acquirer cleanup, automatic recovery refuses a demonstrably live acquirer, automatic recovery is preferred after it exits, and operator-confirmed targeted removal of only the exact reported lock path is the fallback after verifying that no related acquisition remains active. The three skills retain REQ-EVIDENCE-WRITER-LOCK-006's fewer-than-80-lines limit by appending the rollback semantics within existing lines so the measured line count remains unchanged, not by raising the limit. The published-identity capture and rollback unlink operations are independently injectable so capture and non-`ENOENT` unlink failures are deterministic. Injected analysis tests prove descriptor-based published identity capture; missing published identity; absent-at-verification and vanished-at-unlink success; unreadable and malformed metadata; canonical-root and transaction-ID mismatch; device/inode replacement; non-`ENOENT` unlink failure with `lockRemoved: false`; successful verified unlink followed by directory synchronization and created-directory cleanup; and synchronization failure with `lockRemoved: true`, durability guidance, and the acquisition error preserved as primary. Deterministic CLI tests prove the JSON rollback fields and both cause projections plus the human rollback code, message, lock-removed state, and guidance. Skill-content and packed-copy tests prove the distributed recovery guidance and unchanged line limit.
