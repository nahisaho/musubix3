# Attestation evidence-head stability across no-op `gate` re-runs

Source: GitHub Issue #21. A signed, successfully-verified `attestation`
(`attestation.mode: "ci-required"`) was reported to become `status: invalid`
after a later, unrelated `gate` re-run performed with zero source/config
changes. The reporter's own hypothesis was that non-deterministic content
regenerated by `gate` (`quality.json`/`performance.json`) leaks into
`collectEvidenceHeads`'s `evidenceHeads.quality`/`evidenceHeads.performance`.

Investigation against the current `packages/analysis/src/attestation.ts`
confirms `heads.quality` and `heads.performance` are already computed from a
deliberately narrowed, canonicalized projection (dropping `generatedAt`,
`durationMs`, `stdout`/`stderr`, and any `attestation`-named check/metric,
and sorting each execution's nested `tests` array), and `heads.workspace` is
a content digest of `files(root)` filtered by `evidenceInputPaths`, where
`files(root)`'s directory walk (`packages/analysis/src/files.ts`) never
descends into `.musubix/evidence/**`, so regenerated evidence files
themselves cannot perturb `heads.workspace` either. The actual root cause
is narrower: `mutationEvidenceHead` (`packages/analysis/src/mutation.ts`),
in the pre-fix baseline this change addresses, sorted the outer
`executions` array by full canonical content, but only projected (did not
sort) each execution's nested `mutants` array before canonicalizing it. A
mutation command that legitimately emits its mutant list in a different
array order across two otherwise-identical runs (for example iterating a
`Map`/directory listing whose enumeration order is not guaranteed stable)
therefore produced a different `evidenceHeads.mutation` digest on the next
`gate` run, invalidating any attestation that bound the earlier digest,
even though no mutation actually changed.

## REQ-ATTESTATION-EVIDENCE-STABILITY-001: All evidence heads stay stable across a no-op gate re-run in every mode
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The system shall produce identical `collectEvidenceHeads` output (across every key it populates for a given project) across two consecutive `gate` invocations run in the same mode (full, `--changed`, or `--feature`) when no non-evidence input included by `evidenceInputPaths(files(root))` changes between them.
Acceptance: Given a fixture project that deliberately seeds every supported evidence input so that `collectEvidenceHeads` populates all ten keys (`tdd`, `workflow`, `changes`, `order`, `formal`, `performance`, `mutation`, `modelCorrespondence`, `quality`, `workspace`), and given no change to any non-evidence input included by `evidenceInputPaths(files(root))` between two consecutive `gate` runs in the same mode, `collectEvidenceHeads(root)` after the first run deep-equals `collectEvidenceHeads(root)` after the second run (all ten keys), for each of the `full`, `--changed`, and `--feature` modes independently.

## REQ-ATTESTATION-EVIDENCE-STABILITY-002: `mutationEvidenceHead` is invariant to mutant array order
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The system shall canonicalize `mutationEvidenceHead`'s input so that reordering the `mutants` array within any `MutationExecution` element, without changing its content or multiplicity, produces the same canonicalized representation before hashing.
Acceptance: Given two `MutationEvidence` values whose `executions` arrays contain the same executions and whose corresponding executions' `mutants` arrays contain the same multiset of mutant records in a different order, `mutationEvidenceHead` returns an identical digest for both values; given two such values where a representative mutant field or the mutant count genuinely differs, `mutationEvidenceHead` returns different digests for those specific tested cases.

## REQ-ATTESTATION-EVIDENCE-STABILITY-003: A signed attestation remains valid after a no-op gate re-run with reordered mutation evidence
Priority: must
Type: functional
Pattern: event-driven
Statement: When a `gate` re-run following a signed and verified `ci-required` attestation regenerates mutation evidence containing the same mutants in a different array order with no other tracked or evidence-input change and within the same accepted CI run context and configured attestation age/skew limits, the system shall continue to report that attestation as valid on re-verification.
Acceptance: Given a signed and verified `ci-required` attestation, when `gate` is re-run — within the same accepted CI provider/run context and within configured `maxAgeSeconds`/`maxFutureSkewSeconds` limits — with a mutation command that reports the same mutants in reversed array order and no other tracked or evidence-input file changes, `verifyEvidenceAttestation` reports `{ valid: true, status: 'verified' }` for the existing signed attestation.

## REQ-ATTESTATION-EVIDENCE-STABILITY-004: Evidence-head composition is documented
Priority: must
Type: functional
Pattern: ubiquitous
Statement: The system shall document, for each key `collectEvidenceHeads` can populate, its direct input or projection (an evidence file, a repository input snapshot, or another named source) and either the exact retained fields or the exact fields deliberately excluded from that key's canonicalization.
Acceptance: `README.md` contains a section listing all ten `collectEvidenceHeads` keys, each naming its direct input or projection (explicitly labeling any whole-file-hash or repository-snapshot entries as such rather than implying a narrower evidence-file source) and stating either its exact retained fields or its exact excluded fields, verifiable against `collectEvidenceHeads` and the per-entry head functions it delegates to.
